# Implementation: the first PR series

How `sentinel.md` becomes code, in an order where each PR is reviewable alone, has its own tests, and leaves `main` importable. Agreed 2026-09-21; PR 0 opened 2026-09-22.

## Goal

The minimal surface that lets `inspect_ai` connect: the types a dispatcher constructs, the decorators an author writes against, the runner a protocol calls, and the three protocols the compile rule needs. No `inspect_ai` dispatcher yet; that is the next series, on inspect_ai's `feature/sentinel` branch.

## Decisions

The decisions that stand, as of 2026-10-06. The entries below record how each was reached; the PR sections name things as they were when each landed.

- **Sentinel is the surface; inspect_ai hosts it.** Sentinel ships types, decorators, the runner and the protocols, tested with fake `Host` and `Recorder`. inspect_ai's dispatcher, `Host` and `Recorder` live on inspect_ai's `feature/sentinel`.
- **Real registration.** `@monitor` and `@protocol` register under `"monitor"` and `"protocol"`, added to `inspect_ai`'s `RegistryType` by PR 0 ([inspect_ai#5514](https://github.com/UKGovernmentBEIS/inspect_ai/pull/5514), branch `feature/sentinel`). Sentinel's `inspect-ai` git ref points at that branch until it merges.
- **Tool stages only, for now.** `BeforeToolCall` and `AfterToolCall`; `Step` is their union. The generate stages are sentinel #42, a draft.
- **`Host` is the author-facing ABI**: `generate` and `ask_human`, with `fetch` planned ([Context and Host](#context-and-host), [human()](#human)).
- **Recording is the runner's, through `Recorder`**, which the host implements and authors never call. Five methods, each taking the instance's `Context` and its factory's registry name: `record`, for every participating child's report; `failed`, for a monitor that raised ([Failure policy](#failure-policy)); `cancelled`, for a child cancelled before it reported; `bypassed`, for a protocol a descendant's `decide_final()` ended the step past; and `superseded`, for a `decide_final()` decision that lost a race or was outranked by an exception in the same layer. Recording is not on the `Host` ABI.
- **`Context` is the author's, `HostContext` the host's.** `Context` is immutable and has `path`, `host`, `eval` (an `EvalContext`, `None` outside an eval) and `store_as()`, and no private fields. The host passes `HostContext(host, recorder, store)` to `run_sentinel` (since 2026-10-14 `host` is its `HostNative` and `HostContext` builds the top `Context`; before, the host built the `Context` and passed it), which keeps the runner's state in a per-step context variable ([Interface cleanup](#interface-cleanup), [Eval-only context](#eval-only-context-under-contexteval)).
- **Author surface vs integration surface.** `__init__` exports what an author writes against, including `Reported`, `Report`, `Failed`, `MonitorFailedError` and `PortabilityError`. `_integration.py` re-exports what inspect_ai needs (`HostContext`, `Recorder`, `validate_instance_name`, `step_types`, `resolve_sentinel`, `Sentinels`, `run_sentinel`, `sentinel_from_config`, `config_from_sentinel`). inspect_ai takes integration names from `_integration` and author types (`Decision`, `Step`, `EvalContext`, `HumanAnswer`, …) from the top-level package.
- **Shipped protocols:** `observe_only`, `concurrent`, `sequential`, `threshold` and `human`. `Task(sentinel=)` requires a protocol: monitors alone are an error naming `observe_only()` and `threshold()`.
- **Imports from `inspect_ai.core`** where a name is there: the wire types since sentinel #59, `SentinelAction` and `SentinelSuspicion` since #60 ([inspect_ai.core imports](#imports-from-inspect_aicore)).
- **Portable by default.** `portable=True` is checked when a factory is called ([Portable monitors](#portable-monitors-and-protocols-are-checked-when-configured)).

## PR 1: types

`_step.py`, `_report.py`, `_context.py`. Data only.

```python
Stage = Literal["tool_call", "tool_result"]        # grows with the generate stages

@dataclass(frozen=True)
class BeforeToolCall:
    conversation: str
    message: str
    call: ToolCall
    view: ToolCallView
    input: list[ChatMessage]
    history: list[ChatMessage]
    escalations: tuple[Reported[Decision], ...] = ()

@dataclass(frozen=True)
class AfterToolCall:
    conversation: str
    message: str
    call: ToolCall
    result: ChatMessageTool
    output: ToolResult
    view: ToolCallView
    input: list[ChatMessage]
    history: list[ChatMessage]

Step = BeforeToolCall | AfterToolCall
```

`escalations` references `Reported`, so PR 1 defines it in `_report.py` rather than leaving it to the runner PR. *Superseded 2026-10-14: escalations are a protocol's third parameter, not a step field; see [Escalations are a protocol parameter](#escalations-are-a-protocol-parameter).*

```python
Suspicion = float | dict[str, float]  # finite; a dict has at least one key
Action = Literal["proceed", "modify", "reject", "terminate", "escalate"]

class Observation(BaseModel):
    suspicion: Suspicion
    explanation: str | None = None
    metadata: dict[str, Any] | None = None
    @classmethod
    def score(cls, suspicion, explanation=None) -> Observation
    @classmethod
    def flag(cls, explanation=None) -> Observation     # suspicion=1.0

class Decision(BaseModel):
    action: Action
    audit: bool = False
    modified: ToolCall | None = None                    # ChatMessageAssistant joins with AfterGenerate
    explanation: str | None = None                      # log-only; the agent never sees it
    message: str | None = None                          # what the agent reads; reject only, for now
    metadata: dict[str, Any] | None = None
    @classmethod proceed / reject(explanation, *, message) / terminate / escalate

Report = Observation | Decision

R_co = TypeVar("R_co", bound=Report, covariant=True)  # covariant so Reported[Decision] flows into Reported[Report]

@dataclass(frozen=True)
class Reported(Generic[R_co]):
    name: str
    path: str
    report: R_co
```

```python
class Host(typing.Protocol):
    async def generate(self, input: str | list[ChatMessage], *, model: str | None = None,
                       role: str | None = None, tools: list[ToolInfo] | None = None,
                       tool_choice: ToolChoice | None = None,
                       config: GenerateConfig | None = None) -> ModelOutput: ...

class Recorder(typing.Protocol):
    def record(self, context: Context, step: Step, reported: Reported[Report]) -> None: ...
    def cancelled(self, context: Context, step: Step, name: str) -> None: ...
    def bypassed(self, context: Context, step: Step, name: str) -> None: ...
    def superseded(self, context: Context, step: Step, reported: Reported[Decision]) -> None: ...

@dataclass(frozen=True, kw_only=True)
class Context:
    task: str | None
    task_description: str | None
    sample_id: str | int | None
    epoch: int | None
    sample_description: str | None
    input: str | list[ChatMessage]
    metadata: dict[str, Any]
    path: str
    store: Store
    host: Host
    target: Target | None = None
    def store_as(self, model_cls: type[SMT]) -> SMT      # instance=self.path

@dataclass(frozen=True, kw_only=True)
class RunnerContext(Context):
    recorder: Recorder
    def child(self, name: str) -> RunnerContext          # path joined with "/"
```

Tests: report constructors set the fields the design says; `Observation` and `Decision` round-trip through pydantic JSON (they are serialized into `SentinelEvent`); `Decision.modified` accepted for `modify` and rejected otherwise is *not* checked here (that is the boundary check, PR 4); `store_as` namespaces by `path`; `child()` composes paths from an empty and a non-empty parent and returns a `RunnerContext`.

## PR 2: decorators and registration

`_monitor.py`. Stage inferred from the second parameter's annotation; kind is the decorator; return annotation must agree, checked at decoration time. `registry_tag`/`registry_add` from `inspect_ai._util.registry`, as `@approver` does. Sentinel's git ref moves to `feature/sentinel`.

Tests: stage inference for each payload and for `Step`; an unannotated second parameter is an error; `@monitor` on a function annotated `-> Decision | None` is an error, and vice versa; `registry_create("protocol", "no_curl")` resolves; factory params recorded in registry info.

Implemented: stages are read at factory-call time from the returned function's second-parameter annotation via `get_type_hints` and stored on the instance; `stages(instance)` exposes them to the runner and is integration surface. A union of stage payloads registers at every member. The return annotation must be the report type, optionally with `None`. `registry_create` is not a construction path for sentinels: it instantiates only factories whose return annotation's class name equals the registry type, and `Monitor`/`Protocol` are union aliases, so it returns the factory uncalled and `inspect_ai` deliberately has no `registry_create` overload for the two types, which makes such a call a type error. Configuration and replay construct through `create_registry_object`.

## PR 3: runner

`_runner.py`. Per child: skip when not annotated for the stage (indistinguishable from abstention); name from mapping key or registry name, duplicate within a layer is an error; derive the child context with `child()`; record every participating report through `context.recorder`; exceptions propagate. Plural forms fan out with anyio (own `tg_collect`, no inspect_ai dependency); `run_protocols` cancels siblings on `terminate`. `run_children` runs both families in one task group.

Tests use a list-backed `Recorder` and a stub `Host`. Cover: filtering, naming and the duplicate error, path derivation, every participating report recorded including ones the caller ignores, `max_suspicion()` over scalar and dict suspicion, `strongest()` precedence, sibling cancellation on `terminate`, a raising child fails the call, `TypeError` on a bare `Context`.

Implemented: the decorators store the accepted payload classes on each instance and `step_types(instance)` (runner-facing, not exported) reads them; the runner filters with `isinstance`, so there is no stage-name vocabulary in the filter. Children are named by mapping key or by `registry_unqualified_name`, since a package-qualified registry name (`acme/suspicion`) would put the path separator inside a segment; two packages' monitors sharing a leaf name in one layer therefore collide, and the duplicate-name error tells the author to name them with a mapping. `run_monitor` and `run_protocol` check the child's registry type; `run_monitors`, `run_protocols` and `run_children` all validate their children once in `named_children` and then fan out through one private `_run_named`, which owns the `terminate` cancellation. The task-group unwrap catches `ExceptionGroup` only, never `BaseExceptionGroup`, so a cancellation travelling with an error propagates intact, as in inspect_ai's `tg_collect`. `Observation` now rejects an empty structured suspicion, since `max_suspicion()` has no answer for it. Exceptions propagate unconditionally: the failure policy (warn and continue for a monitor nothing consumes, `fail="open"`) is not implemented here and is not PR 4's either; it needs a per-child hook in `_run_child`, because by the time an exception leaves the task group the siblings' results are gone, and it will be added with that hook in a later PR. A child cancelled before it reported, whether by a sibling's `terminate` or by cancellation from above, is recorded through `Recorder.cancelled()`, and a recorder that raises there fails the layer exactly as one raising from `record()` does, so no recorder bug is hidden behind a log line; cancellation lands at a child's next await, so one that finishes without awaiting is recorded normally. When several children fail concurrently only the first exception surfaces, and a child raising its own `ExceptionGroup` passes through as a group; both match inspect_ai's `tg_collect` and the deferred failure-policy hook will want the sibling errors.

## PR 4: protocols, boundary check, final decisions, resolve, integration

`_protocols.py`, `_check.py`, `_final.py`, `_resolve.py`, `_integration.py`, `_registry.py`, and the `inspect_ai` entry point in `pyproject.toml`.

- `observe`: records, returns `None`.
- `concurrent`: `run_children`; `strongest()`; a `modify` with more than one deciding child becomes `reject` naming the modifier.
- `threshold(monitors, reject_at, terminate_at=None)`: as written in `sentinel.md` (*superseded: keyword-only `escalate_at`, `reject_at` and `terminate_at`; [threshold escalates and terminates without reject](#threshold-escalates-and-terminates-without-reject)*).
- `validate_decision_shape(decision, step)` raises on the deterministic protocol bugs: an action illegal for the stage (`reject` and `modify` are `BeforeToolCall` only), or `modified` not set exactly when `action == "modify"`.
- `decide_final(decision)` ends the step: it raises `Final`, a `BaseException`, which the runner records as the calling protocol's decision after the shape check, then carries past every layer above, recording each through `Recorder.bypassed()` and cancelling siblings as `terminate` does. The dispatcher catches it at the root. It replaces the `binding` field and the floor the runner clamped to.
- `resolve_sentinel(spec)`: monitor or monitors-only collection to `observe`; anything else containing a protocol to `concurrent`; every configuration wrapped, so a lone protocol is `concurrent([protocol])` and a lone monitor `observe([monitor])`, and a lone child records the same paths as a list of one. `observe`, `concurrent` and `threshold` raise `ValueError` when given no children.

Tests: each protocol's rules above; every row of the resolve table; each shape rule raising; a `decide_final()` passing every layer above, recorded, bypassing and cancelling; two racing `decide_final()`s; an error beside a `decide_final()`; `decide_final()` from a monitor.

Implemented: both checks take the `Step` rather than a stage string, so the payload type stays the stage identity; the runner applies the shape check as each protocol returns or calls `decide_final()`, so a shape error names the leaf; `Final` carries its origin (the calling protocol's context, step and `Reported` decision) from its first catch; each layer it passes records itself as bypassed immediately, a `Final` that loses a race is recorded as `superseded` at the group where it lost, and the decision is recorded once, by `run_sentinel`, when it takes effect, so a `Final` escaping `run_protocol` or `run_children` below the root is not yet recorded; nested exception groups, including a protocol's own task group, are flattened to their leaves and resolved by one policy in both places, so a protocol's own group mixing an error and final decisions surfaces the error and supersedes the decided ones, as a runner group does; a protocol or monitor whose own `decide_final()` fails supersedes the child decisions beside it before raising; a `Final` raised by a monitor's own body is a `TypeError` naming the monitor, since a monitor returns observations, while one made by a protocol the monitor ran propagates and records the monitor as bypassed; in a task group an exception outranks a `Final`, and of several `Final`s the first to arrive escapes and the rest are superseded; when an exception outranks them, every one is recorded as superseded; `resolve_sentinel` reuses the runner's `named_children` so duplicate names and uncalled factories fail at configuration time, classifies a single instance with `is_registry_object` so a set, an iterator or a string gets `named_children`'s message rather than being wrapped in a list, and warns through `logging` for a monitors-only configuration, naming each instance as it is configured, so an explicit `observe()` is how to say recording is intended; the three shipped protocols register as `inspect_sentinel/<name>` through the `inspect_ai` entry point in `pyproject.toml`; inspect_ai imports `RunnerContext`, `Recorder`, `validate_instance_name`, `step_types`, `resolve_sentinel`, `Sentinels` and `run_sentinel` from `inspect_sentinel._integration` only; `run_sentinel` records the resolved root as a layer at `path=""` under its unqualified registry name and returns a `decide_final()` decision as the outcome, so the dispatcher never catches `Final`; `concurrent` records every decision it makes, and when more than one protocol decided its explanation lists each one's decision after the winner's own; `validate_decision_shape` does not re-check `modified`'s type, which `Decision` validates. `threshold` is `BeforeToolCall`-only, as designed, because `reject` is not legal after a tool call.

Known limit: a `terminate` outrun by a sibling's `decide_final()` inside a protocol's own task group, rather than `run_children` or `run_protocols`, is not marked superseded; its record stands as written.

## PR 5: multi-function factories

**Multi-function monitors (agreed 2026-09-25).** A `@monitor` or `@protocol` factory may return a sequence of functions instead of one. The group is one configured instance: one instance name, one `path`, one child context, and so one `store_as` namespace that every member shares; that is the point, since accumulating across stages is the trajectory-score case the design argues for and closure state is wrong for it (created once per configuration, shared across samples). Members are told apart by the inner function's `__name__`, recorded as a `function` field on `Reported` and `SentinelEvent`; path plus function identifies a report, and read-mode validation keys on both. Duplicate function names within one factory are a configuration error, checked when the factory is called. The decorators validate each member and record the union of their payload types; the runner treats the group as one child and dispatches to every member that accepts the step, so one instance may contribute several reports at a step, which `Observations` and `Decisions` already accommodate as sequences. Each member still watches exactly one stage, so "One function, one point" stands; what changes is that a factory may emit several functions when they share state, which is the class-with-a-method-per-stage the design rejected, reached through functions so the static scan and per-function portability verdict still work. Two instances of one factory, and two samples, keep separate state as before. `sentinel.md` "One function, one point", "Instance names", and the `SentinelEvent` listing need updating.

Implemented: `run_monitor` and `run_protocol` are removed; `run_monitors`, `run_protocols` and `run_children` accept one instance, a sequence or a mapping and always return a possibly empty sequence, since one instance may now report more than once; `named_children` treats any callable as a single instance, so an uncalled factory or an undecorated function still gets its own message. A factory returning a sequence (not a string) gets a private group object, a `MonitorGroup` or `ProtocolGroup`, registry-tagged and carrying the union of its members' payload types, whose `__call__` is typed so it fits every `Monitor` or `Protocol` alias and raises `TypeError` if called directly. `_run_child` derives one child context and runs the members that accept the step through `_run_member`, which holds the per-function shape checks, the `decide_final()` handling and the recording; a group cancelled part way is recorded once, through `Recorder.cancelled`, at the instance level. The fan-out collects a group's reports as they are recorded, so a group cancelled after one member reported returns that report, as a lone child that finished first does; a member's `terminate` stops the group, since nothing outranks it: the members after it do not run, so none can override it with `decide_final()`, and sibling instances are cancelled as for a lone child. `Reported.function` is set for every report, a lone function's included. `threshold` requires every function of every monitor to watch `BeforeToolCall`, since it runs only there and a member watching another stage would never run. `run_sentinel` rejects a group, since the root is what `resolve_sentinel` returns and a step has one outcome. `concurrent` counts votes by instance, so a group's `modify` is contested only by another instance's decision or by another of its own functions modifying, and its explanation labels a group member's vote `name.function`.

## S6: configuration

`_config.py`. `sentinel_from_config(config)` builds a sentinel from the YAML/JSON shape in `sentinel.md` "Configuration" through `create_registry_object`; `config_from_sentinel(sentinels)` is the inverse, for the log and `eval_retry`. Also drops the unused public `Stage` alias, since `SentinelEvent` declares its own stage literal.

Implemented: the shape is `SentinelConfig`, a pydantic `RootModel` over a list of `SentinelEntry` or a mapping of instance names to them; an entry has `name`, `params`, an optional `version` and an optional `meta` (see [Versions in the log](#versions-in-the-log)), and any other key is kept as a pydantic extra validated as a nested `SentinelConfig`, so the model serializes to exactly the YAML shape and `entry.nested` returns the nested layers. `sentinel_from_config` accepts a file whose only key is `sentinel`, a bare registered name (a list of one), the model or the plain list or mapping; it walks the plain shape itself rather than through pydantic, so each error names the entry path (`sentinel.attempt.children[1]`), and a `TypeError` or `ValueError` from a factory is re-raised with the path prepended. A nested key is legal exactly when the factory's signature has that parameter, and may not also appear in `params`; there is no `tools` key. Names are looked up as both monitor and protocol, and `@monitor` and `@protocol` refuse a name already registered as the other kind, so at most one matches; a bare name that matches nothing exactly is then tried as `inspect_sentinel/<name>`, as `registry_lookup` does for `inspect_ai/`, so a local factory shadows a shipped one of the same name without making either unrebuildable. A file is parsed as JSON and otherwise as YAML (PyYAML rejects tab-indented JSON), with mappings loaded as pairs so a repeated key is an error naming the file and entry path. A factory with `**kwargs` accepts any nested key, since `registry_tag` records those arguments under their own names. The result is the list or mapping of instances, unresolved. `config_from_sentinel` reads `registry_value` of each instance, whose params already hold nested instances as registry dicts, and writes a non-empty list or mapping of monitor or protocol registry dicts as nested entries; `@monitor` and `@protocol` refuse a factory with a parameter named `name`, `params`, `version` or `meta`, the entry's own keys, so only a `**kwargs` argument of one of those names reaches it, and that stays in `params` in registry-dict form; a lone instance is recorded as a list of one, and a package name is written bare when the bare name finds it unambiguously. Both functions and both models are exported from `_integration`, not the author-facing `__init__`: authors write Python or YAML, and the model is for inspect_ai's log and CLI.

## S7: the factory name for the log

`SentinelEvent.name` is the registry name of the factory and `path` the instance path, but the `Recorder` had no way to learn the registry name: `Reported.name` is the instance name, `cancelled` and `bypassed` receive only the instance name, and `Context` carries no registry name, so for `{"attempt": chain(...)}` the dispatcher could only record `name="attempt"`, repeating the path's last segment.

Implemented: `RunnerContext` gains `factory: str`, the full registry name as `registry_info(child).name` gives it (package prefix included), defaulting to empty so the dispatcher's top-layer context need not know the root; `child(name, factory)` takes it and the runner passes each child's registry name when it derives the child's context; `run_sentinel` sets it on the root's own context, so the root's decision, its `bypassed` record and any `decide_final()` origin at the root carry it. The `Recorder` methods take a `RunnerContext` rather than a `Context`, since the runner always passes one, so the dispatcher reads `context.factory` without a cast. A `terminate` superseded by a sibling's `decide_final()` is re-derived with its factory's name, as the other records are. `Reported` is unchanged: the instance name is what authors compare, and the factory is recording metadata.

## No outcome field

Decided with the user 2026-09-29: `SentinelEvent.outcome` is removed (inspect_ai c6d332ba6). What the layer above did with a report is the decision event at the parent path, so the field only duplicated the log. Which child a top-level result came from stays inferred by the viewer, exact after `decide_final()`.

## Threshold explanations

Implemented, agreed with the user 2026-09-29: a terminate names the highest-scoring monitor (first in configuration order on a tie) and carries its explanation: `suspicion 0.95 from audit: <reason>`. It previously said only `suspicion 0.95`. The reject at first carried no explanation, to keep the reasoning from the agent; superseded by [Decision.message and single-instance protocols](#decisionmessage-and-single-instance-protocols), which makes `explanation` log-only, so the reject now carries the same explanation.

## Decision.message and single-instance protocols

Implemented, agreed with the user 2026-09-29: `Decision` gains `message: str | None`, the only text the agent reads from a decision; `explanation` is log-only. `Decision.reject(explanation, *, message=None)` takes it keyword-only and the other constructors do not. The shape check allows `message` only on a `reject`, since "proceed, but tell the model X" needs a way to deliver text while the step proceeds, which does not exist yet. `threshold`'s reject and terminate both carry `suspicion 0.95 from <name>: <reason>` and neither sets `message`, so the agent gets the host's default "not approved" text. `observe`, `threshold` and `concurrent` take a single instance as well as a sequence or mapping (`Monitor | Monitors`, `Monitor | Protocol | Children`), matching `run_monitors`, so `threshold(suspicion_monitor(), reject_at=0.8)` type-checks. The inspect_ai dispatcher must pass `message`, not `explanation`, to the agent.

## decide_final()

Renamed from `final()` with the user 2026-09-30: `final` shadowed `typing.final` and read as a decorator, while the function raises and ends the step. A verb says that nothing after it runs. The exception it raises is still the internal `Final`.

## Public names

Decided with the user 2026-09-30, before the first release, so nothing is kept for compatibility:

- The protocol alias is `Protocol`, not `ControlProtocol`: it pairs with `@protocol` as `Tool` pairs with `@tool`. The collision with `typing.Protocol` is accepted; the package imports typing's as `TypingProtocol`, and the docs say "a control protocol, not `typing.Protocol`" on first use. The decorator stays `@protocol`, the registry type `"protocol"`, and the plural `Protocols`.
- `Decision.clear()` is `Decision.proceed()`, which says what happens to the step rather than what the protocol concluded; it still produces `proceed`.
- `Reports`, what `run_children` returns, is a `NamedTuple` of `observations` and `decisions`, so `observations, decisions = await run_children(...)` works beside named access.
- The planned ordered composition is `sequential`, not `chain`: it pairs with `concurrent` and does not collide with `inspect_ai.solver.chain`. It shipped 2026-10-01 (see "sequential()").
- `Reported` keeps its name. It was reviewed as a possible verb form of `Report`; read as an adjective on its type parameter, like `typing.Annotated`, `Reported[Decision]` is a reported decision: the decision together with the identity of the instance that reported it. `ChildReport` and `Attributed` were considered.
- Vocabulary: a *step* is the payload a monitor receives, a *stage* is its type (`BeforeToolCall`, `AfterToolCall`, and the generate stages), and "a point in the loop" is only an informal gloss on stage. `Context` and `Step` are unrelated to inspect_ai's `StepEvent` and `step()`. A monitor judges a call against `step.input`, exactly what the model was sent; `context.input` is the sample's input, the assignment (*superseded: now `context.eval.sample_input`; [Eval-only context](#eval-only-context-under-contexteval)*).

## Explicit groups, decorator arguments and the call guard

Decided with the user 2026-09-30, before the first release, so nothing is kept for compatibility:

- A multi-function factory returns `MonitorGroup(before, after)` or `ProtocolGroup(a, b)`, both exported, instead of a list. They are final classes holding the functions in order with no `__call__`, so pyright rejects calling a group; construction checks that there is at least one function and that `__name__`s are distinct, and the decorator's `_register` still validates each member (stage, return annotation, kind), since it knows the kind: a `MonitorGroup` from `@protocol`, or the reverse, is a `TypeError`, and so is a plain list or tuple, with a message saying to return the group. `@monitor` is overloaded so a factory returning `Monitor` gives `Callable[P, Monitor]` and one returning `MonitorGroup` gives `Callable[P, MonitorGroup]`; `@protocol` likewise. `Monitors`, `Protocols`, `Sentinels`, the runners' parameters and the shipped protocols' parameters name the groups beside the functions. Runtime behaviour is unchanged.
- `@monitor(name=..., version=...)` and `@protocol(name=..., version=...)` beside the bare form, with typed overloads. `name` overrides the registered name as `@solver(name=)` does; `version` is an `int`, default 0 as for Inspect Scout's scanners, stored under `version` in the registry info's metadata for calibration to record. `portable=` and `fail=` are future arguments on this form. `portable=` will default to True and trigger the runtime portability check ([workstreams.md](workstreams.md), workstream 11).
- A configured function called directly while a runner is invoking a sentinel raises `RuntimeError` ("call children through run_monitors/run_protocols/run_children"). The decorator wraps each inner function in a guard with `functools.wraps`, so `__name__`, `__wrapped__`, the signature and the annotations are preserved; the runner sets a context variable to the function it is about to invoke, and the guard sets it to `None` for the body, so a direct call from inside a body fails and a call through the runner (which sets it again, in its own task) passes. The variable defaults to "no run", so a direct call outside any run, as in a unit test, works.
- The docs say "annotate `-> Observation`, or `-> Observation | None` if it can abstain" (and the same for `Decision`), since both annotations are accepted.

Implemented: the old private `Group`/`MonitorGroup`/`ProtocolGroup` with a raising `__call__` is gone; one internal base, `Group`, remains for `isinstance` checks and holds `functions`. Each member's accepted stages are recorded on its guarded function and `members()` reads them from there. `named_children` treats a group as one instance, as it does a callable.

## References, per-dimension thresholds

Decided with the user 2026-09-30, before the first release, so nothing is kept for compatibility:

- `Observation` and `Decision` gain `references: list[Reference]`, reusing `inspect_ai.scorer.Reference` (the type Scout's `Result.references` uses), so Inspect View can link cites such as `[M22]` in an explanation. Every named constructor takes `references=` as a keyword. `threshold` copies the references of the monitor its explanation names onto its decision. inspect_ai's `SentinelEvent` records them; empty for `cancelled` and `bypassed`.
- `threshold`'s `reject_at` and `terminate_at` take a float or a mapping keyed by `"<monitor>.<dimension>"`, `"<dimension>"`, a scalar monitor's instance name, or `"*"`; the most specific key wins, unlisted scores never trigger without `"*"`, and a float is `{"*": float}`, normalized at configuration, so a float threshold's decisions and explanations are unchanged. Any score reaching its threshold acts, terminate first. Configuration checks well-formed keys, that a dotted key names a configured monitor (so a dimension containing `.` must be qualified), finite values, and terminate above reject wherever both cover a score (*superseded: a threshold that can never apply is the error, and a dotted key is always qualified; [threshold escalates and terminates without reject](#threshold-escalates-and-terminates-without-reject)*). A crossing through a dimension's own key is explained `sabotage 0.72 ≥ 0.60 from audit: ...`; through `"*"`, or for a scalar monitor, as before.

- The docs say why `explanation` is log-only though `Approval.explanation` is shown to the model, and give the `modify` pattern with `dataclasses.replace(step.call, arguments=...)`.

## Root and escalate

Decided with the user 2026-09-30, before the first release, so nothing is kept for compatibility. This replaces PR 4's "every configuration wrapped" rule.

- **A lone protocol is the root, unwrapped.** `resolve_sentinel` returns a single `Protocol` as the root itself, so `Task(sentinel=threshold(suspicion(), ...))` records `threshold` at the empty path and its monitor at `suspicion`. A list or mapping still resolves to `concurrent(...)`, and monitors alone to `observe(...)` with the warning (*superseded: monitors alone are an error naming `observe_only()` and `threshold()`; [Interface cleanup](#interface-cleanup)*). A lone `ProtocolGroup` is wrapped in `concurrent`: the root returns the step's one outcome, `run_sentinel` runs one function, and combining several functions' decisions is `concurrent`'s job. The root records its own decision at the empty path, as every layer does. Configuration follows: `SentinelConfig` accepts one entry, `config_from_sentinel` records a lone instance as one entry, and `sentinel_from_config` builds one entry, or a bare registered name, as a lone instance, so a retry records the same paths. A mapping is one entry when its `name` is a string and a mapping of instance names when every value is an entry; anything else is an error naming the layer.
- **`escalate` outranks `proceed`.** The precedence is `terminate > reject > modify > escalate > proceed`, in `PRECEDENCE`, `Decisions.strongest()` and `concurrent`. A peer's `proceed` cannot override an `escalate`, a stronger decision still wins, and a layer whose strongest decision is `escalate` returns `escalate`, its explanation listing the votes when several decided. An `escalate` does not contest a `modify`. `sequential`, when it lands, returns the last escalate when every deciding link escalated, so it passes up the same way.
- *Superseded by [Unhandled escalate](#unhandled-escalate), 2026-10-10: an escalate that reaches the root terminates.* **A top-level escalate proceeds.** When the root's decision is `escalate`, nobody is left to hand it to: the inspect_ai dispatcher lets the step proceed, the escalate stays recorded as the root's decision, and the host warns once per process that `sequential([..., human()])` sends escalations to a person. `run_sentinel` returns the escalate; the host decides what an unresolved escalate means.
- **Runners stay three.** `run_children` runs anything; `run_monitors` and `run_protocols` are typed shortcuts whose parameter and return types catch misuse. Docs only.

## One stage per function

Decided 2026-10-01. Each function a `@monitor` or `@protocol` factory returns handles exactly one stage, so no function dispatches on the payload type. A monitor annotates one payload class, as before. A protocol annotates one payload class, or `Step` when it is stage-agnostic and only forwards the step (`concurrent`, `observe`). Any other union is rejected when the factory is called, with an error naming a `MonitorGroup`/`ProtocolGroup` with one function per stage, or `Step`. Since `Step` is a union, a union of every stage written out equals it and is accepted; the check compares the annotated set against all stages and rejects a proper subset with more than one member.

## sequential()

Shipped 2026-10-01, the first of the `sequential()` and `human()` series. `sequential(children)` takes what `concurrent` takes, annotates `Step`, and runs each child through `run_children` with a one-entry mapping, so each link is recorded under its own name and a link that does not watch the stage is not invoked. The first decision other than `escalate` is returned and later links do not run; an `escalate` is appended to `step.escalations` for the next link. The list starts empty for each run of the chain, so escalations do not cross layers. Monitors are recorded and fall through. All-escalate returns the last escalate, monitors only `proceed`, nothing participating `None`. An empty children list is a `ValueError` when the factory is called; YAML nests the links under `children:`. With it, decided with the user 2026-10-01, `Child` and `Children` are superseded by `Sentinel` (a monitor, protocol or group) and `Sentinels` (one sentinel, or a sequence or mapping of them), both exported; `Sentinels` is what `Task(sentinel=)`, `concurrent`, `sequential` and `run_children` take. The check that a `human()` directly under `concurrent` is an error is not stubbed: with no `human()` it would be dead code, so it lands with `human()`.

## human()

Shipped 2026-10-01, the second of the series; the inspect_ai host implementation of `Host.ask_human` (the human approval surfaces extracted from `human_approver` into a shared helper, rendering escalations above the call and the result after it) follows in PR 3 on inspect_ai's `feature/sentinel`, and until then inspect_ai's host does not satisfy `Host`. `Host.ask_human(step, choices) -> HumanAnswer` is in the ABI: one method for every stage, the host rendering the step by its type, notifying the person and marking the sample as awaiting a person. `HumanAnswer` is a frozen dataclass of `decision`, `reason` and `modified`. `human(stages, choices=None)` is registered as `inspect_sentinel/human`:

- `stages` is required, `"tool_call"` and/or `"tool_result"`; an empty list, a bare string, a repeated, unknown or unsupported stage is a `ValueError` when the factory is called, naming the valid stages (leaving it out is Python's `TypeError`, which configuration reports with the entry named). One function per stage, `tool_call` and `tool_result`; a `ProtocolGroup` when both.
- Choices use inspect's approval words: default `approve`, `reject`, `terminate` before a call and `approve`, `terminate` after it. Given choices are checked against every chosen stage, so `reject` or `modify` with `"tool_result"` is a `ValueError`; so are an empty list and `escalate`.
- It asks whenever reached: no escalation filter, no `ask=` mode, no warning.
- `approve` maps to `Decision.proceed()`, `reject` to `Decision.reject(explanation=reason, message=reason)`, `terminate` to `Decision.terminate(explanation=reason)`, `modify` to a `modify` with the answer's call, held to the call's `id` and `function` by the shape check. A host answer outside the choices offered, other than `terminate`, or a `modified` call on anything but `modify`, is a `ValueError`; a host answers `reject` if offered, otherwise `terminate`, when the person ends the prompt without a choice.
- **The answer is an ordinary decision (decided by the maintainer in review, 2026-10-01).** The `final=` parameter is gone and `human()` does not call `decide_final()`. Inside a `sequential()` the answer ends that chain; above the chain the usual vote applies, so beside other protocols in a `concurrent()` it is one vote: a peer's `reject` outranks the person's `approve`, and the person's `reject` or `terminate` is not weakened.
- **A `human()` in a `concurrent()` is allowed (decided by the maintainer in review, 2026-10-01).** This replaces the placement check that raised a `ValueError` naming `sequential()`. A `human()` there, beside other protocols or at the root a top-level list or mapping resolves to, asks about every call it is reached on, which can be intended, as with no warning when nothing earlier watches a stage. The docs recommend `sequential()` for asking only on escalation.
- `@protocol` gained an overload for a factory annotated `-> Protocol | ProtocolGroup`, which `human()` is.

## Failure policy

Decided with the maintainer 2026-10-01; replaces the design's earlier "fail loud unless nothing consumes it" with `fail="open"`. `sentinel.md`, "Failure semantics", is the policy; what landed:

- **A monitor never fails the sample itself.** `_run_member` catches an `Exception` from a monitor function and returns a `Failed(name, path, function, error)` (exported) in place of the observation, recorded through a new `Recorder.failed(context, step, failed)`; the instance's other functions and its siblings run on. A cancellation (a `BaseException`) is recorded as cancelled, not failed, and so is an exception raised in a cancelled scope (the runner checkpoints before recording a failure, since some SDKs turn cancellation into their own error); a `LimitExceededError` propagates, including one among several errors from a monitor's own task group, since a cost or time limit reached in a monitor's model call ends the sample; a monitor returning a `Decision` or calling `decide_final()` still raises, as a bug the runner detects. A protocol's exception propagates as before.
- **`Observations` carries the failures.** `failed` is a tuple of `Failed`; while it is non-empty, iteration, indexing, `len()` (so `bool()`), `in` and `max_suspicion()` raise `MonitorFailedError` (exported, a `RuntimeError`), which lists each failed path, function and error and is chained to the first error. `succeeded` is the observations without the failures and always reads. `len()` raises too, since a protocol testing `if not observations:` would otherwise abstain when its only monitor failed, which is failing open.
- **Who handles it.** `observe()`, `concurrent()` and `sequential()` read only decisions, so they log a warning per failure, once per (instance path, exception type) per process, and continue; `sequential()` counts a failed monitor link as having taken part, so a chain of only monitors still returns `proceed`. `threshold()` does not handle failures (decided), so the read raises and the sample fails. A custom protocol checks `failed` and reads `succeeded`.
- **No `fail=`.** Removed from the design as a future decorator argument; `portable=` stays.
- **Transcript.** inspect_ai's `SentinelEvent` gains `status="error"` (observations only, with `function` and no suspicion, action or references) and an `error: str | None` field holding the exception's type and message, set only on an error event, as `ModelEvent.error` carries a model call's. One event per failure, at the call. Inspect View shows it as a "Failed" row on the tool call's sentinel inset and in the event tree, with the error as its detail.

## Interface cleanup

Decided by the maintainer on 2026-10-02, before the first release, so nothing is kept for compatibility. One change in each repository, since `_integration.py` is the contract between them:

- **`Task(sentinel=)` requires a protocol.** `observe()` is renamed `observe_only()` (`inspect_sentinel/observe_only`); it records its monitors and returns None, as before. `resolve_sentinel` raises a `ValueError` for a monitor, a `MonitorGroup`, or a list or mapping of only monitors, naming each monitor and saying to wrap them in `threshold()` or `observe_only()`; the warning is gone. A list or mapping with at least one protocol still resolves to `concurrent()`, and monitors in it are recorded. inspect_ai's `resolve_sentinel_spec` now also resolves the root, so `Task(sentinel=)`, `eval(sentinel=)`, `eval_set(sentinel=)` and `--sentinel` raise when they are given, not when the task runs. A configuration recorded with `observe` no longer loads.
- **`Context` is immutable.** It was already a frozen dataclass; `Context.store` is removed, so the API no longer hands a monitor or protocol the agent's state; a convention, not isolation, since the `StoreModel` from `store_as()` carries its store. `store_as()` stays, backed by the sample store the host passes in `HostContext` (see "`Context` carries no runner state" below). Giving checks access to the sample store is a separate entry under [Deferred](#deferred), "Later".
- **`Context.input` is `Context.sample_input`, and `input_text` is `sample_input_text`.** Beside `step.input`, what the model was sent, the longer names say which input it is, and the property keeps the field's prefix so the two read as a pair.
- **`RunnerContext` is `HostContext`.** The related names were surveyed in both repositories:

| Name | Outcome | Reason |
|---|---|---|
| `RunnerContext` | `HostContext` | The host builds it and supplies what it adds (the recorder and the store); the runner only reads it. |
| inspect_ai `_context()` | `_host_context()` | It builds the `HostContext`, and `_context` also names inspect_ai's `_sentinel/_context.py`, which holds the active sentinel. |
| `Recorder` | kept | It says what it does; the host implements it beside `Host`, so a `Host` prefix adds nothing. |
| `_runner.py` | kept | It holds the runner (`run_sentinel`, `run_children`, `run_monitors`, `run_protocols`). |
| `_host.py` | added | It holds what the host implements or builds: `Host` (and, since 2026-10-14, `HostNative`, which `Host` wraps), `HumanAnswer`, `Recorder` and `HostContext`, moved out of `_context.py`, and the runner's private step context variable, which keeps `Context` and `validate_instance_name`. |
| `run_root` | renamed `run_sentinel` | Decided by the maintainer on 2026-10-03. It pairs with `resolve_sentinel`: a host resolves the sentinel once and runs it at each step. The runner's "root" stays off the host surface. |
| `_integration.py` | kept | It is the contract inspect_ai imports, and re-exports `HostContext` and `Recorder` from `_host.py`. |
| inspect_ai `_HostNative`, `_Recorder` | kept | Each is the inspect_ai implementation of the protocol it is named for. `_HostNative` was `_Host` until 2026-10-14, when the protocol was renamed `HostNative` and `Host` became the class that wraps it. |

- **`HostContext` wraps a `Context` instead of subclassing it.** Decided by the maintainer on 2026-10-03. `HostContext(host=..., recorder=..., store=...)` is what the host builds and passes to `run_sentinel(protocol, host_context, step)`; until 2026-10-14 it took the top `Context` (`context=...`), and since then the host passes its `HostNative` and `HostContext.context` builds the `Context` (an empty path, a `Host` around the host), so a host never builds a `Context` or a `Host`. The runner's per-layer state is described in the next entry. `HostContext.child()` is replaced by a private runner helper that keeps `validate_instance_name`. The `Recorder` methods take the instance's `Context` and its factory's registry name, `record(context, factory, step, reported)` and likewise for `failed`, `cancelled`, `bypassed` and `superseded`, and `Final`'s origin carries the deciding protocol's `Context`. Why: the `Context` an author is given no longer hides a subclass carrying the recorder, the runner no longer recovers the `HostContext` with `isinstance` and `cast`, and the host contract is a `Context` wrapped in a `HostContext`.

- **`Context` carries no runner state.** Decided by the maintainer on 2026-10-03, replacing the private `_run` and `_store` fields of `Context`. `HostContext(host=..., recorder=..., store=...)` (`context=...` in place of `host` until 2026-10-14): the host supplies the sample store beside the recorder. `run_sentinel` sets a private context variable for the step holding the recorder, the store, and a mapping from each layer's path to its factory's registry name; it registers the root at path `""` and the runner registers each child's path before invoking it. `run_children`, `run_monitors` and `run_protocols` look up the `path` of the context they are given, and `store_as()` reads the store from the variable. Called outside a step, for example with a context kept after its protocol returned, they raise `RuntimeError`; with a context whose `path` is not a layer of the running step, `ValueError`. anyio copies context variables into the tasks a protocol starts, so a protocol that fans out with its own task group runs children as before, and two samples' steps do not see each other's state. Entries are not removed when a layer finishes: a path is one instance per step, and a second, different factory under a path already used in the step is a `ValueError`, since its records and `store_as()` state would be indistinguishable from the first's; the path is registered before the stage filter, so this fails at every stage, and the same instance run again under its path is allowed. No lock guards the mapping, since tasks run on one event loop and each access is one dict operation. Precedent: inspect_ai keeps per-sample and per-call state in context variables (`util/_store.py` `store()`, `util/_span.py` `_current_span_id`, `log/_transcript.py`, approval's `_tool_approver`), as does inspect_scout's `ObserveContext`. Why: `Context` carries nothing hidden, so an author's context is exactly the data it shows, and a context used outside its step, or one whose path is not a layer of the running step, fails loudly instead of recording somewhere unintended. A context whose path is another running layer's is not detected; the check is by path.

- **`run_root` is `run_sentinel`.** Decided by the maintainer on 2026-10-03; see the table above. Earlier entries in this document use the new name.

"The dispatcher" in inspect_sentinel's docstrings, where it meant whatever builds the context and invokes the root, is now "the host"; the design keeps "dispatcher" for inspect_ai's in-process host.

They are pure functions over inspect_ai types, with no runtime services, so they work in a proxy host too. The guide's section is "Helpers for Rules" on the Protocols page. On 2026-10-04 the maintainer cut everything that copied built-in tools' argument names or parsed shell and Python text, as surprising and fragile; see "Finding paths in shell and code text" under Deferred.

- **`call_text(call) -> str`.** Every string argument value, in the order the arguments were given, recursing into lists and dicts (a dict's values in insertion order), joined with newlines; empty strings and non-strings are skipped. It knows nothing about particular tools. An earlier version kept a table of inspect_ai's built-in tools and their text arguments, leaving out mode arguments such as `text_editor()`'s `command`; it was dropped because it copied argument names that inspect_ai can change, and a tool of the same name from elsewhere has other arguments. If per-tool knowledge is wanted later, derive it from the tool's schema, supplied by the host, rather than a table in sentinel.
- **`tool_matches(call, *patterns, case_sensitive=True) -> bool`.** Exact names and explicit globs, matched with `fnmatch.fnmatchcase` against the whole name: `"bash"` does not match `bash_session`, `"bash*"` does, and a comma is not a separator. Decided 2026-10-04 for least surprise. An earlier version copied `ApprovalPolicy(tools=...)` (an implicit trailing `*` and comma splitting) with a test against `policy_approver`; the docstring now states the difference in one sentence. Decided by the maintainer on 2026-10-05: `case_sensitive=` as on `find_words`, default `True`, so two tools that differ only in case stay distinct, and `False` covers a bridged agent's `Bash` beside inspect_ai's `bash`. Matching uses `fnmatchcase` (with both sides casefolded when insensitive), so it is the same on every platform, where approval's `fnmatch` folds case only on Windows.
- **`find_words(text, words, *, case_sensitive=True) -> list[str]`.** A word matches where it is not preceded or followed by a word character (`(?<!\w)` and `(?!\w)`, not `\b`, so words that begin or end with punctuation, such as `-delete`, work), and a space in a word matches any run of whitespace. Returns the words as given, without duplicates, in order of first appearance, so an explanation can name them.
- **`result_text(step) -> str`.** The result's text with non-text content as `[<type>]`, or `Error (<type>): <message>`, as inspect_ai's `view_with_result` renders it for human review.
- **`path_matches` and `path_resolves`.** Moved to a separate PR on 2026-10-05 ([workstreams.md](workstreams.md), workstream 14); the code and tests are on the branch `archive/rule-helpers-path-matching`.
- **No public step builders.** `before_tool_call()` and `after_tool_call()` were public in an earlier revision for unit-testing rules; decided by the maintainer on 2026-10-05, they are test fakes in `tests/_fakes.py` instead (top-level test builders have no precedent in inspect_ai and only cover half of a test, with no `Context`). See "Testing helpers for authors" under Deferred.
- **Examples.** `no_network.py` and Getting Started use `call_text` and `find_words`; `nested.py` uses `call_text`. They check `call.function == "bash"`, which reads more plainly than a pattern there. `escalate_to_human.py`'s `triage()` uses `tool_matches`, `call_text` and `find_words` to reject `bash()` and `python()` calls that mention `/etc` and escalate ones with a delete word. The Protocols page's example uses `tool_matches`, `call_text` and `find_words` to escalate package installs.
- **Framing.** Decided with the maintainer on 2026-10-03, adjusted 2026-10-04: the docs no longer say rules catch mistakes and not an adversary, or that they are illustrative and easy to evade. They say rules are cheap and run without a model call; they match a call's text and structured arguments and cannot prove a call safe; anything that needs an understanding of shell or code goes to an LLM monitor, or is escalated, typically `sequential([rule(), llm_monitor(), human()])`.

Decided by the maintainer on 2026-10-05, before the first release, so nothing is kept for compatibility. One change in each repository.

## Portable monitors and protocols are checked when configured

The `portable=True` check ([workstreams.md](workstreams.md), workstream 11), as decided by the maintainer on 2026-10-05, narrowed on 2026-10-06 after the WASM sidecar spike (draft PR #58), and settled on 2026-10-06 after review (decisions A–C below).

- **`portable: bool = True` on `@monitor(...)` and `@protocol(...)`**, recorded under `portable` in the registry info's metadata. `portable=False` opts out.
- **When the factory is called, before it runs**, on every call. Importing a module checks nothing. The factory's file is parsed once per call and the factory found by `co_firstlineno` and name, or, when the file was edited since import, by its name if the file has exactly one definition of it. A factory without source (the plain REPL before 3.13, `exec()` of a string, a deleted file) is skipped; the 3.13+ REPL keeps source (`<python-input-N>`) and is checked, as are Jupyter notebooks, since IPython puts cell source in `linecache`. Source that cannot be parsed or no longer holds the factory raises a `PortabilityError` saying the factory could not be checked, with its file and line, the reason and `portable=False`.
- **Errors only, for what fails in a WASM guest** (decided 2026-10-06). The sandbox is the enforcement; this check is early feedback for common honest mistakes, with no false positives, and no warnings, since they cannot be silenced. Refused:
  - inspect_ai outside `inspect_ai.core`, judged by the resolved object's defining module; anything identical to a public `inspect_ai.core` attribute passes, so re-exported aliases (`inspect_ai.model.ChatMessage`) pass, and `StoreModel` passes by identity, since `store_as()` takes it.
  - Environment variables: `os.environ`, `os.environb`, `os.getenv`, `os.getenvb`, `os.putenv`, `os.unsetenv`. A bound method of `os.environ` (`get = os.environ.get`) is refused with it.
  - Processes and threads: `subprocess`, `os.system`, `os.popen`, `os.kill`, `os.killpg`, `os.startfile`, `os.exec*`, `os.fork*`, `os.spawn*`, `os.posix_spawn*`, `pty.spawn` and `pty.fork`, `multiprocessing`, what starts a thread (`threading.Thread`, `threading.Timer`, `_thread.start_new_thread`; decision C), `concurrent.futures`' thread, process and interpreter pools (named also as lazy attributes of `concurrent.futures`), `concurrent.interpreters` and `_interpreters`, `asyncio.subprocess` and `asyncio.to_thread()`, and `anyio`'s `to_thread.run_sync`, `from_thread`, `to_process`, `to_interpreter`, `run_process` and `open_process` (decision B).
  - Direct networking: `socket`, `ssl`, `socketserver`, `http.client`, `http.server`, `urllib.request`, `ftplib`, `smtplib`, `imaplib`, `poplib`, `nntplib`, `telnetlib`, `xmlrpc`, `asyncio.streams` (`open_connection`, `start_server`), `anyio`'s socket functions (`connect_tcp`, `connect_unix`, `create_tcp_listener`, `create_unix_listener`, `create_udp_socket`, `create_connected_udp_socket`, the Unix datagram sockets, `getaddrinfo`, `getnameinfo`; decision B), and the HTTP clients `httpx`, `httpcore`, `requests` and `urllib3` (added after review; they fail in the guest, and calling one instead of `context.host.generate()` is a common mistake).
  - Third-party packages with compiled code: a top-level package all of whose installed distributions list an extension module (`.so`, `.pyd`, `.dylib`, `.dll`) in their RECORD, read as text and cached per `sys.path`; `pydantic_core` is allowed, since sentinel builds it for WASI.
- **Not checked** (decided 2026-10-06): file access (granted by the host: read-only files bundled with the monitor; state belongs in `store_as()`), `time.sleep()` (unmeasured; revisit after measuring in the spike), imports inside other function bodies (a bundler concern), `exec`, `eval` and `compile`, the rest of the standard library, model SDKs, and `asyncio` and `anyio` apart from the functions above.
- **Shallow.** Names referenced in the factory's body and the functions and lambdas defined inside it, resolved one level: a name bound only by imports in the factory (decision A), the closure, the module globals, then the builtins (which always pass). Attribute chains are followed only through modules, read from the module's own `__dict__` so a lazy module is not loaded, and through names not loaded, which are judged by name; so `os.path.join` passes and `os.environ` fails. Data read from a module is judged by that module, a class or function by its `__module__`, and other data bound to a name by its type; the loaded objects behind refused names (`threading.Thread`, `anyio.run_process`, whose `__module__` anyio rewrites) are also refused by identity. A name assigned anywhere in the factory other than by an import (targets, parameters, `except` and match targets, comprehension variables, nested `def` and `class` names, `global` and `nonlocal`) is local throughout: a rare false negative, never a false positive. Each import inside the factory is judged by the module name, or by the attribute of an already-loaded module for `from M import N`, reporting every refused name. Annotations, `type` alias values and type-parameter bounds are not checked. Objects are classified by `type()`, never `isinstance()`, so a lazy proxy is not evaluated. Helpers, classes, wrappers, partials and decorators are not followed. The check never imports anything.
- **Decisions A–C** (maintainer, 2026-10-06, after review): A, a name bound only by imports inside the factory resolves to the module or attribute imported, so `import os` then `os.environ.get()` inside the factory is refused; B, `anyio` and `asyncio` are allowed apart from their thread, process and network functions, refused consistently for both; C, only what starts a thread is refused, not locks, events or `threading.local`, since a componentize-py guest has no threads (spike #58, M5 in `spikes/wasm_sidecar/README.md`: `can't start new thread`) and concurrency in it is async.
- **`PortabilityError(TypeError)`**, exported, raised from the factory call and listing every violation: file and line, the function's qualname, the reference, what it resolved to and why, followed by the fixes (`context.host.generate()`, `ask_human()`, `store_as()`, factory parameters for configuration, moving the reference, `portable=False`). A configuration file entry raises `PortabilityError`, prefixed with the entry's path, rather than a plain `TypeError`.
- **History.** The first version (2026-10-05) followed the author's own helpers and classes transitively and judged references against allowlists; four review rounds hardened it. It was replaced on 2026-10-06 by this shallow denylist; see the PR's review notes.
- **The shipped protocols pass**, as do the examples. One test factory that raises `LimitExceededError` from inspect_ai is declared `portable=False`.
- **Docs.** A Portable Monitors page (`docs/portability.qmd`): what is checked and why, what is not and why, the depth and its limit, the sandbox as the enforcement, read-only bundled files, configuration through factory parameters, and module-level code running at build time. A section on the Monitors page and the decorator docstrings.
- **Known limits** (listed in `docs/portability.qmd`): helpers, classes, decorators and partials outside the factory are not followed; a name assigned in the factory other than by an import is local throughout; dynamic access (`getattr()`, `globals()`, instance attributes, containers); a package with optional compiled speedups (PyYAML) is refused although its pure-Python fallback would work; a factory whose source cannot be parsed or located is refused as not checked; a changed `__module__`. `Host.fetch` is still to build, so a monitor that needs HTTP is not portable yet.

## `Host.generate` takes one model string

## `Host.generate` takes separate model and role strings

Decided by the maintainer on 2026-10-07, before the first release, so nothing is kept for compatibility. Supersedes [Host.generate takes one model string](#hostgenerate-takes-one-model-string); there is no `/`-based rule.

- `Host.generate(input, *, model: str | None = None, role: str | None = None, tools=None, tool_choice=None, config=None)`. `model` is always a model name, `role` always a model role.
- With neither, the role is `monitor`. A configured role (given or defaulted) wins. A given role that is not configured falls back to `model` if given, without a warning, as inspect_ai scorers' `model` and `model_role` do. A `model` without a `role` is used as given; the default `monitor` role is consulted only when `model` is None. A role that is not configured with no `model` is up to the host; inspect_ai falls back to the agent's model with the once-per-eval warning naming the role.
- A `Model` instance for `model` is a `TypeError` pointing at `Task(model_roles=...)` or `--model-role`, and an empty `model` or `role` is a `ValueError`.
- An LLM monitor's factory takes `model=None, role=None` and passes both through (`examples/llm_suspicion.py`).
- `tool_choice` is added beside `tools`, so a protocol that regenerates (`resample`) repeats exactly the request the agent made.

## Unhandled escalate

Decided with the maintainer 2026-10-10, prompted by AISI R6 ([requirements-aisi-sync-monitor.md](requirements-aisi-sync-monitor.md)). Supersedes "A top-level escalate proceeds" in [Root and escalate](#root-and-escalate) and answers `sentinel.md` open question 24. Built in sentinel #74 and #78; the action was renamed `proceed` the next day ([One word: proceed](#one-word-proceed)).

- **An escalate that reaches the root is a configuration bug, and fails closed.** Every intended outcome has an explicit protocol (`human()` for a person, `handle_escalation()` below for a fixed policy), so an `escalate` returned by the root means nobody configured what happens next. `run_sentinel` records the root's escalate and returns a `terminate` in its place, marked as an unhandled escalation and explaining each escalation and its reason, so the host only ever applies a terminate, at every stage. Sentinel owns the conversion (amended the same day) so that every host (an eval, a bridge, the proxy, replay) behaves the same; it is a decision rather than an exception because an exception is a sentinel failure, which errors the sample and is retried by `eval_retry`, re-escalating each time. `terminate` rather than `reject` because it is legal at every stage, and because a rejected agent tends to retry variations of the same action.
- **`handle_escalation(action)`**, a shipped protocol that answers the escalations handed to it: `action` is `"terminate"` or `"continue"` and is required, so every configuration states its policy. It decides only when `step.escalations` (since 2026-10-14 its `escalations` parameter) is non-empty and abstains otherwise, so it is harmless at the root alone; its explanation names each escalation it handled and why (and, with R5, the scores). Used as the last link of a `sequential`: `sequential(threshold(...), handle_escalation("terminate"))`, or after `human()` to cover a person who cannot be reached. `"continue"` is the explicit way to let an unsure escalation through, recorded in the configuration and the log. No `"reject"`: it is illegal after a call and at the generate stages, AISI do not want it, and it can be added later without breaking anyone. Named "handle" rather than "resolve", which `resolve_sentinel()` already uses for building a configuration.
- **No build-time warning in this step** (amended the same day). An unhandled escalate fails closed at runtime with a message naming the fix, which is enough for a first version. A heuristic build-time warning that assumed every custom protocol may escalate fired on Getting Started's own rule; a decorator argument to silence it, and then [Typed decisions](#typed-decisions), were considered and not adopted. Built in sentinel #74 and #78.
- **To build**: the conversion in sentinel's `run_sentinel`; inspect_ai's dispatcher drops the once-per-process warning and, defensively, treats an escalate still returned by an older inspect_sentinel the same way; `handle_escalation()` in sentinel; docs (`final-decisions.qmd`, `composition.qmd`, the getting-started examples) and the runner's docstring ("unresolved escalate" becomes "unhandled"). Approval parity is not kept: `approval=` rejects when every approver escalates; an `as_protocol(approver)` adapter follows this rule.

## Typed decisions

*Not adopted (maintainer, 2026-10-12). The implementation (sentinel #77, typed decision classes, enforced annotations, a build-time check, typed compositions with `then=`, `Verdict`, a nominal `Protocol` type) was reviewed and closed unmerged: the type machinery was judged not worth its weight. An escalate that reaches the top still terminates the sample at run time ([Unhandled escalate](#unhandled-escalate)); the decision API stays a single `Decision` class. Kept below as the record of what was considered.*

Decided with the maintainer 2026-10-10, stacked on [Unhandled escalate](#unhandled-escalate).

- **One class per action.** `Proceed` (action `continue`), `Reject`, `Terminate`, `Modify` and `Escalate` subclass `Decision`; the constructors return them (`Decision.reject(...)` is a `Reject`). The logged shape is unchanged: `action` stays the discriminator, so old logs read. A parameterised `Decision[Literal[...]]` was rejected as unreadable in annotations.
- **A function declares what it can return** with a union: `-> Reject | None` for a rule that only rejects, `-> Reject | Proceed` for one that always decides. A bare `-> Decision | None` means any action, as today. The decorator reads the return annotation as it reads the stage annotation.
- **Enforced twice.** Type checkers reject returning a class outside the union; at runtime the runner's shape check raises when a function does.
- **Unhandled escalates caught when the sentinel is built.** From the unions and the composition rules (a function whose union excludes `None` always decides, so it handles any escalation reaching it), `resolve_sentinel` raises a configuration error when an escalation provably reaches the root unhandled. A path through an unannotated protocol is not flagged; the runtime terminate covers it.
- Shipped protocols are annotated precisely; `handle_escalation` returns `Proceed` instead of `None` when there is nothing to handle, the same outcome, so that it counts as a handler.
- **Typed compositions** (added 2026-10-11, in the same PR; not adopted with the rest, 2026-10-12). A protocol's type carries what it can return, `Protocol[R]`, inferred from its annotation (`-> Decision` is `Protocol[Decision]`, which may escalate). `concurrent(children)` and `sequential(children)` return the union of their children's types; `sequential(children, then=handler)` takes a final link that always decides and never escalates and returns `Protocol[Proceed | Reject | Terminate | Modify]`. So the editor shows when an escalation can reach the top, and says nothing when no child can escalate: `handle_escalation` or `human()` is needed exactly when a child's type includes `Escalate`. Python cannot subtract a type from a union or express conditional types, so `sequential` without `then=` stays conservative and the "handled" result is a fixed non-escalating union. `run_sentinel` returns `Proceed | Reject | Terminate | Modify`. `Task(sentinel=...)` is in inspect_ai, which does not import sentinel's types; typing it strictly is a follow-up there. The build-time check and the runtime terminate remain for configurations without static types (YAML, plain lists and mappings, unannotated protocols).

## threshold escalates and terminates without reject

Decided with the maintainer on 2026-10-12 for AISI's R5 (`design/requirements-aisi-sync-monitor.md`, on the `docs/aisi-sync-monitor-requirements` branch), with no compatibility kept. First built on the typed-decisions branch (#77), which was closed; rebuilt on `main` without its type machinery.

- **Signature.** `threshold(monitors, *, escalate_at=None, reject_at=None, terminate_at=None)`: all keyword-only and optional, at least one required, else a `ValueError` naming `observe_only()`. Each takes a number or a per-dimension mapping, as `reject_at` and `terminate_at` did.
- **Thresholds are floors.** Each `*_at` means "at or above this score, at least this action"; the decision is the strongest action whose threshold any score reaches (`terminate` > `reject` > `escalate`), else `proceed`. No ordering rule: a threshold that can never apply is the configuration error, naming it and why (`escalate_at=0.9 can never apply: terminate_at=0.8 is lower`). A key is dead when a stronger action's threshold is at or below it for every score it covers; a dimension one mapping lists and another does not is not dead. Implemented by testing one score per class of keys that can cover it: each monitor's single number, each dimension a key names for it, and a dimension no key names. This replaces "terminate above reject wherever both cover a score", which also rejected live configurations such as `reject_at=0.8, terminate_at={"egress": 0.7}`.
- **A dotted key is always qualified.** `"<monitor>.<dimension>"` by the longest instance name that prefixes it, an error if none does, and never also a bare dimension, at configuration and when matching scores alike. Before, a key accepted as qualified for one monitor also matched another monitor's dimension of the same dotted name, which the dead-threshold check could not see.
- **Stages.** With `reject_at`, `threshold` runs only before tool calls, and a monitor watching another stage is a `TypeError` when it is configured. Without it, `threshold` returns one function per tool stage its monitors watch (a `ProtocolGroup` when they watch both), from a table of stage to payload type that the generate stages extend with #42. Monitors of different stages combine, each thresholded at its own stage; a score is not carried from before a call to after it, which would need state across the two steps and is not asked for. Its type is `Protocol | ProtocolGroup`, as `human()`'s is. A lone `threshold` whose monitors watch both stages is a `ProtocolGroup`, which `resolve_sentinel` wraps in `concurrent` as it does a lone two-stage `human()`, so it is recorded at `threshold` below the root rather than at the empty path.
- **What the reviewer sees.** The explanation still names the highest score that reached the decision's threshold and its monitor ([Threshold explanations](#threshold-explanations) stands). Every decision but `proceed` carries every reporting monitor's references, the named monitor's first, and `metadata["observations"]`, a list of `{"monitor", "suspicion", "explanation"}` for every monitor that reported at the step, so a `human()` after it finds every score in `step.escalations`. inspect_ai's `_human_view` renders only each escalation's name and explanation, so the scores reach the person once it also renders `metadata["observations"]` (Deferred, below).
- **Escalations are answered in a `sequential()`.** `sequential([threshold(monitors, escalate_at=0.6, terminate_at=0.9), human(stages=["tool_call"])])`: the threshold's other decisions end the chain, so the person is asked when it escalates, and also when it abstains because no monitor reported. An escalate that reaches the root unanswered ends the sample as an unhandled escalation.
- The two functions are named `tool_call` and `tool_result`, as `human()`'s and `handle_escalation()`'s are, so a lone `threshold` records `tool_call` where it recorded `decide`.

## Generate stages landing

Rulings of 2026-10-10 and 2026-10-12 ([generate-stages.md](generate-stages.md), decisions), landed with inspect_ai #5811:

- **Every agent loop's model calls** are checked (decisions 1 and 2 revised; phase fence plus deny list): any model call while the sample runs its solvers, on any model, except inside a tool's own body (an agent the tool runs opens its own span and is checked), a sentinel run, a compaction summary, `score()` from a solver, an approver, a reviewer or an MCP server's sampling request. Sample init and scoring are outside the fence.
- **`escalate` at the generate stages** (decision 16). `threshold` gains `model_input` and `model_output`; `handle_escalation` answers at all four stages and is marked as answering escalations only, so it never makes a stage watched on its own.
- **`history` keeps its meaning** (decision 15, revised): the scaffold's list at the tool stages, the caller's at the generate stages. The as-sent view (AISI R10) is its own PR, an on-demand query on `TranscriptHistory.find_last` (inspect_ai #5831); marking compaction and `score()` calls in the transcript for it and for replay (R7) is deferred to that work, designed with its viewer and TUI impact. Decision 17's recording is dropped, since R2 finds a tool call's producing `ModelEvent` in the transcript. *Built 2026-10-14 as the step field `sent`, built incrementally as each agent turn is made, with no transcript marking ([The history as sent](#the-history-as-sent-stepsent-now-stephistory)).*
- **`reject` and `modify` at the generate stages** (decisions 8–13) are deferred to part 2 and stay shape-check errors.

## `step.history` is `None` when the host cannot provide it

Decided 2026-10-13: `history` is `list[ChatMessage] | None` at every stage. It is `None` when the host cannot know the caller's list: a proxy host, which sees only the request; a replay from a log that cannot establish the list at that step, since a log records the sample's final messages and what the model was sent, not the scaffold's list at each step (R7; the reconstruction options are on #66, not built); or a step with no scaffold conversation behind it. ## human() at AfterGenerate

AISI R1, 2026-10-13: a protocol at `AfterGenerate` can escalate, and `human()` can answer it, so a monitor that judges a turn as a whole, because the combined effect of parallel calls matters, can hand that turn to a person before any of its calls runs.

- **`human(stages=["model_output"])`**, the stage name `SentinelEvent.stage` records. Its choices are `approve` (to `proceed`, the turn reaching the agent unchanged) and `terminate`; offering `reject` or `modify` there is a `ValueError` when the factory is called, since neither is legal at the generate stages until part 2. `model_input` stays unsupported.
- **inspect_ai renders the turn as one view.** `Host.ask_human` hands the existing surfaces (ACP, the approval panel, the console), which show one call per prompt, a single view: the escalations (`step.escalations` then, the `escalations` passed to `ask_human` since 2026-10-14; name and explanation, escaped as at the tool stages), how many calls the turn makes, and then each call under a `Call i of n` header, as the transcript shows it through its tool's viewer when it has one (the viewer's call content; its context is not shown). The assistant text is the prompt's message, as at the tool stages, and ACP shows it in the conversation above the card. The person approves or terminates the turn as a whole, not call by call.
- **No call can hide or pass for another** (review of inspect_ai #5846). Viewers interpolate the agent's arguments into markdown unescaped, so in one combined view an argument could close its code fence and open an HTML comment that swallows every later call. Each call's content is therefore shown only inside a code block fenced longer than any backtick run in it, a viewer's single code block keeping its language and any other content shown as source; the headers, separators and count outside the code blocks are inspect_ai's own. The prompt's title, which ACP shows as the card's title, carries the count too: `Assistant turn: 2 tool calls (bash ×2)`.
- **Nor through characters that act rather than show** (second review of inspect_ai #5846). A terminal escape sequence in one call's arguments could move the cursor and overwrite another call's lines on the console, the panel and the ACP TUI; bidi overrides, zero-width and tag characters could reorder or hide text. inspect_ai's `display_safe()` (`_util/format.py`) shows each visibly, as OpenBSD's `vis(3)` does, as a marker of its code point, e.g. `‹U+001B›` and `‹U+E0041›`: C0 controls other than newline and tab, DEL, C1 controls, zero-width characters and the word joiner, bidi embeddings, overrides and isolates, the zero-width no-break space, and the tag block. The marker is not a backslash escape (third review of #5846, decided by the maintainer), so backslashes are never changed and code reads exactly as written except at a marker: doubling backslashes once anything was escaped turned a shell command that runs `rm` into one that reads as a quoted string, and a typed `\x1b` in one string could pass for a real escape character in another. A literal marker opener in the text is itself marked (`‹U+2039›`), so a marker cannot be typed. The turn view applies it to each call's content, the headers and viewer titles, the escalations, the assistant text and the title, and adds a notice line, `This turn contains hidden or control characters, shown as ‹U+…›.`, when it marked anything.
- **Beside the prompt too** (third review of #5846). The ACP TUI shows the turn's streamed text and reasoning above the approval card, and `--display conversation` (selected by `--trace`) prints the turn's text, reasoning and tool calls just before the prompt; written raw, a cursor move or a scroll region there could rewrite or hide the prompt's calls. Both now go through `display_safe()`: the TUI's message text and reasoning segments, and the conversation display's assistant message.
- **Limits.** What a tool's viewer makes of a call's own arguments inside its code block is the viewer's, so a call can still garble its own content there. Earlier tool output in the ACP TUI's conversation and in `--display conversation` is still shown as is, and can carry control characters onto the same screen as the prompt. The shared viewers (`code_viewer`, the default viewer) and the tool-stage surfaces do not use `display_safe()` yet, so at the tool stages a single call can still hide its own trailing content through a fence breakout or control characters, and the assistant text in the panel and console is shown as is; applying it there, and to tool output, is a follow-up in inspect_ai.
- **ACP.** The turn gets one permission card of its own, under an id of its own, not linked to the calls' cards. No tool event completes it, so inspect_ai finishes it when the prompt ends, `completed` on an answer and `failed` on a dismissal or cancellation, sending its title and content so a client that did not get the request still sees a complete card. Ending the prompt without a choice terminates, since `reject` is not offered.
- `examples/escalate_turn_to_human.py` escalates a turn whose `bash()` or `python()` calls delete files.

## Escalations are a protocol parameter

Decided by the maintainer 2026-10-14. A breaking change, with no compatibility kept, since the package has almost no users.

- **Escalations leave the step.** `BeforeGenerate`, `AfterGenerate`, `BeforeToolCall` and `AfterToolCall` hold only facts about the conversation that the host provides and that read the same live and in replay (`input`, `history`, `output`, `call`, `result`, …). What earlier links of a `sequential` decided at this step is chain state, which `sequential` used to thread by rewriting the step with `replace(step, escalations=...)`.
- **A protocol takes them as a third parameter**: `async def decide(context, step, escalations)`, `escalations: Escalations`, the exported alias of `tuple[Reported[Decision], ...]`, positional like the other two. A monitor keeps `(context, step)`. The decorators check the count, so a two-parameter protocol or a three-parameter monitor is a `TypeError` when the factory is called, naming the expected parameters; there is no two-parameter form for protocols.
- **Why: monitors must not see escalations.** A monitor after a `threshold` in a `sequential` read its escalation, including `metadata["observations"]` with every other monitor's score and explanation, which broke monitor independence ([sentinel.md](sentinel.md), "The surfaces"; AISI's R4 narrowing kept monitor observations out). The signature enforces it, not runtime stripping.
- **The runner.** `run_children` and `run_protocols` take a keyword-only `escalations=()` and hand it to the protocols they run, never to a monitor; `run_monitors` takes none. `sequential` passes each link the escalations of the links before it; `concurrent`, `observe_only`, `threshold` and the root pass none, so escalations still do not cross layers. `unhandled()` already took the escalations that reached the root explicitly and is unchanged.
- **`Host.ask_human(step, escalations, choices)`.** The host renders the escalations it is passed, who escalated and why, in place of reading `step.escalations`; `human()` passes on the ones it was handed. inspect_ai's host changes with it.
- **`Escalations` is exported** (decided the same day): the alias of `tuple[Reported[Decision], ...]`, used in the `Protocol` type, the shipped protocols, `Host.ask_human`, the runner, the docs and examples, so a rule that ignores the parameter annotates it in one word.
- **`human()` keeps the person's reason on an approve** (decided the same day): `approve` maps to `Decision.proceed(reason)` rather than a bare `proceed`, so the approval's reason is in the log and in what AISI R4's earlier decisions will show. A reject's and a terminate's reason were already kept.
- **`Host.score` has no `{{ escalations }}` variable** (merging #87, 2026-10-14). #87's template rendered `step.escalations` as an `[BEGIN ESCALATIONS]` block. `score` is how a monitor asks a model, and a monitor never sees escalations, so the variable, its default-template block and the helper are gone; a template that names it raises as an unknown variable before the model is asked. `HostNative.ask_human` and `Host.ask_human`'s delegation take `escalations`.
- **Rejected:** a `ProtocolContext` with `.escalations` (it breaks `Context`'s constant-for-a-sample invariant), a context variable or accessor (hidden state), and an `oversight` sub-object on the step (still the step).

## Human decisions

AISI R4, decided by the maintainer on 2026-10-14: a monitor can see the decisions a person made through `human()` at earlier steps of its conversation, so a later prompt can mark calls a person already approved, and a protocol can avoid asking again.

- **A plain field on every payload**, `human_decisions: tuple[HumanDecision, ...] | None`, beside `history` as a fact about the conversation (keyword-only, default `None`, so it can sit ahead of fields without defaults). Not a `Context` member, which is constant for the sample, and not a `Host` read, which every host would have to implement and which would have to enforce "earlier" itself. `None` means the host cannot tell.
- **`human()` decisions only**, as recorded with status `reported` and not superseded later: a `terminate` that a sibling's `decide_final()` outran is recorded and then superseded, and the host drops it before the step settles (review of #96, findings R4-1 and R2-1). The match is by path and action, not by object: a decision with the person's action superseded at the person's path or at a layer above it, since a composition such as `concurrent()` passes the person's decision up as a copy; a cancelled `human()` never recorded a decision. Neither took effect, and `handle_escalation()` is a fixed policy rather than a judgment. Other protocols' decisions are left out because a `threshold()` decision carries every monitor's score (`metadata["observations"]`, and the top score in its explanation), and passing those on would break monitor independence (sentinel.md, "The surfaces"); a test holds that no score reaches a kept decision. Every `human()` answer is kept, not only approvals.
- **`HumanDecision(stage, step_id, call_ids, decided: Reported[Decision])`**: the step coordinates as `SentinelEvent` records them, the tool calls it covered (the call at a tool stage, every call in the turn at `model_output`), and the `human()` instance with its decision, a reject's or terminate's reason as the `explanation` (`human()` records none on an approve). It is what the person decided, not the step's outcome.
- **"Earlier" is by step, and a step is its stage and its step id**, so a `tool_call` decision about call X is visible at X's `tool_result`, and a `model_output` decision about a turn at each of its calls' tool stages. A decision made at the step itself never is, including to monitors beside the `human()`, and nor is one from a parallel step still running: the host publishes a step's decisions to the conversation's list only once that step has settled, and snapshots the list when it builds a step.
- **What is kept is sentinel's rule**: `kept_human_decision(factory, step, step_id, reported)` in `_integration`, which the host calls from `Recorder.record`, and `supersedes(path, reported, kept)`, which it calls from `Recorder.superseded`. The kept decision is a detached copy: the person's own `Decision` carries the runner's provenance for the step, which reaches every decision there, `threshold()`'s scores included (finding R2-3). inspect_ai keeps the results per transcript and conversation, so a step costs a tuple copy and nothing depends on transcript events still being in memory.
- **Renamed, reframed, narrowed (maintainer, 2026-10-14, after review pass 2).** `earlier_decisions` / `EarlierDecision` became `human_decisions` / `HumanDecision`, and the host helper `kept_human_decision()`; the semantics above stay. The use is a monitor rendering the conversation and annotating each past call a person reviewed, so it does not flag already-reviewed history again. It is not a standing permission: mark the exact call, never lower suspicion of a new call that resembles an approved one (state changes: an `rm -rf build/` approved in one directory deletes something else after a `cd`; gaming: get a benign call approved, then issue a similar harmful one). A record is what the person decided, not what happened, so a monitor marks only calls that ran; the person's reason is untrusted text, quoted when rendered.
- **`human_decision_for(step, call_id)`**, public: the latest `HumanDecision` covering a call (a turn approval covers each of its calls; the call's own decisions come later and are more specific), or None, also when `human_decisions` is None. Keyed on tool call ids only (maintainer, 2026-10-15): the provider assigns them and they survive scaffolds that copy or rebuild messages, while `ChatMessage.id` does not (bridged agents, rebuilt lists), so there is no lookup by message. A review of a turn with no tool calls stays in `human_decisions` (a complete record, its `step_id` tying it to its `SentinelEvent`) but has no stable key to annotate by. `docs/monitors.qmd`, "Annotating Calls a Person Reviewed", is the worked example.
- **Dismissals: by explanation, not a flag.** A prompt the person cancelled or closed without choosing is recorded as the surface's fail-closed answer, a `reject` or `terminate`, with an explanation that says so (ACP: "ACP client cancelled the permission request."; inspect_ai's own fallback: "The person closed the prompt without choosing; failing closed."): render the explanation, and do not present it as the person's judgment. A typed flag was built and dropped (maintainer, 2026-10-14, after review pass 3): `HumanAnswer.dismissed` and `HumanDecision.dismissed`, set by the host and recorded by `human()` as `metadata["dismissed"]`. Catching an ACP cancellation, which answers `reject` and so looks like a choice, needed a stringly-typed key in the public `Approval.metadata`, changed ordinary `approval=` users' logs, had the sentinel dispatcher reach into `approval/_human`, and added public fields, for a signal the explanation already carries. A possible later addition if a monitor ever needs a typed signal.
- **Not covered: other review protocols.** A team's own review protocol (AISI R9) does not appear in `human_decisions`; see Deferred, Later, "Protocols that share their decisions".
- **Intended consumer: R8's shared renderer**, item 8.5: an option that annotates matching calls in a fixed, unforgeable format (Deferred, "Shared message rendering").
- **Replay** reads the same records from the log's `SentinelEvent`s ([sentinel-development.md](sentinel-development.md), "Human decisions in replay"); built with workstream 10 (R7). A proxy host fills the field from its own record of `ask_human` answers, or leaves it `None`.

## The history as sent (`step.sent`, now `step.history`)

*Renamed for 0.2.0 ([Renaming the histories](#renaming-the-histories)): this section's `sent` is `history`, and its `history`, the scaffold's list, is `agent_messages`.*

AISI R10, decided by the maintainer on 2026-10-14 (in four rounds: the full list, not only the opening prompts; scoping live only; on the step, not on `Host`; no opt-in). `history` keeps its meaning; what the model was sent over an agent instance's run is a third message list on the step ([sentinel.md](sentinel.md), "The history as sent").

- **A step field, always filled**: `sent: list[ChatMessage] | None` on all four payloads, beside `input` and `history`, keyword-only with a default of `None`. It is a fact about the conversation, like the other two. It was briefly `Host.sent(step)`, an on-demand query, and then an opt-in field like the designed `target` opt-in (`@monitor(sent=True)`); both were dropped. Every monitor and protocol gets it while a sentinel runs, and no registry records a request. `None` only when the host cannot produce it: a proxy, or a replay from a log. If its cost ever matters, a flag or a sentinel-level switch can be added without breaking anyone.
- **Full list.** AISI said the opening prompts would do for now and the full list would likely be wanted later; the full list costs about the same, so it was built directly.
- **Duplicates and edits**: each version is kept in the order sent. A message is already sent when a version with the same id and equal content was sent, or when the previous call had the same role and content at the same index, which covers messages rebuilt with a fresh id each call (the `GenerateConfig` system message); such an id is remembered as the message it repeats, so the copy is not added again when it comes back later (review of inspect_ai #5871, fix round 1). Only each message's latest rebuilt id is kept, so the index is one entry per message sent, not one per message per request, which a scaffold rebuilding every message on every call (a bridge) made quadratic (fix round 2). An id reused as the rebuilt id of a second message keeps both (fix round 3). Accepted edge: a scaffold that keeps two rebuilt ids for one message and alternates between them can see it repeated. inspect_ai checks `_sent.py` against a from-scratch reference fold of these rules on seeded random request sequences (reused and fresh ids, rebuilds, omissions and returns, edits, id collisions, compactions, the caller's list changed in place), after every request; it catches each earlier defect (fix round 3). Content excludes the id, `source` and `metadata`. Under `reasoning_history="last"` an assistant turn appears once with its reasoning and once without.
- **Built incrementally, holding shared references.** inspect_ai folds each agent turn's input in when `Model._record_model_interaction` records the call (before the request is sent, so a request in flight counts, and each retry's identical input adds nothing), by the same agent-turn test as the generate stages. Per conversation, weak-keyed by the transcript: the messages sent, the versions sent under each id, each message's latest rebuilt id mapped to the message first sent, and what the previous call sent at each position, in a list of its own, since `_prepare_input()` can hand back the caller's list, which the caller may then extend (fix round 1). It holds the `ChatMessage` objects, almost all shared with the scaffold's list and the transcript's events, for the conversation's life; each step gets a copy of the list. No per-step rebuild and no read-back from the transcript, so bounded transcripts are unaffected. Nothing is built while no sentinel is active, and nothing is written to the log. Measured 2026-10-14 on mockllm, 300 agent turns with a 4 KB tool output each, every stage watched (tracemalloc, index on against off): `react` with `CompactionSummary` (20 compactions) +0.23 MB of 121 MB, no message held only by the index, 64 KB of lists and dicts; a scaffold sending a fresh but unchanged system message each call +0.25 MB, one message held only by the index, 72 KB of containers; one sending a changed system message each call +0.29 MB, those 300 messages (33 KB) held only by the index, 113 KB of containers; one rebuilding every message with a fresh id on every call, as a bridge does, +0.31 MB with 1,196 remembered ids at 300 turns and +0.43 MB with 1,996 at 500, where keeping every rebuilt id had cost +12 MB (90,000 ids) and +30 MB (250,000) (fix round 2). In that last case the messages as first sent, about the conversation's size, are held by the index and the transcript's events while the scaffold holds its fresh copies, so with bounded transcript eviction they are held by the index alone. The cost grows with what the scaffold itself no longer holds: a scaffold that discards its own pre-compaction turns leaves them held by `sent`, which is the point of it.
- **Known limits**: a model call a scaffold makes inside its agent loop is an agent turn and is in the list, for example ControlArena's own monitor and compaction summariser. Decided 2026-10-14: no rule that tries to tell such calls apart (an "adopted output" rule was considered); a scaffold keeps one out by running it through `inspect_ai.agent.run()`, which gives it its own agent span and so its own conversation. Sub-agents inside one bridged CLI share the bridge's conversation. A message the scaffold changes in place after sending it shows its current content.
- **R4 overlap**: R4's earlier protocol decisions (sentinel #96, inspect_ai #5868) are also per conversation. `sent` reads nothing from the transcript, so the two share no helper; both add a keyword-only field to the payloads.

## Renaming the histories

Decided by the maintainer on 2026-10-15, for the 0.2.0 breaking release, bundled with the escalations change (#97) so users absorb one break; no compatibility shims (sentinel 0.x):

- `step.sent` becomes **`step.history`**: everything this agent instance has sent to the model, in the order sent. It is the always-meaningful, safety-relevant view (what the model actually saw), and the portable one: inspect_ai records it, and a proxy can rebuild it from traffic. So it gets the natural name.
- The old `step.history`, the running agent loop's own message list (`react()`'s `AgentState.messages`, a sub-agent's own list, or the list a caller passed to `generate`; `None` when the host cannot know it, as under a proxy), becomes **`step.agent_messages`**, Inspect's own term for it. It is Inspect-only.
- Names rejected for the old field: `task_messages` (reads as `TaskState.messages`, which is wrong for sub-agents and handoffs), `solver_history` (agents are not solvers), `scaffold_history` (accurate, but `agent_messages` uses Inspect's term).
- What followed the field: the excerpt helpers name the scaffold's list `agent_messages` too: `Excerpt.agent_messages`, `keep_agent_messages()` (was `keep_history()`), and the exclusion `"agent_messages"` (was `"history"`). The keys `new_since_last_report()` records in a monitor's store change with it, so a monitor's marks from before the rename are not found, and its first step after an upgrade shows the conversations whole. `step_as_str()`'s rendered text is unchanged: the block is still `[BEGIN HISTORY]` and the absent case still says "The agent's conversation history is not available.", since renaming text a monitor's model reads changes prompts, not just names (open: whether to rename it, and whether `step_as_str()` should render the as-sent `history`).
- The positional order of the payloads is unchanged: `agent_messages` takes the old field's place, and `history` stays keyword-only with a default of `None`.
- Earlier records in this file and in [generate-stages.md](generate-stages.md) keep the names they were written with.

- **A second set of rule helpers**, decided with the maintainer on 2026-10-03: `urls_in(text)`, `host_matches(url, patterns)` and `secrets_in(text)`. Left out of the first set to keep it small; nothing blocks it.
- **Finding paths in shell and code text.** Cut from sentinel PR #49 on 2026-10-04: `paths_in(call)` (paths in a file tool's arguments and in `bash()`, `bash_session()`, `python()` and `code_execution()` text), `unresolved_paths(call, *, cwd=None, home=None)` (references a rule cannot resolve, for a deny-list to escalate) and the private shell lexer `_shell.py`. The code and its tests are kept on the branch `archive/rule-helpers-shell-paths` (d9c2c90, "fix: read arithmetic shifts as arithmetic, and cover the guard branches"). What the work learned:
  - Regex and hand-lexer parsing failed open in case after case found by review: `$@`/`$*`; backslash-newline continuation; `~+`/`~-`; extglob; pathlib `/` and Python implicit string concatenation; directory changes by `git -C`, `tar -C` and `cwd=`; quoting inside a word (`'/e'tc/passwd`); `\cd` and `c''d`; and `<<` inside `$((…))` lexed as a heredoc.
  - False escalations of the deny-list idiom (reject a protected path, escalate anything unresolved) were reduced from 25 to 11 of a 286-command corpus (8.7% to 3.8%) and from 26 to 19 of a reviewer's 187 (14% to 10%), by reading `$HOME`/`$PWD`, following simple `cd`, and treating quoted arguments of a list of literal-reading programs as literal. Each relaxation needed its own guards.
  - A general rule that single-quoted text is literal is unsound: `bash -c`, `eval`, `find -path`, `sed`'s `e` command and `awk`'s `system()` read the text again.
  - A revisit should start from a real parser, such as `bashlex` or tree-sitter-bash, checked for portability to a proxy host, not regexes. Until then, finding what a command touches is an LLM monitor's job.
- **Shell evasion indicators** — a helper naming suspicious shell constructs (command substitution, decode-then-execute, inline interpreters, obfuscated command names) for rules to escalate on. Requested 2026-10-03; not built by an agent (blocked by a safety classifier while drafting test fixtures); to be written by a maintainer.

### Then: design decisions

- **Revisit `decide_final()`: is it the right design at all?** Raised in review: any protocol at any depth, including third-party code inside `observe_only()` or `threshold()`, can call it and bypass every layer above, while the design sells child decisions as advisory to the parent. Options to weigh: a declared capability (`@protocol(final=True)`, recorded in the registry and the log, with an undeclared call raising); parent control (`allow_final=` on a layer, or finalization only at the root); containment (`shadow()`); or a different mechanism. `sentinel.md` open question 23. `human()` no longer uses it, which weakens the case for keeping it. Simplifying the runner's origin-threading and its superseded and bypassed bookkeeping is part of the outcome.
- **Containing `decide_final()`**: a parent configured to hold back a child's final decision, e.g. `shadow(child)` for trialling a protocol on live traffic, recorded as its own event kind. Waits for a user who needs shadow mode.
- **`Decision.modify(step, arguments=...)`**, a constructor that keeps the call's id and function by construction. A tool-call form can land before the generate-stage `modify`, with the signature designed for both; [generate-stages.md](generate-stages.md) proposes one constructor overloaded on the step type. Until then, authors write `Decision(action="modify", modified=replace(step.call, arguments={...}))`, and the shape check rejects a changed id or function.

### Then: tool-stage completeness

- **An opt-in tool filter.** Discussed with the user 2026-10-01, replacing the earlier idea of a default filter. There is no default filter: `submit()` is monitored like any tool, because the final answer is where sabotage or sandbagging shows up and silently dropping coverage is a safety failure, and since inspect_ai 34adba814 the sentinel checks `handoff()` calls before and after they run, as approval does for every tool, and inspect_ai's review reviews them too (`feature/sentinel`). A monitor not written for a tool abstains in its body (`if step.call.function == "submit": return None`). Rules: it applies only to tool-stage functions; setting it on an instance with no tool-stage function is a configuration error raised when the factory is called; in a mixed group it filters only the tool-stage members. ### Then: hosts (in-process, bridge, sidecar)

From comparing inspect_ai's in-process dispatch with the sidecar handler in #102, 2026-10-14 ([comment](https://github.com/meridianlabs-ai/inspect_sentinel/pull/102#issuecomment-6181966737)). The sidecar entries wait on #102 landing.

- **Rejecting one call, not the whole turn, under the bridge and the sidecar.** In-process, a `reject` at `BeforeToolCall` fails that one call, its siblings run, and nothing counts rejections. The bridge and the sidecar can't hold back part of a reply the scaffold has been handed, so they reject the whole turn (siblings marked "not run") and end the run after three rejected turns in a row. Idea: remove only the rejected call from the reply the scaffold receives, so it runs the rest, then put the call and its rejection back into the next request before the model sees it. The model sees what it sees in-process; the scaffold's own conversation never holds the rejected call, as the bridge already accepts. Keep today's whole-turn retry when every call in the turn is rejected, since a reply with no calls reads to most scaffolds as a finished turn. To settle: whether removing and restoring a `tool_use` block passes Anthropic's checks on signed thinking; Responses with `previous_response_id`, where the provider already holds the call and the next request must carry an output for it; rewriting each wire format, streamed or not; and what the cap counts (likely turns in a row whose every call was rejected). Prototype in the bridge first, on `ModelOutput` and `ChatMessage` rather than wire bytes. Then decide whether the native loop gets the same cap.
- **Tool stages for bridged agents** (inspect_ai #5759). Today bridged agents get the generate stages only. The sidecar's reply path is the model: `BeforeToolCall` for each call in the model's output, at the point in `bridge_generate` where `apply_bridge_tool_approval` runs, and `AfterToolCall` for the tool results the next request carries, de-duplicated. Goes with the per-call rejection above.
- **The sidecar skips stages nothing watches.** `Handler` builds every step and calls `run_sentinel` at every stage; in-process skips a stage that `watched_stages(root)` lacks before it builds the step. Replies are still read, since what is kept from them feeds the tool stages.
- **The sidecar's `ask_human` doesn't approve on its own.** At the tool stages it answers `approve` and logs a warning, so a `human()` gate lets every call through. Answer the most cautious choice offered, or raise as at the generate stages, or make approving an explicit option.
- **A retry answer for the proxy.** The sidecar refuses a rejected turn with `--reject-status` and relies on the client to send the request again; many clients take a 400 as final. A result carrying the body to send again would let the proxy hook ask the model again before it answers the client, as the bridge does.
- **`modify` in the sidecar**, by rewriting the tool call in the reply through `ReplaceReplyResult`; it raises `NotImplementedError` today.
- **What a proxy does when the sentinel fails or runs out of time.** Say in `proxy_endpoint.schema.json` that `SENTINEL_FAILED` and `TIME_LIMIT` refuse the call by default, as in-process fails the sample.
- **The proxy is told which stages are watched**, by a method or on `/health`, so a proxy whose sentinel watches only `BeforeGenerate` need not hold streamed replies back. A change to the endpoint's schema.
- **The proxy marks calls that aren't the agent's turns** (a client's titles, compaction summaries), with a field in `judge_request` or a header, so the sidecar can skip them as `is_agent_generate()` does in-process. Until then they are judged as agent turns.
- **The sidecar's records carry the step id and conversation**, as `SentinelEvent` does, so the two can be shown in one viewer or converted to a log.
- **Say that a monitor's model calls must not go through the proxy.** The sidecar calls models directly, but an environment that points a provider's base URL at the proxy would have the monitor's own calls judged.
- **A time limit for the sentinel in-process.** Sample limits are suspended while the sentinel runs, and nothing bounds it, so a hung monitor model call hangs the sample. The sidecar's `--time-limit` is the precedent.
- **The runner refuses actions a stage can't carry out yet.** Until "Generate stages, part 2" (under Later) lands, a `reject` or `modify` at `BeforeGenerate` or `AfterGenerate` is dropped by both hosts without a word; refusing it in `run_sentinel` makes every host agree, and part 2 lifts the refusal.
- **`AfterToolCall.output` is `None` where the host can't see it.** The sidecar passes `""`, which a monitor reads as an empty result. `ToolResult | None`, as `truncated` already has `None` for "this host can't tell". Replay needs it too, since a log never holds the untruncated output: R7 PR 2 builds it ([sentinel-development.md](sentinel-development.md), "Building replay: the PR series").
