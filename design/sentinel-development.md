# Developing sentinels

How the monitors in a sentinel get built, measured and calibrated before they are trusted to act. The mechanism is Inspect Scout: a monitor becomes a scanner over the steps of a transcript, and Scout's validation sets, metrics and viewer become the monitor's feedback loop.

## Goal

A monitor is a classifier, and nobody should trust a classifier they have not measured. Concretely, the things a monitor author needs to do before configuring one to act:

- run it over a corpus of transcripts and see what it flags
- label a set of steps or trajectories as should-flag / should-not-flag, and get precision, recall and F1 against them
- change the prompt and see whether the numbers moved
- collect the score distribution over known-benign runs, and turn a budget ("audit the top 1%") into a threshold
- check how the monitor actually behaved in an eval it was attached to, without re-running it

Scout already does the first four for *scanners* — validation sets with splits, balanced accuracy, precision, recall and F1, Scout View for labelling, a results dataframe, and scanner versioning to compare prompts — over Inspect logs and over transcripts from other sources. The design problem is therefore small: make a monitor look enough like a scanner that all of that applies, without either package growing a second copy of anything. *Revised 2026-10-20: for R7, a scan gives one result per step in the transcript's resultset, and Scout's validation and labelling at the step grain wait on per-item rows, deferred ([The scan unit and the validation unit](#the-scan-unit-and-the-validation-unit)).*

## The shape

**A monitor is a scanner over steps.** Scout scans a `Transcript` and returns a `Result`; a monitor takes `(Context, Step)` and returns a `Report`. Everything a step needs is already in a transcript, so a transcript can be re-walked into the steps the monitor would have seen and the monitor run against each in order.

``` python
from inspect_scout import scan, scan_results_df, transcripts_from
from inspect_sentinel.scout import as_scanner

status = scan(
    scanners={"suspicion": as_scanner(suspicion_monitor("openai/gpt-4o-mini"))},
    transcripts=transcripts_from("./logs"),
)
steps = scan_results_df(status.location, scanner="suspicion", rows="results")  # one row per step
```

`as_scanner()` accepts a protocol too, so `as_scanner(threshold(...))` back-tests a whole configuration the same way, and the recorded per-layer reports go along with it. It takes the sentinel as `Task(sentinel=)` does, and records it in the configuration form the eval log records (`SentinelConfig`, inspect_ai `_sentinel/_config.py`), so Scout can write it in the scan spec (`ScannerSpec.params`), resume the scan, and rebuild the scanner in a worker process. (`as_scanner()` was first placed in Scout as `inspect_scout.sentinel`; it moves to sentinel, decided 2026-10-19, decision R7-D3 below.)

Three things fall out of this that the rest of the document works through:

- **Offline replay is a third deployment**, beside the eval and the proxy, and it has a fidelity table like the other two. Reconstruction from a messages-only transcript is *the same projection* the proxy and the bridged agent already use, so one function serves all three.
- **The recorded reports finally have a consumer.** `sentinel.md` records every report, including the ones a protocol ignored, on the argument that they are the benign distribution calibration needs. Scout is where that distribution gets read.
- **Threshold calibration is a scan plus a percentile.** `sentinel.md`'s open question 5 — where a protocol's thresholds come from — has an answer that needs no new machinery.

## Packages

`inspect_sentinel` is its own distribution, to depend only on `inspect_core` once that is extracted (see `inspect-core.md`; today it depends on `inspect_ai`). The chain is then:

```
inspect_core  ←  inspect_sentinel  ←  inspect_ai  ←  inspect_scout
```

Today `inspect_sentinel` depends on `inspect_ai` (for the wire and event types), and imports Scout lazily where it uses it, as `step_as_str` and `Host.score` already do (`_preprocess.py`, `_score.py`; Scout is a dev dependency). `inspect_ai` imports sentinel lazily and does not declare it; it declares it only once inspect_core is extracted ([workstreams.md](workstreams.md), workstream 1), which is postponed. Until then the Scout adapter in sentinel adds no cycle: Scout is an optional extra, `inspect_sentinel[scout]`, and sentinel → Scout → `inspect_ai` is a line (R7-D3, decided 2026-10-19). Once `inspect_ai` declares sentinel, that extra would close a cycle (sentinel → Scout → `inspect_ai` → sentinel), and the adapter moves to `inspect_scout.sentinel`. What goes where (revised 2026-10-19 for R7):

| Where | What | Why there |
|------------------------|------------------------|------------------------|
| `inspect_sentinel` | `steps_from_messages()`; the `ReplayStep` record; `Context` from a transcript's info; the replay `Host`; the replay runner (units, store, recorder); `as_scanner()`, the read-mode scanner, `steps_in()` and `fidelity_probe()` in `inspect_sentinel.scout`, behind the `scout` extra; `replay_monitor()`; `calibrate()` | the replay host and runner are built on the runner's integration contract (`_integration`), so they change in step with it; the development loop's verbs live here ([workstreams.md](workstreams.md), workstream 10) |
| `inspect_ai` | the step builder, shared by the live dispatcher and a log driver, `steps_from_events()`: every step field, the as-sent fold, step ids and earlier `human()` decisions, from live facts or from a log's events | the live builder is here, and one function per field is what keeps live and replay from drifting ([One builder for live and replay](#one-builder-for-live-and-replay)); the event types are not in core today |
| `inspect_scout` | condensed model events for a scanner (PR 4); later, per-message and per-event results from a transcript scanner, and viewer work (deferred 2026-10-20) | does the scanning; owns validation and the view; knows nothing of sentinel |

The middle row is pressure on `inspect-core.md`'s first open question. If `ModelEvent` and `ToolEvent` move down, the events-based reconstruction moves down with them and `inspect_sentinel` can replay an eval log at full fidelity on its own. Nothing in this document requires that; it only gets tidier.

## Replay over logs (R7)

AISI's R7 asks to run the exact same `@monitor` over stored eval logs, each replayed step carrying what the monitor saw live, including after a compaction and in logs from before Sentinel; to match each step's report to the same step live; to score a chosen subset of steps; to parallelise and use provider prompt caching; and to keep live and replay identical as Sentinel changes. The replay halves of R2 (`input`), R3 (`tools`, `truncated`), R4 (`human_decisions`) and R10 (`history`) are part of it. Parked for design on 2026-10-14 with one direction agreed: build on Scout, which already runs scanners concurrently across transcripts, manages model connections, records results, resumes and validates, rather than a standalone `replay()` engine.

The plan, proposed 2026-10-19:

1. **The log records where each model call was made** (`ModelEvent.origin`, one of a small closed set of kinds such as `agent`, `tool`, `compaction` and `environment`), and one shared rule derives agent turns from it; a call's conversation comes from the span tree ([What the log records](#what-the-log-records)). This is what replay needs that a log lacks today, and with it live stops depending on message ids the log cannot keep (R7-D8, decided 2026-10-20). Nothing else is added: where the log does not say, replay infers, and this document states where that differs from live ([How exact replay is](#how-exact-replay-is)). It is inspect_ai PR 1, which also makes `timeline_build` use it, so the viewer, Scout and replay see the same conversations.
2. **One step builder in inspect_ai, two drivers.** The live dispatcher and the log driver gather facts differently and hand them to the same functions; a test runs an eval with a probe that records every step it sees, and asserts that the steps rebuilt from the written log are equal, field by field ([One builder for live and replay](#one-builder-for-live-and-replay)).
3. **Scout scans transcripts; each step is a result in the transcript's resultset.** `as_scanner()` is a transcript scanner returning one `Result` per step, citing the step's message or event and carrying the step id and stage in its metadata. Scout records the list as it records any resultset, and its dataframe gives one row per step, so Scout's row model does not change. Validation and labelling in Scout at the step grain are deferred (revised 2026-10-20; [The scan unit and the validation unit](#the-scan-unit-and-the-validation-unit)).
4. **Within a transcript, units run concurrently and steps run in order within a unit.** A unit is a conversation's run of steps between two of its compactions by default, optionally split further, or the whole sample for a stateful monitor ([Cost and parallelism](#cost-and-parallelism)).
5. **Every field has a stated fidelity** for new logs, older logs and bridged agents ([Fidelity in replay](#fidelity-in-replay)). Transcripts that do not record origins, older Inspect logs and every other source Scout imports, get their conversations and turns from the transcript's timeline, which gains a continuity rule; logs from before Sentinel get `human_decisions` from `ApprovalEvent`s ([Transcripts without recorded origins](#transcripts-without-recorded-origins)).
6. **Read mode and replay agree**, checked by the same probe, end to end through Scout. The probe ships, so a user can run the check on their own scaffold and logs ([Two modes: replay and read](#two-modes-replay-and-read)).
7. **Nothing quadratic** (maintainer, 2026-10-19): replay's work is linear in the log's stored size, and no step copies or rescans the conversation, live or in replay ([Nothing quadratic](#nothing-quadratic)).
8. **Replay is shown to be trustworthy, not only tested** (maintainer, 2026-10-20): production monitors run live and replayed over haystacks with planted needles and over real runs, comparing their prompts, verdicts and needles found, against the noise between two live runs ([Showing replay can be trusted](#showing-replay-can-be-trusted)).

### Decisions

Settled by this design (2026-10-19), each argued in its section:

- **The conversation comes from the span tree; no conversation field is recorded.** *Revised 2026-10-19.* First settled as `ModelEvent.conversation` and `CompactionEvent.conversation`, because the span tree gives the live answer only if every event's span chain leads to the span `current_agent_span_id()` named, and `SpanRotationScope` moves the current span through a shared cell that tasks spawned earlier also see. Checked by reading `util/_span.py` (inspect_ai 386e0994): the rotation scope only rotates the current span, for the checkpointer's `checkpoint` spans; it never sets the agent span, and each span it opens records as its parent the span current when the scope opened. So the innermost `agent` span reached from an event's `span_id` through `parent_id`, else the sample's uuid, is what `_conversation()` returned. PR 1's tests assert it on every model call, including a sandbox-bridged agent that checkpoints, whose service tasks were spawned before a rotation; a case where it fails brings the field back. A tool step's conversation is its producing `ModelEvent`'s.
- **The step builder lives in inspect_ai**, used by both drivers; the replay host, runner and Scout adapter live in sentinel.
- **Step ids, including `BeforeGenerate`'s repeat ordinal, are computed in one sequential pass** over the whole sample before any monitor runs, so concurrent units cannot change them.
- **A failed monitor fails the transcript's scan.** The runner records a raising monitor as failed, as live; `as_scanner()` reading a failed report for a monitor it is validating raises, so the transcript's Scout result is an error, as AGENTS.md's failure policy requires. A protocol that handles `observations.failed` reports its decision as usual.
- **Read mode compares by step id and instance path**, and the agreement test uses a probe monitor whose report is a digest of every step field. *Revised 2026-10-20 by the maintainer: the probe is public, `fidelity_probe()`.*

**Decisions for the maintainer.** None blocks the rest of the plan: each has a recommendation the PR series assumes, and changing one changes only the PR named. R7-D1 to R7-D7 were decided by the maintainer on 2026-10-19; R7-D6 and R7-D7 follow from the second. R7-D8 to R7-D12 came from review passes 1 and 2 (2026-10-20). The maintainer decided R7-D8 that day, and then the trims in [How exact replay is](#how-exact-replay-is), which settle R7-D8a and R7-D9 to R7-D12 without new log fields. R7-D8b is the one still open; it holds PR 1, and the rest of the plan assumes its recommendation.

- **R7-D1: record what replay needs whether or not a sentinel is configured?** *Decided by the maintainer 2026-10-19: yes.* Recommended: yes. It is set on every `ModelEvent` in a sample, so any log written after PR 1 can be replayed exactly, not only logs from evals that ran a sentinel. Alternative: record it only while a sentinel is active (where `record_agent_turn` runs today), which keeps logs from evals without a sentinel unchanged but leaves them with the older-log fidelity. Additive either way. Affects PR 1. *Revised the same day with R7-D4: what is recorded is `ModelEvent.origin`, a fact about where the call was made, rather than an `agent_turn` verdict and a conversation field ([What the log records](#what-the-log-records)); recording it regardless of a sentinel stands.*
- **R7-D2: add the `agent_messages` fingerprint to `SentinelEvent` now?** *Decided by the maintainer 2026-10-19: no, and as a rule, "nothing quadratic" ([Nothing quadratic](#nothing-quadratic)).* Recommended: no. Replay establishes `agent_messages` by cross-checking `sample.messages` (option 1 of [Reconstructing `agent_messages` in replay](#reconstructing-agent_messages-in-replay)) for every log. The fingerprint (option 2) helps only logs that ran a sentinel, and computing it means hashing the scaffold's whole list at every watched step, which is quadratic in a conversation's length. Revisit when a monitor needs `agent_messages` exactly in replay. Alternative: add `agent_messages_len` and `agent_messages_hash` to `SentinelEvent` in PR 1. Affects PR 1 only if chosen. *Overtaken 2026-10-20: `agent_messages` was redefined as the conversation as the agent ran it, which replay builds exactly from the log's events ([Reconstructing `agent_messages` in replay](#reconstructing-agent_messages-in-replay)); the cross-check is gone, and no fingerprint is needed.*
- **R7-D3: `as_scanner()` in `inspect_sentinel.scout` rather than `inspect_scout.sentinel`?** *Decided by the maintainer 2026-10-19: sentinel, while inspect_core is postponed, on the conditions below.* Recommended: sentinel. The adapter is the replay host and runner around `run_sentinel`, which change with sentinel's integration contract; Scout then needs only generic changes (condensed model events; `Result.subject`, deferred 2026-10-20) and never tracks sentinel versions, and workstream 10's reframing (2026-10-02) already puts the loop's verbs in sentinel, with Scout under the hood. Alternative: Scout, as first drawn in [Packages](#packages), which makes Scout depend on sentinel's private contract. Affects PRs 2 and 5.

  The dependencies decide where it can stay. Sentinel declares `inspect_ai`, Scout declares `inspect_ai`, and `inspect_ai` imports sentinel lazily without declaring it, so Scout as a sentinel extra is acyclic. The three-package cycle (sentinel → Scout → `inspect_ai` → sentinel) appears only when `inspect_ai` declares sentinel, which waits on inspect_core ([Packages](#packages)). So, decided with it:

  - Scout is an optional extra, `inspect_sentinel[scout]`, as `sidecar` is, never a required dependency. Only `inspect_sentinel.scout` imports it, and importing `inspect_sentinel` does not load `inspect_scout`.
  - `inspect_sentinel.scout` imports nothing private from sentinel: it is built on the public replay API (`replay_monitor()`, `ReplayStep`, the report types), so it can move to Scout unchanged.
  - When `inspect_ai` comes to declare sentinel, the adapter moves to `inspect_scout.sentinel` in the same change. `inspect_sentinel.scout` cannot stay behind as a re-export, since that import is the cycle.
  - The extra's floor is the first Scout release with PR 4.
- **R7-D4: where do conversations and agent turns come from in a transcript that does not record them?** *Decided by the maintainer 2026-10-19: from the transcript's timeline, improved for every reader rather than for replay alone.* First recommended the same day: `history` `None` for logs written before PR 1, with an opt-in inference flag. Revised because the case is common, not legacy: no source Scout imports (Claude Code, ATIF, LangSmith, Logfire, Phoenix, Weave) marks which model calls are the agent's own, so `None` by default would leave most of what people scan without a `history` or a correct set of generate steps. Settled with it, the same day:

  - **One definition, shared.** A conversation is an agent span of the transcript's timeline (inspect_ai `timeline_build`), and its agent turns are that span's own model calls that are not utility. The viewer, Scout's timeline scanners (`llm_scanner(timeline=, depth=, compaction=)`) and replay all read it, so improvements land in `timeline_build` and its TypeScript port, not in a replay-only classifier.
  - **Facts, not a verdict.** The log records where each call was made (`ModelEvent.origin`), and one rule says which origins are turns, live and offline. A recorded `agent_turn` was considered and dropped: it would freeze wrong answers into logs, such as a Petri audit's auditor calls today, and fix the definition at the time of writing. A typed span around each region that turns agent scope off was considered and dropped as clutter in the transcript. Origins are a closed set of kinds, since the rule must decide from the value alone; which agent a call belongs to is the name of its span.
  - **Where `origin` is missing** (older Inspect logs, other sources), `timeline_build`'s prompt rules and a new continuity rule mark helper calls ([Transcripts without recorded origins](#transcripts-without-recorded-origins)). A source that knows better supplies a stored timeline, as Petri does with `"target"`, or sets `origin` itself.
  - **Monitors do not branch on provenance.** A `context.replay` that told a monitor how its step was established was considered and dropped: a monitor under test must run the same code live and in replay. Each result records how its turns were established (`"turns": "recorded"`, `"inferred"` or `"stored"`), and what to trust is chosen by which transcripts are scanned (Scout's transcript filters, such as `source_type`) and by filtering results. Selection uses Scout's own options, `timeline=`, `depth=` and `compaction=`, with the meanings `llm_scanner` gives them; the `infer_agent_turns=` flag and a mode treating every call as a turn are dropped.

  Affects PRs 1, 3, 5 and 6.
- **R7-D5: `human()` in replay when the log holds no answer for it.** *Decided by the maintainer 2026-10-19: a policy, `as_scanner(human=...)`, answers; by default the recorded answer, else the answer a host gives when no person can be asked, marked as not a person's.* First recommended the same day: `Host.ask_human` returns `None` and `human()` abstains. Revised because abstaining is not neutral. In `sequential([threshold(...), human(...)])` the threshold's `escalate` is then the chain's last decision, and an escalate that reaches the root becomes a `terminate` recorded as an unhandled escalation ([pr-series.md](pr-series.md), "Unhandled escalate"), a configuration bug the configuration does not have; beside peers in a `concurrent()` it lets their `proceed` through instead. The decided form:

  - **The recorded answer**, when the same `human()` instance, by path, answered at the step: its `SentinelEvent` ([Human decisions in replay](#human-decisions-in-replay)). For a log from an eval that ran no sentinel, a person's `ApprovalEvent` for the call answers a `human()` at `tool_call` (the approvers named by `human_approvers=`, mapped as in [Transcripts without recorded origins](#transcripts-without-recorded-origins)).
  - **Otherwise the fail-closed answer**: `reject` where it is offered, `terminate` otherwise, as the sidecar host and Inspect's own host answer when no person can be asked (`sidecar/_host.py`, `ask_human`). A protocol then decides as it would live with nobody there.
  - **Or a stand-in for the person**: `human=` takes a callable `(ReplayStep, Escalations, choices) -> HumanAnswer`, asked where there is no recorded answer: an oracle built from validation labels, as AI control evaluations model a reviewer, or a model.
  - **Each answer says where it came from.** The result of a step whose protocol reached `human()` records `"human": "recorded"`, `"unanswered"` or `"simulated"` in its metadata, so a back-test counts the steps that would have gone to a person apart from real blocks.

  `Host` and `human()` do not change; the policy is the replay host's. Affects PR 5. *Refined 2026-10-20 after review pass 2 (F9), and trimmed the same day:* the stand-in is `async`, `(ReplayStep, Escalations, choices) -> Awaitable[HumanAnswer]`, so it can ask a model, whose usage lands in the scan's `model_usage`. A recorded answer is replayed as recorded even from a prompt the person closed without choosing, or against escalations the replayed configuration no longer makes; both are known differences ([How exact replay is](#how-exact-replay-is)).
- **R7-D6: steps share read-only views of the conversation's lists instead of copies?** *Decided by the maintainer 2026-10-19: yes; `Sequence` is preferred.* Recommended: yes. To meet "nothing quadratic", `history`, `agent_messages`, `human_decisions` and the tool stages' `input` and `tools` become read-only sequences (`Sequence[ChatMessage]`, `Sequence[HumanDecision]`, `Sequence[ToolInfo]`) that share the list they are cut from, live and in replay, in place of the `list` and `tuple` copies each step makes today. A breaking change to the step types, with no compatibility kept (sentinel 0.x); a monitor that wants a list calls `list()` on it, at its own cost. Alternative: keep the types and copy at every step, which is quadratic in a conversation's length. Affects PRs 2 and 3. *`agent_messages` added 2026-10-20 after review pass 1: it is cut from a per-conversation record like the others, so it is a view too.*
- **R7-D7: does the rule also cover the one pass each agent turn makes over its own input?** *Decided by the maintainer 2026-10-19: no, keep the pass.* Recommended: no, keep that pass. Live, `record_sent` compares each message of a turn's input with what was sent before, mostly by identity, as the call is made. That work is in proportion to the request the call sends, which inspect_ai already serializes whole and whose messages the log's pool already hashes one by one (`condense_model_event_inputs`, `event/_pool.py`), so it does not change the order of the run's cost; removing it would need the agent loop to tell inspect_ai which messages are new, which no scaffold does. What the rule removes is work repeated at every step over the whole conversation. Alternative: treat the pass as quadratic too, and design an interface for scaffolds to pass only new messages. Affects nothing in R7 if accepted.
- **R7-D8: what generate step ids and the as-sent fold rest on.** *Decided by the maintainer 2026-10-20: live stops depending on message ids.* Charles: "yes i agree with thinking on ids. investigate risk of changing format. let's use a concise format it doesn't need to be human legible. it obv needs to withstand concurrency". Raised by review pass 1: the log's message pool deduplicates by content without the id (`_msg_hash`, `event/_pool.py`, hashes `model_dump_json(exclude={"id"})`; the incremental writer in `event/_pool_index.py` falls back to the same hash), so a restored input gives each position the id of the first message stored with that content, and live depended on ids twice. `BeforeGenerate`'s step id was the last input message's id with an ordinal (`_step_id`, `_sentinel/_dispatch.py`), and the as-sent fold counted a message under a new id as new unless it was unchanged at the same position (`_record`, `_sentinel/_sent.py`). So two calls whose last input messages were `u1` and `u2` replayed as `u1` and `u1:2`, and an input `[a: A, b: B]` followed by `[c: B, d: A]` folded to four messages live and two from the pool. Decided:

  - **No `input_id_overrides` field.** It was the first recommendation (sparse `[position, id]` pairs on the condensed `ModelEvent`, restoring the ids the pool drops); it is now an alternative, as are hashing the id into the pool key (a rebuilding scaffold's messages stored again on every call) and recording only the last input message's id.
  - **Generate step ids no longer come from message ids.** The format is concise, need not be legible, is identical live and in replay, and withstands concurrency: parallel agents and sub-agents in one sample, sub-agents sharing one conversation inside a bridged CLI, and fan-out over one prompt object. The tool stages keep the tool call id.
  - **`history` decides what is new by content and position**, aligned against the previous call's input, with no ids ([The as-sent fold without ids](#the-as-sent-fold-without-ids)).

  Why the id was the last input message's (inspect_ai #5811, 2026-10-12, which built `_step_id`; `generate-stages.md` section f and decision 15; [Step ids](#step-ids)): a step id must exist live when the monitor runs, in a messages-only transcript and in an events transcript, so that one label serves replay and read mode; a message id was the only thing all three had before the `ModelEvent` exists. The ordinal was added for loop-level retries, a rejected call regenerated behind the same last message. Neither reason requires a message id once the log carries the generate's own id.

  **Risk of changing the format** (checked 2026-10-20 against inspect_ai `main` 4a4f7ea, PR #5986 at 86d921d, ts-mono `main` 96a1c0b, inspect_scout `main` 2653f93, and this repository):
  - inspect_ai writes the id and reads it nowhere: `_Recorder` stamps every `SentinelEvent` of a step with it (`event/_sentinel.py`, `step_id: str`), and `kept_human_decision()` copies it into `HumanDecision.step_id`. Its type stays `str`, so the OpenAPI schema and generated viewer types do not change.
  - ts-mono's viewer uses it as an opaque key: outside a `sentinel` span it groups `SentinelEvent`s by `stage` + `step_id`, and it pairs only tool-stage steps with their `ToolEvent` by `step_id == ToolEvent.id` (`transcript/transform/toolSentinels.ts`, `pairToolSentinels`, `hostTool`). The tool stages do not change. Nothing renders or parses a generate-stage id.
  - Sentinel stores `HumanDecision.step_id` and never parses it; a decision's `call_ids` at `model_output` come from the step's output, not from the id (`_human_decisions.py`). The sidecar computes and reads no step id; Scout has none.
  - What breaks is one documented rule: `generate-stages.md` section f links a `model_input` event to its `ModelEvent` through the last input message's id and a `model_output` event through `output.message.id`. With the change both link through the generate's id, the `uuid` of its first `ModelEvent`, which is simpler; that section is updated with PR 1 ([What this asks of the other documents](#what-this-asks-of-the-other-documents)). The replay rule that found a `model_output` decision's calls through the assistant message with that id reads them from that generate's output instead.
  - Old and new logs side by side: nothing joins step ids across logs. Read mode and replay join within one log, and labels are keyed by transcript and step. A log written before the change has no generate id; replay takes a generate's step id from what that log does have, in a fixed order ([Step ids](#step-ids), "Computing them in replay"), so read rows, `HumanDecision`s and labels still join wherever a live record exists, and each step records which source it used.
  - No compatibility is kept: sentinel is 0.x, and inspect_ai's change is to a value inside an unchanged field. It lands in PR 1 with the fold.

  Sub-decisions:

  - **R7-D8a: where the generate's id comes from.** *Decided by the maintainer 2026-10-20, with the trims in [How exact replay is](#how-exact-replay-is): the uuid of the generate's first `ModelEvent`, minted before the sentinel runs; no new field.* `Model.generate()` mints the uuid its first attempt's `ModelEvent` will carry before `sentinel_before_generate()`, uses it as the step id, and creates that event with it. It is unique and random, so no counter or schedule can reorder it, and it is identical live and in replay, since replay reads it from the event. A retry attempt's event has its own uuid, so a generate's attempts are grouped by inference: errored attempts followed by one with the same input, in the same span. A `BeforeGenerate` that left no `ModelEvent` keeps its id in its `SentinelEvent`. The id is 22 characters (inspect_ai's shortuuid), not the 11 a new field would have taken. Considered: `ModelEvent.generate_id` on every attempt, which groups attempts exactly for about 30 bytes per event; and a hash of the conversation and an ordinal, which needs no field but is numbered in scheduling order live and in log order in replay when sub-agents share a bridged CLI's conversation.
  - **R7-D8b: does `AfterGenerate` share the generate's id?** *Open.* Recommended: yes. The two steps of one generate then join directly, two cache hits on one request no longer share one `model_output` id (left open in `generate-stages.md`), and an output with no choices no longer has the empty id. Alternative: keep the output message's id, which is stable and needs nothing new, but keeps both of those defects and gives the stage a different kind of id from its `BeforeGenerate`. Affects PRs 1 and 3.
- **R7-D9: record how far each tool call got?** *Decided by the maintainer 2026-10-20, with the trims: no field; replay infers it.* Live, `BeforeToolCall` runs only for a call that parsed, names a known tool and was approved, and `AfterToolCall` only where `_apply_tool_review` reaches the sentinel: the body returned without an unmapped exception, the call was not cancelled, and no review policy terminated (`call_tool`, `call_tool_task`, `_apply_tool_review` in `model/_call_tools.py`). Rejected, unparsable, unknown, halted, cancelled and failed calls still get a `ToolEvent`, so replay infers from the log which stages ran ([One builder for live and replay](#one-builder-for-live-and-replay), "Which steps ran"). One case cannot be told apart: a schema validation error, after `BeforeToolCall` and before the body, and a `ToolParsingError` the tool raises itself record the same error type; replay reads both as the first, so a tool that raises `ToolParsingError` itself gets no `AfterToolCall` in replay. Considered: `ToolEvent.reached` (`"checked"`, `"reviewed"`), about 20 bytes per tool event, exact, and robust to changes in how `_call_tools.py` records errors, which PR 3's test catches for the cases it scripts.
- **R7-D10: record which step a `sentinel` span checked?** *Decided by the maintainer 2026-10-20, with the trims: no; cuts at per-stage anchors.* A span whose instances all abstained holds no `SentinelEvent`, so replay cannot find it, and cuts the step's `history` and `human_decisions` at an anchor that keeps decisions published in between ("The cut"). That differs from live only when a parallel call's step publishes between the step being built and its anchor. Considered: `SpanBeginEvent.metadata` holding the stage and step id on `sentinel` spans, about 50 bytes per span; a `SentinelEvent` for every step; the step in the span's name.
- **R7-D11: a `BeforeGenerate` that ran live but left no `ModelEvent`.** *Decided by the maintainer 2026-10-20, with the trims: replay builds no step for it, and this document says so.* The sentinel terminated at that step, a monitor there failed, or `_check_limits_before_dispatch()` refused the call ("so that a call refused here leaves no event behind", `model/_model.py`), so the request is in the log nowhere. Read mode still has that step's `SentinelEvent`s. Considered: a `"missing"` list on the transcript's result; a step rebuilt from the previous turn, marked approximate; the request recorded on the `SentinelEvent`.
- **R7-D12: say when a person did not answer.** *Dropped by the maintainer 2026-10-20, with the trims.* When a person ends a `human()` prompt without choosing, the host answers `reject` if offered and `terminate` otherwise, and nothing records that the prompt was closed, so replay marks it `"human": "recorded"`. That is a listed known difference. Considered: `HumanAnswer.closed`, recorded by `human()`.

### How exact replay is

*Decided by the maintainer 2026-10-20.* Asked whether the design was adding complexity and overhead for exact playback of edge cases that add no value, the maintainer agreed to trim it to one rule: **replay is exact where monitors commonly look; elsewhere this document says it is not; a log field is added only when a common case needs it.** So PR 1 adds one field, `origin`, beside R7-D8's change to how live builds generate ids and `history`. Trimmed, each first proposed after a review pass: a generate id field (R7-D8a), how far each tool call got (R7-D9), the step named on its `sentinel` span (R7-D10), a `"missing"` record (R7-D11), `HumanAnswer.closed` (R7-D12) and an `"escalations"` marker (R7-D5), a fidelity record per step (dropped, with the one-flag form that replaced it), and most fail-closed rules for malformed logs (two kept, [One builder for live and replay](#one-builder-for-live-and-replay), "Logs as input").

**No per-step flag.** *Decided by the maintainer 2026-10-20.* A flag marking approximate steps (`ReplayStep.approximate`, `"approximate": true` in result metadata) was proposed with the trims and dropped. Monitors never see it, since R7-D4 keeps provenance out of the step, and for analysis it would mislead: most differences below cannot be detected per step (an edit after sending, a closed prompt, a scaffold's own retry, a parallel publish race), two leave no step to mark, and the rest are properties of the whole log, so a missing flag would read as "exact" when it is not. A result keeps `"turns"` (R7-D4) and `"human"` (R7-D5), which mark something real. To leave out whole logs, filter on what Scout already exposes per transcript: its source type, the inspect_ai version, and the eval's configuration, such as `log_images`.

**Known differences.** Each is stated where it arises, and PR 3's test names it rather than scripting machinery for it:

- a tool that raises `ToolParsingError` itself gets no `AfterToolCall` in replay (R7-D9);
- a `BeforeGenerate` that left no `ModelEvent` gets no step (R7-D11);
- a step whose `sentinel` span holds no event is cut at its anchor, which differs when a parallel call's step publishes in between (R7-D10);
- a scaffold that catches a model error and calls generate again with the same input is replayed as one generate, since attempts are grouped by inference (R7-D8a);
- a message the scaffold edits in place after sending it shows as sent in replay and as edited live, in `history` and `agent_messages`;
- a log written with `log_images=False` holds a placeholder for each image;
- a recorded `human()` answer is replayed as recorded when the person closed the prompt without choosing (R7-D12), and when the replayed configuration hands `human()` different escalations from the ones the person saw;
- a scaffold that runs one message's calls in more than one `execute_tools()` call has them replayed as one batch;
- `eval.metadata` is the sample's final metadata, which a solver can have changed during the run;
- in a log written before R7-D8, generate step ids come from the fallbacks in [Step ids](#step-ids).

### Nothing quadratic

Decided by the maintainer on 2026-10-19, rejecting the `agent_messages` fingerprint (R7-D2): "nothing quadratic". A conversation of *n* turns has inputs that grow with *n*, so any work that walks the whole conversation at every step or every call costs the square of *n* over a run. Replay's work is linear in the size of the log as stored (its message pool, its events and their input ranges), and per step it is constant beyond what the monitor itself reads. Each piece:

| Work | The quadratic way | How replay does it |
|---|---|---|
| Reading model inputs | expanding every `ModelEvent`'s input from the pool: Scout decodes each pooled message again for every event that refers to it (`_transcript/json/stream_parse.py`, `resolve_item_dict`), and inspect_ai's reader builds a list per event (`event/_pool.py`, `_expand_refs`) | the log driver reads each event's `input_refs` and the message pool, decoding each pool message once; a step's `input` is a view over its event's ranges. Scout gains a way for a scanner to receive model events condensed (PR 4) |
| The as-sent fold | walking each turn's whole input against everything sent | aligning each turn's input against the previous turn's only ([The as-sent fold without ids](#the-as-sent-fold-without-ids)): a range equal to the previous turn's at the same position is matched whole; other positions are matched by a content key computed once per pool row |
| Finding a step's producing `ModelEvent`, its `sentinel` span, its `ToolEvent` and `ApprovalEvent` | a search per step | indexes built in the single pass: by event uuid, by stage and step id, and by tool call id resolved by position, the newest before the step, as live's `find_last` ([One builder for live and replay](#one-builder-for-live-and-replay), "Logs as input") |
| `history`, `human_decisions`, `agent_messages` per step | a copy per step | a read-only view of the conversation's append-only list cut at a length, typed `Sequence` (R7-D6, decided 2026-10-19) |
| `agent_messages` | rebuilt from the conversation's events at each step | appended to in the single pass, one message per agent turn's output and per tool result, and cut at a length per step |
| Step ids, the cut, units | | generate ids read from the events; positions from the single pass |
| The agreement probe | hashing every list at every step | digests `history` and `agent_messages` by length and their last message; whole lists are compared only in inspect_ai's step test, over small scripted evals |
| Scout's rows | the transcript copied per row | one resultset row per transcript, expanded per step only when the dataframe is read |

**Built code the rule reaches** (found 2026-10-19, fixed in PR 3, which rewrites the builder anyway). Live, every step copies whole lists: `sent_messages()` returns `list(found.messages)`, the as-sent list so far; the tool stages copy the producing call's input and tools (`list(producer.input)`, `list(producer.tools)`); `_human_decisions()` copies the published list into a tuple (`_sentinel/_dispatch.py`, `_sentinel/_sent.py`); and inspect_ai PR #5986's `ran_messages()` returns `list(ran)`, a copy of the whole `agent_messages` record at every step (found by review pass 2, F10). R7-D6 (decided 2026-10-19) replaces them with views typed `Sequence`. `record_sent` also walks each turn's whole input and rebuilds its `previous` list; R7-D7 asks whether that per-call pass stays.

**Pinned by counting, not timing.** PRs 3, 4 and 5 each add a deterministic test that counts the work rather than timing it: on synthetic conversations of *n* and 2*n* turns, with a compaction and parallel tool calls, the pool messages decoded, the messages the fold visits and the elements copied into step fields stay within a constant times the log's size, and double, not quadruple, from *n* to 2*n*.

## Reconstructing steps

### What the log records

Specified 2026-10-19 as inspect_ai PR 1; revised the same day (R7-D4) from `agent_turn` and conversation fields to one fact, `origin`. Live, inspect_ai decides at each model call whether it is one of its conversation's agent turns, from a context variable (`AgentScope`, `_sentinel/_scope.py`), and folds the input into that conversation's as-sent list (`Model._record_model_interaction` calls `record_agent_turn`, `_sentinel/_dispatch.py`), but writes none of it to the log. Of the places that turn agent scope off, tools, scorers and a sentinel's own run sit in spans that say so: the compaction summary call (`model/_compaction/summary.py`) runs inside the agent's span with the agent's system prompt, and approval, review and MCP sampling open no span. So a log cannot say which calls make up `step.history`. One field fixes that:

| Event | Field | Type | Set | Old logs read as |
|---|---|---|---|---|
| `ModelEvent` | `origin` | `str \| None`, default `None`; one of the kinds below | when the event is created in `Model._record_model_interaction`, from the current scope | `None`: not recorded |

**The kinds** are a closed set that inspect_ai owns, since every reader of the rule depends on it:

| Kind | Set by | A turn |
|---|---|---|
| `"agent"` | the default during the solve, and every `span(type="agent")` (`util/_span.py`), which `as_tool()`, `handoff()`, `run()` and `as_solver()` open | yes |
| `"environment"` | `model_origin("environment")`: the setup being evaluated against, such as Petri's auditor or a simulated user | no |
| `"helper"` | `model_origin("helper")`: a scaffold's own helper call in its loop, such as its own summarizer | no |
| `"tool"` | a tool's own body (`model/_call_tools.py`) and a bridged host tool (`agent/_bridge/sandbox/service.py`) | no |
| `"compaction"` | the compaction summary call | no |
| `"approval"`, `"review"` | approval and review | no |
| `"sampling"` | MCP sampling | no |
| `"sentinel"` | a sentinel's own run, including its monitors' calls | no |
| `"scorer"` | `score()` and the scorers | no |
| `"setup"` | any other call outside the solve, such as sample init | no |

`sentinel_scope()` takes the kind of its region and the scope's context variable carries it, so `origin` is the kind of the innermost region. A `final` region keeps its kind under an agent span opened inside it, as agent scope does today: an agent span inside approval stays `"approval"`. `"environment"` and `"helper"` are final too, so an auditor's sub-agent stays environment. A new kind is a change to inspect_ai, never a scaffold's own string.

**The rule is one function** in inspect_ai: a call is an agent turn when its origin is `"agent"`. The dispatcher uses it live in place of `current_scope() is AgentScope.ON`, `is_agent_generate()` becomes an active sentinel and that rule, and `timeline_build` and the log driver read it from the event. Because the context variable that sets `origin` is the one live already reads, the recorded value is the live one, with or without a sentinel (R7-D1).

**Names come from spans.** Which agent a call belongs to ("target", "auditor") is the name of its enclosing span, already in the log; no free-form name is recorded. One can be added beside the kind later, if a case without a span needs it.

**`model_origin()` is public**, accepting the kinds a scaffold may set, `"environment"` and `"helper"`; the others are inspect_ai's. Its docs say the marker reaches only the task that set it and the tasks that task spawns, so a design that makes the evaluated agent's calls from inside an environment region, such as an auditor's tool that generates the target's turn, marks the target too. Petri's current design does not ([What this asks of the other documents](#what-this-asks-of-the-other-documents)).

**The conversation is not recorded.** It comes from the span tree: the innermost `span_begin` of type `agent` reached from the event's `span_id` through `parent_id`, else the sample's uuid (Decisions, above). A `CompactionEvent` is placed in its conversation the same way.

**The timeline uses it** (PR 1). Where `origin` is recorded, `timeline_build` and its TypeScript port (ts-mono `timeline/core.ts`) mark a call whose origin is not `"agent"` as utility and do not apply their system-prompt rules to it. An agent span with no turn, such as an auditor's, stays in the tree as a conversation, not as utility. So the compaction summary call drops out of the viewer's timeline and Scout's timeline scanners as it drops out of `history`, and Petri's hand marking of its realism spans as utility (`_mark_utility_spans`) is no longer needed. The viewer can label a call with its origin; it need not.

**Additive.** `origin` has a default, so older logs load with `None`; events are pydantic models with the default `extra="ignore"` (none in `event/` sets `forbid`), so an older inspect_ai reading a newer log drops it. inspect_ai's OpenAPI schema and ts-mono's generated viewer types are regenerated with the PR (ts-mono's change lands on its `main` first). No span or event is added, so the transcript gains nothing to show, and the viewer and the ACP TUI, which treat span types specially, see no change, as generate-stages.md decision 15 requires.

**Cost.** About 20 bytes of JSON per `ModelEvent` (`"origin":"agent"`) before the log's compression, against model events whose `input`, `output`, `config` and `call` run to kilobytes; PR 1 measures a 300-turn mockllm sample to confirm. At run time, one context-variable read per model call.

**Not recorded, and why.** A tool event's origin or conversation: a tool step's are its producing `ModelEvent`'s. The step's `agent_messages`: built from the conversation's agent-turn `ModelEvent`s and `ToolEvent`s ([Reconstructing `agent_messages` in replay](#reconstructing-agent_messages-in-replay)). A per-step input: R2 is met from the producing `ModelEvent` (pr-series.md, Deferred, "Record `step.input` instead of rebuilding it"). The untruncated tool output: never in the log, so `AfterToolCall.output` is `None` in replay.

**Acceptance for PR 1.** Table-driven tests on mockllm, with and without a sentinel configured. `origin` is `"agent"` for the `generate()` solver, `react` turns, sub-agents run through `as_tool()`, `handoff()` and `run()`, and a bridged agent's calls; `"tool"` for a tool's own call; `"compaction"`, `"approval"`, `"review"`, `"sampling"`, `"sentinel"` (a monitor's call), `"scorer"` and `"setup"` for theirs; and `"environment"` and `"helper"` under `model_origin()`, including for an agent span opened inside them or inside approval. The conversation from the span tree equals `_conversation()` on every model call, including a sandbox-bridged agent that checkpoints. With a probe sentinel watching all four stages, every live `step.history` equals the fold of the inputs of its conversation's `"agent"` calls before the step's `sentinel` span, in log order, so the field is sufficient before any replay code exists. `timeline_build` and its port agree on a shared fixture. A log written before the field loads with `None`. The schema and viewer types are regenerated. With R7-D8: the sufficiency test passes for two calls whose last input messages have the same content under ids `u1` and `u2`, an input `[a: A, b: B]` followed by `[c: B, d: A]`, a message edited between calls, a message inserted in the middle, a message dropped and later restored, and two identical `continue` nudges sent at different turns; live, each generate step's id is the `uuid` of that generate's first `ModelEvent`, for parallel agents, a fan-out of one prompt object to several sub-agents, and sub-agents sharing a bridged CLI's conversation.

### The as-sent fold without ids

*Decided 2026-10-20 (R7-D8).* `step.history` holds every message a conversation's agent turns have sent, each once, where it was first sent. Live, inspect_ai decided what was new by message id and by position (`_record`, `_sentinel/_sent.py`), which a log's pool cannot reproduce. Live and replay now share one rule, in `_sentinel/_steps.py`, that uses content and position only:

- **Same content** is the message without its `id`, `source` and `metadata`, the fields not sent to the model (`_NOT_SENT`), compared by a content key: a hash of that form. Live computes the key once per message object, keyed by object identity as the pool's own writer does, so a re-sent object is not hashed again; replay computes it once per pool row.
- **Alignment.** Each agent turn's input is walked against the previous turn's input of the same conversation, with a pointer into the previous input. A message the same as the one at the pointer, or at a later position of the previous input (found through an index of the previous input's keys), is matched, and the pointer moves past it; the messages skipped over were dropped by this call. A message matched nowhere at or after the pointer is new and is appended to `history`. The first turn's whole input is new.
- **Cost.** One pass over each input and one index of the previous input's keys, in proportion to what the call sends, as R7-D7 accepted; in replay, ranges equal to the previous input's at the same position are matched whole without decoding.

What this changes live (R10): a message rebuilt with a fresh id where it was before is matched, as the alias rule did; a message edited between calls is new, as a new version was; a message reordered is new, as one under a fresh id was. Two cases change: a message re-sent under its own id at a new position, which the id rule matched, is now new unless it follows its previous position in order; and a message dropped by one call and restored by a later one is counted again. Two equal messages sent at different turns, such as `react`'s repeated `continue` nudge, stay two messages, since each is new where it appears. PR 1 changes the live fold to this rule and its sufficiency test covers each case.

### One builder for live and replay

AISI's last R7 line, "live and replay stay identical as Sentinel changes", is a property of code, not of a document: two builders drift. So there is one.

**inspect_ai owns it.** A new module, `_sentinel/_steps.py`, holds one function per stage that takes the facts a step is made from and returns the step, and the pieces those facts need: the as-sent fold (`_Sent`, made a plain object whose `record(input)` both drivers call; `record_sent` keeps its per-transcript map for the live driver), the producing-call predicate (`_produced_by`), step ids with `BeforeGenerate`'s repeat counter, and the conversation's `human()` decisions published as each step settles (`_publish`, `_human_decisions`). The live driver is `_dispatch.py` as it is, gathering facts from its arguments, the transcript's history and context variables. The log driver, `steps_from_events()`, gathers the same facts from a sample's events, messages and message pool, in one pass that is linear in the log's stored size ([Nothing quadratic](#nothing-quadratic)):

| Fact | Live (`_dispatch.py`) | From the log |
|---|---|---|
| conversation | `_conversation()` | the innermost `agent` span above the producing or own `ModelEvent` (its `span_id`, then `parent_id`), else the sample's uuid |
| agent turns folded so far | `record_sent` as each call is made | the conversation's `ModelEvent`s whose `origin` is `"agent"` before the step's cut (below), in log order; without `origin`, the timeline's turns ([Transcripts without recorded origins](#transcripts-without-recorded-origins)) |
| `input`, `tools` at the tool stages | `_producing_event()`: `transcript().history.find_last(_produced_by(id))` | the same predicate over the log's events |
| `input`, `tools`, `tool_choice`, `config`, `model` at the generate stages | `Model.generate`'s arguments | the turn's `ModelEvent` |
| `output` | `Model.generate`'s result | `ModelEvent.output` |
| `call`, `message` | `execute_tools`' arguments; at `AfterToolCall`, the call that ran (`executed_call`), with any modification a sentinel made at `BeforeToolCall` | at `BeforeToolCall`, the assistant message in the producing `ModelEvent.output`, with an approver's modification from its `ApprovalEvent`, since approval runs before the sentinel; at `AfterToolCall`, the call that ran, from the `ToolEvent`'s `id`, `function` and `arguments`, which `call_tool` sets after a sentinel's `modify` |
| `result` | the `ChatMessageTool` built for the model | the message with `ToolEvent.message_id`, from a later input of the conversation or `sample.messages`, else rebuilt from the `ToolEvent` (`result` is the content the model saw) |
| `truncated` | `execute_tools`' `(original, limit)` | `ToolEvent.truncated` |
| `view` | `resolve_tool_call_view(call, viewer)` | at `AfterToolCall`, `view.call` from `ToolEvent.view`; at `BeforeToolCall`, the whole view from an `ApprovalEvent` where one recorded it, else `ToolEvent.view` when the `ToolEvent`'s arguments equal the approved call's, else absent, since a sentinel's `modify` replaced `ToolEvent.view` with the modified call's and the tool's viewer is not in the log; `context` absent |
| `human_decisions` | published as each step's span ends | the same rules over the log's `SentinelEvent`s ([Human decisions in replay](#human-decisions-in-replay)) |

**The cut.** Live, a step's `history` and `human_decisions` are taken when the step is built, just before its `sentinel` span begins, and a step's own `human()` decisions are published when its span ends (`_publish`). In a log that ran a sentinel watching the step's stage, the cut is that span's `SpanBeginEvent`, found by the `SentinelEvent`s inside it, so the replayed value is the live one. Elsewhere, and for a span holding none because every instance in it abstained (R7-D10), the cut is the step's anchor, the last point before the step was built: before its own `ModelEvent` at `BeforeGenerate`; at that event's end at `AfterGenerate`; just before its call's `tool` span begins at `BeforeToolCall` (`call_tool` builds the step after approval and before the span); and at that span's end at `AfterToolCall` (`_apply_tool_review` builds it once the body returns). Decisions published before the anchor are in; the step's own call's are not. *Revised 2026-10-20 after review pass 1: the tool stages' anchor was after the producing `ModelEvent`, which drops a decision published at the call's `tool_call` step from its `tool_result` step.* The anchor differs from the live cut only when a parallel call's step publishes between this step being built and its anchor, or another agent turn of the same conversation starts there, which takes two agents sharing a conversation, as sub-agents inside one bridged CLI do.

**Events in log order.** The driver reads events in the order the log stores them, flattening an older log's nested events (`ToolEvent.events`) in place, and makes one sequential pass over the whole sample before any monitor runs: step ids, the fold, the cut and the published decisions all depend on order, and none on monitor results. The pass yields `ReplayStep`s in live order; the runner then groups them into units ([Cost and parallelism](#cost-and-parallelism)).

**Logs as input.** *Added 2026-10-20 after review pass 2 (F5); trimmed the same day.* Replay trusts the structure inspect_ai writes (events, their order, spans and their parents, the ids inspect_ai mints, the message pool) and never the content the agent under observation writes or is shown, which it passes to monitors as data and never reads as structure. Tool call ids come from the provider, and through some servers and bridged CLIs from the model's own text, so nothing makes them unique across a sample; replay resolves one by position, as live does (the newest producing `ModelEvent` before the step, `find_last`, and the `ToolEvent` and `ApprovalEvent` after it). Two things fail the transcript, a Scout error naming the rule, rather than being guessed at: two steps of one stage with one step id, which no result row could tell apart, and a `parent_id` cycle in the span tree, which a walk must never loop on. An unknown `origin` needs no rule: only `"agent"` is a turn, so a kind added later reads correctly as not a turn. `origin` stays typed `str` in the schema, since a `Literal` would make an older inspect_ai fail to load any log written after a kind was added.

**Which steps ran.** *Added 2026-10-20 after review pass 1; revised after review pass 2, and trimmed to inference.* From events, a step exists where it ran live, or would have run had a sentinel watched its stage, which a result message or a completed `ModelEvent` does not imply. A generate is one `Model.generate()` call, which writes one `ModelEvent` per attempt: a provider error retried, an attempt timeout, or a cache hit on a retry (a failed attempt keeps its event with `error` set and a pre-filled empty output, `_model.py`). Its attempts are grouped by inference: errored attempts followed by one with the same input, in the same span, are one generate, whose id is its first attempt's `uuid` (R7-D8a).

| Stage | Exists when | Inferred from |
|---|---|---|
| `BeforeGenerate` | once per agent-turn generate, not per attempt | `origin`; a generate that left no `ModelEvent` gets no step (R7-D11) |
| `AfterGenerate` | the generate's last attempt records no `error`, and its output is not a refusal raised under `fail_on_refusal` (`config.fail_on_refusal`, a non-empty output, `stop_reason == "content_filter"`) | the events |
| `BeforeToolCall` | the call got past parsing, lookup and approval | not for a call with `parse_error`, an unknown tool, an `ApprovalEvent` that rejected or terminated, or a halted call's synthesised `cancelled` result |
| `AfterToolCall` | the body returned normally and no review policy terminated | not for the calls above, nor a call whose error is `parsing` (read as a schema validation error, R7-D9), nor one whose `ToolEvent` records `failed` or an operator cancel's `timeout`, nor one in a batch the sample ended in |

The messages projection ([From messages](#from-messages)) cannot tell any of this and stays approximate: it builds a step for every assistant message and tool result.

**What pins it.** Two tests, so a field added to a step without its log form fails CI:

- In inspect_ai (PR 3), **live equals replay, step by step.** Scripted mockllm evals of the common cases (`react` with summary compaction, parallel tool calls, a truncated result, a sub-agent through `as_tool()` and one through `handoff()`, a retried refusal, a provider error retried to success, a cache hit, a `GenerateConfig` system message rebuilt each call, a scaffold that rebuilds its input each call, an approver that modifies a call, a sentinel that modifies a call at `tool_call`, a scripted `human()` answer, `human()` approving a call at `tool_call` followed by an abstaining monitor at `tool_result`, a rejected call, an unparsable call, a schema validation error, a pre-filled assistant message run through `execute_tools()`, and a batch that raises) run with a probe sentinel watching all four stages that records each step it is handed. The test rebuilds the steps from the written log with `steps_from_events()`, asserts that the set of stage and step-id keys is the same as live, and compares the steps by those keys over every field of the step dataclass, iterated with `dataclasses.fields()`, against a short, named list of fields that replay leaves absent (`AfterToolCall.output`, `view.context`). A new step field is compared by default, so it fails until its log form is built or it is added to that list on purpose. The known differences ([How exact replay is](#how-exact-replay-is)) are named in the test as such, not scripted.
- In inspect_sentinel (PR 5), **read mode equals replay, end to end** ([Two modes](#two-modes-replay-and-read)).

### From messages

The canonical reconstruction works from `list[ChatMessage]` alone, because that is what every source has — an eval log, a Scout transcript from another agent framework, a proxy request. It is exactly the projection `agent/_bridge/_approval.py` performs on a model response and `sentinel-deployment.md` describes for a proxy:

| Stage | Reconstructed from | Fidelity |
|------------------------|------------------------|------------------------|
| `BeforeGenerate` | every message before an assistant message is that generate's `input` | `tools`, `tool_choice`, `config` absent |
| `AfterGenerate` | the assistant message is `output.choices[0].message`; `usage`, `time` absent | good |
| `BeforeToolCall` | each `tool_calls[i]` on an assistant message, with the message text and history to that point | `view` absent |
| `AfterToolCall` | the `ChatMessageTool` whose `tool_call_id` matches, as `result`; history to that point | `output` (untruncated) absent; `truncated` is `None` (unknown) |

Messages give the two histories unevenly. From messages alone, `agent_messages` at a step is the messages before the first assistant message, then each assistant message and tool message up to the step, leaving out later user messages; it is right where the transcript is one agent's run, as everything built from messages assumes, and approximate otherwise, since messages do not say which model calls were agent turns (see "Reconstructing `agent_messages` in replay" below). At the tool stages `input` (and with it `tools`) is `None` from messages alone: the history to that point is right until the first compaction and wrong after it (the model was shown a summary plus recent turns), so it is not offered as the model's input. A live step without a recorded model call gets `None` the same way, so a monitor handles both alike.

`view` and `output` being absent is the case `sentinel.md` already requires monitors to tolerate for proxies, which also give `agent_messages` as `None`, so a portable monitor replays from messages unchanged. Note the last row is *better* than the proxy's: a proxy never sees the final step's result because no further request carries it, whereas a transcript is complete.

``` python
@dataclass(frozen=True)
class ReplayStep:
    id: str                 # the step id — see below
    stage: Literal["model_input", "model_output", "tool_call", "tool_result"]  # as SentinelEvent.stage
    step: Step
    segment: tuple[str, int]  # the conversation, and how many of its compactions came before


def steps_from_messages(messages: list[ChatMessage]) -> Iterator[ReplayStep]: ...
```

The `Context` is the sample's and constant, so the runner holds it rather than each step (revised 2026-10-19). `ReplayStep` is sentinel's; inspect_ai's `steps_from_events()` builds it, as the live dispatcher builds sentinel's step types.

### From events

An eval log's events restore what messages lose. `ModelEvent` carries `input`, `tools`, `tool_choice`, `config` and `output` — `BeforeGenerate` and `AfterGenerate` field for field. `ToolEvent` carries `function`, `arguments`, `view`, `result` and `truncated` (the output's size and the limit it was cut to), which restores `view` and lets `result` be exactly what the model saw. It gives `AfterToolCall.truncated` as the live host set it: `Truncation(*event.truncated)` when set, and `False` when absent in a log new enough to record it, that is, one whose `eval.packages["inspect_ai"]` is 0.3.31 or later (`max_tool_output`, inspect_ai #478, which added the field); in an older log, `None`. At the tool stages the producing `ModelEvent` gives `input` and `tools`, the same lookup the live dispatcher makes. The one thing an eval log does not hold is the untruncated tool `output`, so `AfterToolCall.output` stays optional in replay too.

Events also restore `input` exactly, from `ModelEvent.input`, and let `history`, the as-sent view of an agent's run (AISI R10), be rebuilt per agent; it is not `agent_messages`, the conversation as the agent ran it, which is built from the same events ([Reconstructing `agent_messages` in replay](#reconstructing-agent_messages-in-replay)). Live, inspect_ai folds each agent turn's input in as the call is made and writes nothing to the log (built 2026-10-14; `sentinel.md`, "The history as sent"). Replay runs the same fold, the same `_Sent.record()`, over the inputs of the conversation's `ModelEvent`s whose `origin` is `"agent"`, up to the step's cut ([One builder for live and replay](#one-builder-for-live-and-replay)). What the fold needs that a log lacked is which model calls were the instance's agent turns; [What the log records](#what-the-log-records) adds it, and the instance comes from the span tree. Transcripts without it get their turns from the timeline ([Transcripts without recorded origins](#transcripts-without-recorded-origins)). `CompactionEvent`s are not needed for the fold, since a message stays in the list once sent; they mark where a conversation's input stopped extending its previous input, which is where replay splits units.

`steps_from_events()` is an *enrichment* of the messages reconstruction rather than a second algorithm: it walks the same steps, in the order the log records them, and attaches the matching event's fields where one exists. That keeps step identity (below) independent of whether events were available, which is what lets one validation set serve both kinds of source. One thing differs: which steps exist. From events, a step exists only where it ran, or would have run under a sentinel ([One builder for live and replay](#one-builder-for-live-and-replay), "Which steps ran"); from messages, every assistant message and tool result projects one.

### Reconstructing `agent_messages` in replay

*Rewritten 2026-10-20.* The maintainer redefined `step.agent_messages` as **the conversation as the agent ran it**, recorded by inspect_ai and the same at all four stages, in place of the scaffold's list at the step, because AISI's folding scaffolds made that list at `AfterGenerate` the folded input. The inspect_ai change is inspect_ai PR #5986 (branch `dragonstyle/sentinel-agent-messages-as-ran`). Sentinel's side, the definition in `_step.py`, `sentinel.md` ("Two histories"), `sentinel-reference.md` and the docs, lands in its own sentinel docs PR, which CASE writes separately and which this PR does not change ([What this asks of the other documents](#what-this-asks-of-the-other-documents)). This section says how replay fills it.

Live, inspect_ai keeps one record per conversation: the input of its first agent turn, as sent; then, as they happen, each agent turn's output as it took effect and the tool messages `execute_tools()` returned. A step reads the record as it stands. Later user messages (`react`'s continue nudges, a person's messages) are not in it; they are in `history` once sent. Neither are the results of tools run outside `execute_tools()`.

Replay's builder fills it from the log in its single pass ([Nothing quadratic](#nothing-quadratic)), changing the record at the three moments live changes it, not in event order. *Revised 2026-10-20 after review pass 1: the first version appended in event order and cut at the step, which shows a step its own output or result before live does.* Inspect PR #5986 fixes the moments (`Model.generate`, `execute_tools`) and pins them in its tests:

1. **Opening.** The input of the conversation's first agent-turn generate, before that turn's `BeforeGenerate` step: live opens the record before `sentinel_before_generate()`. Message ids in it are the pool's.
2. **An output.** Each agent-turn generate's output message joins once that generate's `AfterGenerate` step is past, so that step does not see its own output and every later step does: live records it after `sentinel_after_generate()` returns, and whether or not `AfterGenerate` was watched. Only the output of the generate's last attempt counts, and only when it records no `error`: a failed attempt keeps its event with a pre-filled empty output, which live never records (review pass 2, F1).
3. **A batch's results.** The tool messages one `execute_tools()` call returned join together, in the calls' declared order, after every tool stage of the batch and before the conversation's next agent turn, so no tool step sees its own result or another result from its batch: live appends `result.messages` once `_execute_tools_impl()` returns, in declared order whatever the completion order. Each message is the one with `ToolEvent.message_id`, from a later input or `sample.messages`, else rebuilt from the `ToolEvent` (`id`, `function`, `result`, `error`). *Revised after review pass 2 (F11):* a batch is what one `execute_tools()` call ran in the conversation: the `ToolEvent`s of one assistant message's calls, in consecutive `tool` spans of the conversation with no agent turn between them, whether a model produced that message or the scaffold built it; live appends whenever `execute_tools()` returns under an agent turn's scope, to the caller's conversation record if it is open. A scaffold that runs one message's calls in more than one `execute_tools()` call is replayed as one batch, which differs from live only for the tool steps between those calls.

It needs PR 1's `origin` to know the agent turns and the span tree to know the conversation; where `origin` is unset, the timeline's turns stand in ([Transcripts without recorded origins](#transcripts-without-recorded-origins)). Four cases follow the live code, and PR 3's live-equals-replay test covers each:

- **An output the agent never received** adds nothing: an event with no choices, or one whose `config.fail_on_refusal` is set and whose output stopped with `content_filter`, which raised `ModelRefusalError` instead of returning.
- **A batch that raised** appends nothing, since live never reaches the append. *Revised after review pass 2 (F3):* a batch raised when one of its stages re-raised, which the log shows as a `ToolEvent` recording `failed`, a `ToolEvent` left pending (no `completed`, as a `ValueError` escaping `call_tool_task` leaves it), or a sample that ended in the batch (a review policy's or a review cancellation's `TerminateSampleError`); a scaffold that catches the error and continues is covered by the first two.
- **A handoff** returns its sub-agent's conversation beside its tool message. Replay takes those messages by id from the next agent turn's input or from `sample.messages`; where neither holds them, the steps after the handoff get `None` rather than a list without them.
- **An `AfterGenerate` `modify`**, once built, changes the output that takes effect. The log must then record the output as it took effect, or replay gives the model's; the generate stages' part 2 decides it.

*Earlier, 2026-10-13 to 2026-10-19:* `agent_messages` was the scaffold's list at the step, which a log holds only at the end of the sample. Replay was to cross-check `sample.messages` against the conversation's outputs and tool results and give a verified prefix for the sample's top-level agent, else `None`; a recorded fingerprint was declined in R7-D2 as quadratic. The new definition makes both unnecessary.

### Human decisions in replay

Decided 2026-10-14 (AISI R4); not built. A replayed step's `human_decisions` holds what the live step held: the decisions a person made through `human()` at earlier steps of the conversation. Replay reads them from the log rather than making them, which is the only way, since a replay cannot ask the person: for each step, the `SentinelEvent`s with `factory == "inspect_sentinel/human"`, `kind == "decision"`, `status == "reported"` and the step's `conversation`, from steps whose `sentinel` span ended before the `sentinel` span of the step itself began, in event order (live, the host publishes a step's decisions as its span ends, and snapshots the list when it builds a step, before its span begins), less each one withdrawn by a `superseded` event at its own step: one with the person's action at the person's `path` or the path of a layer above it, the rule `supersedes()` applies live. A `terminate` that a sibling's `decide_final()` outran is recorded `reported` and then `superseded`, possibly as a copy a composition passed up, at a layer above the person. Both events fall inside the step's span, so a later step sees the same result live and in replay, including a parallel step that began while that span was open. Each becomes an `HumanDecision`: `stage` and `step_id` from the event; `decided` a `Reported[Decision]` rebuilt from `path` (its last segment the name), `function`, `action`, `explanation`, `message`, `modified`, `references` and `metadata`; `call_ids` the step id at a tool stage, and at `model_output` the tool calls of that generate's output (its last attempt's `ModelEvent`; in a log from before R7-D8, the assistant message with that id, from its `ModelEvent` output or `sample.messages`). Because the records are what was decided live, segments replayed concurrently each see the same list.

A log from before Sentinel records a person's approval as an `ApprovalEvent`; replay could map one from a human approver to the same record (stage `tool_call`, step id the call id, `approve` to `proceed`), but this is not planned; until then such a log gives `None`, since replay cannot tell whether a person decided anything. *Revised 2026-10-19 for AISI's R7: planned, in [Transcripts without recorded origins](#transcripts-without-recorded-origins).*

The log driver applies these rules with the same functions the live host uses: it rebuilds each `Reported[Decision]` from the event and calls sentinel's `kept_human_decision()` and `supersedes()` (`_human_decisions.py`), as inspect_ai's `_Recorder` does live, and publishes a step's kept decisions at its span's end with the shared `_publish`, so a field added to `HumanDecision` changes both paths at once.

### Transcripts without recorded origins

Older Inspect logs, written before PR 1, and every transcript Scout imports from another framework. Decided 2026-10-19 (R7-D4); planned as PR 6. AISI's R7 names the first; the second is most of what a Scout database holds. Everything a tool or generate step reads from `ModelEvent`, `ToolEvent` and messages is as exact in an older Inspect log as in a new one (the fidelity table's middle column). Two things differ: which calls are turns, and, in logs from before Sentinel, where a person's earlier decisions come from.

**Conversation.** From the span tree, as for new logs, so the replay loads span events (`as_scanner()` asks Scout for `span_begin` and `span_end`). Scout's Claude Code and ATIF importers put sub-agents in agent spans. LangSmith's types every chain as an agent, so its transcripts split into more conversations than the agent had; continuity does not join conversations across spans, and the importer tests in PR 6 measure the effect.

**Agent turns** come from the timeline: `timeline_build`'s existing rules (`event/_timeline.py`: `_wrap_utility_events` treats a call that makes no tool calls and has a different system prompt from the span's first tool-calling call, or a one-token warm-up call, as utility; `_classify_utility_agents` does the same for a single-turn child span with a different prompt under a parent that runs a tool loop), and a continuity rule added for these transcripts. Continuity is an offline form of the agent bridge's own thread tracking (`AgentBridge._track_state`, `agent/_bridge/types.py`), which tells a bridged CLI's turns from its side calls live:

- Within an agent span, in order, keep the thread's tip: the last turn's input and output. A call whose input continues the tip, with the tip's output at position `len(tip.input)`, is on the thread.
- A call that continues nothing is a candidate; if the next call continues it, the thread moves to it, which is how the bridge follows a compaction it cannot see. A `CompactionEvent` resets the tip directly where one exists (Inspect, Claude Code, ATIF).
- Two calls that continue one tip are a fork: the one whose output is carried on is the turn, and the dead end is utility.
- A call followed in its span by a `CompactionEvent` before any call continues it is utility. *Revised 2026-10-20 after review pass 2 (F8):* Inspect's compaction summary call continues the tip (its input is `system + input + conversation + [prompt]`, `model/_compaction/summary.py`) and is the only call that does, since the next turn's input is the compacted list, and the `CompactionEvent` is written after it (`_compaction.py`), so the fork rule alone would make it a turn. The prompt rules miss it too, since it uses the agent's own system prompt.
- Messages are matched by role and a hash of their text, as the bridge matches them, since ids do not survive a scaffold's round trip; Scout's `_trim_prefix` (`_transcript/messages.py`) matches the same way after trying ids.
- A span in which no call continues another keeps the existing rules' answer, so a scaffold that rebuilds its prompt every turn does not lose every turn. A fork at the end of a span, with nothing after it, goes to the call whose output is in the span's final messages, else the later call.
- Each call is compared at one position, not along its whole prefix, and fingerprints come from the message pool, each stored message hashed once ([Nothing quadratic](#nothing-quadratic)).

Continuity lands in `timeline_build` and its TypeScript port together, so the viewer and Scout gain it too. It is not applied where `origin` is recorded, since a scaffold that drops a turn's output would make it disagree with live. A source that knows its structure supplies a stored timeline, as Petri does with `"target"`, which `as_scanner(timeline="target")` reads, or its importer sets `origin`. Each result records how its turns were established (`"turns"`: `"recorded"`, `"inferred"` or `"stored"`). PR 6 measures the inferred turns against new Inspect logs with `origin` removed, and on sample transcripts from each importer, and states both in the PR.

**Earlier decisions.** When the eval ran no sentinel (`eval.config.sentinel` unset), each `ApprovalEvent` from a person becomes a `HumanDecision`, published once its tool call's step settles, as live: stage `tool_call`, `step_id` and `call_ids` the call's id, `decided` a `Reported[Decision]` with the approver's name as its `name` and `path`, `approve` as `proceed` with the explanation, `reject` as `reject` with it as `message` and `explanation`, `terminate` as `terminate`, and `modify` as `modify` with the `modified` call. An `escalate` is passed on, not decided, and is skipped. Which approvers are people is a parameter, `human_approvers=("human",)`, the registry name inspect_ai's `human_approver` records (`approval/_call.py`, `record_approval`); a team with its own approval UI (AISI R9) names theirs. A person who decides through approval always leaves an `ApprovalEvent`, so a log without one gives `()`, not `None`. A log from an eval that ran a sentinel gets `human_decisions` from its `SentinelEvent`s only, as live, where approval's decisions were never in it.

### What replay cannot do

Replay reproduces the monitor's *reports*, not its *effects*. A `reject` in replay does not change the transcript; the agent already did what it did. This is the right limitation for measuring a classifier — precision and recall are about reports — but it means two things cannot be back-tested offline:

- **Interventions.** Whether rejecting call 7 would have led the agent somewhere better is a question for a live eval, not a replay.
- **Humans.** `human()`, a protocol with no children, cannot be replayed. The useful substitute is to *replay the recorded human decision* when the transcript carries a `SentinelEvent` from that `human()` instance for that step, so a `sequential` can be back-tested against the answers a person actually gave. The replay host does this in `ask_human()`: it reads the asking instance's path from the runner's layer state and answers with that instance's recorded decision at the step (`approve` for a `proceed`). Where there is none, the scan's `human=` policy answers: by default the fail-closed answer a host gives when no person can be asked, or a stand-in for the person; each result says which (decision R7-D5). A log from an eval that ran no sentinel has no `human()` instances; a person's `ApprovalEvent` for a call answers a `human()` at that call's `tool_call` stage, and reaches later steps as `human_decisions`.

## Step ids

Per-step validation needs each step to have an id that exists in a messages-only transcript, in an events transcript, and **live, at the moment the monitor runs** — so that a label made once serves replay and also the read mode over recorded events. Message and tool-call ids satisfy that. Event uuids do not: a `BeforeGenerate` monitor runs before its `ModelEvent` exists.

| Stage | Step id |
|------------------------|------------------------|
| `BeforeGenerate` | the generate's id: the `uuid` of its first `ModelEvent`, minted before the sentinel runs (R7-D8 and R7-D8a, decided 2026-10-20) |
| `AfterGenerate` | the same generate's id (R7-D8b); until R7-D8b is decided, the id of the assistant message produced |
| `BeforeToolCall` | the tool call id |
| `AfterToolCall` | the tool call id |

*Until 2026-10-20* `BeforeGenerate`'s id was the last input message's, with an ordinal suffix on repeat (`{message_id}:2`) for a rejected call regenerated behind the same last message, counted per transcript. The generate's own id needs no ordinal: each `Model.generate()` call mints its own, so a regenerate gets a new one, and nothing counts in an order concurrency could change. Within one monitor's stage, ids are unique per transcript; a `BeforeToolCall` monitor and an `AfterToolCall` monitor both key by tool call id, but validation sets are per scanner so there is no collision.

**Consequence for `sentinel.md`:** `SentinelEvent` gains `step_id: str`, recorded by the runner live, so the read-mode scanner emits results with the same step ids the replay scanner does. *Built: `SentinelEvent.step_id` at all four stages (inspect_ai `_dispatch.py`, `_step_id`).*

**Computing them in replay** (revised 2026-10-20). Replay reads a generate's id from the `uuid` of its first `ModelEvent`. Logs written before R7-D8 used message-based ids live (Charles: "many old logs will not have this field, of course", said of the field then proposed), and a step id only has to equal live where a live record exists to join against: `SentinelEvent`s, `HumanDecision`s and labels. For such a log, a generate's step id is, in order:

1. **The recorded `SentinelEvent.step_id`**, wherever the step's `sentinel` span holds events. Logs from sentinel 0.1.x runs record the live ids in the old format (the last input message's id, with `:N` on a repeat), so read mode, `HumanDecision`s and labels still join.
2. **The `uuid` of the generate's first `ModelEvent` attempt**, as for a new log. Events have carried a unique id since inspect_ai #2097 (2025-07-05; `uuid` today). Attempts are grouped by inference, as for a new log.
3. **The generate's position within its conversation, in log order**, for logs from before event ids: deterministic, but not proof against concurrency, since two agents sharing a conversation number their calls in scheduling order.

Sources 1 and 2 match live where a live record exists; source 3 may not, for logs from before 2025-07. A log from an eval without a sentinel has nothing live to match, so its generate ids need only be deterministic and unique within the transcript, which sources 2 and 3 are.

## The scan unit and the validation unit

Three grains of label are in play, and they do not need three scan units:

| Grain | The label answers | Keyed by |
|------------------------|------------------------|------------------------|
| step | did this tool call or generate deserve a flag | transcript id and step id; the step's message or event |
| transcript | did this trajectory contain an attack | transcript id |
| protocol | did the configuration reach the right decision at this step | as a step; the result is the outermost layer's |

Five ways of getting the step grain into Scout were considered:

- **A `Step` scanner input type.** First-class, and the view could render it natively. But `sentinel.md` says monitors should be incremental, so nearly every real monitor is stateful across steps and needs its transcript's steps *in order with one store*. Scout's input model does not promise sequential in-order invocation within a transcript, so the new type would also need a new ordering guarantee. It buys less than it looks.
- **Scanning individual messages or model events** (Scout's `Scanner[ChatMessage]` and `Scanner[ModelEvent]`), considered 2026-10-20. Scout validates and shows these per item today. But it calls the scanner once per item with only that item, and a step is not a function of one item: `history` is folded from the conversation's earlier agent turns, `human_decisions` comes from earlier `SentinelEvent`s, a tool step joins a `ToolEvent` with its producing `ModelEvent`, turns without `origin` need the timeline, step ids count across the sample, and a stateful monitor needs its steps in order with one store. Rebuilding that context per item would be quadratic and still differ from live.
- **A `Sequence[Step]` input per transcript.** Preserves order, but the ids on a sequence input are the whole list, so validation cannot address one step.
- **A resultset per transcript, each result citing its step.** Chosen for R7, 2026-10-20. No change to Scout's rows: Scout records a list of results as one resultset row, its dataframe expands that into a row per result (`scan_results_df(rows="results")`, `_expand_resultset_rows` in `_scanresults.py`), and Scout View renders citations as links. What it does not give is Scout's validation at the step grain: a case matches a row's input ids, which for a resultset are the transcript's, and label validation is presence or absence per label, so "step 7 was flagged and should not have been" is not expressible.
- **Keep the transcript as the scan unit; make each result its own row.** Chosen on 2026-10-19 as `Result.subject`; deferred 2026-10-20 ([One row per message or event](#deferred-one-row-per-message-or-event)).

### The chosen shape

The adapter is a `Scanner[Transcript]`. It builds the steps in one pass, runs them in units ([Cost and parallelism](#cost-and-parallelism)), in order within a unit with the unit's own store, and returns one `Result` per eligible step, as a list. Each result's metadata holds the step id and stage, and its `references` cite the step's message or event first, then whatever the report cites:

| Stage | The step cites |
|---|---|
| `BeforeGenerate` | its `ModelEvent` (`event`) where the transcript has events; else the last input message |
| `AfterGenerate` | the assistant message produced (`message`) |
| `BeforeToolCall`, `AfterToolCall` | the call's tool result message (`message`), which exists with or without events; Scout has no reference kind for a tool call |

``` python
as_scanner(monitor, unit="step")        # one Result per step, in the transcript's resultset
as_scanner(monitor, unit="transcript")  # one Result; transcript id, as today
```

State stays where `sentinel.md` already puts it; Scout's parallelism across transcripts is untouched; and the transcript-grain form is the same adapter reducing to one result by max suspicion or strongest decision, with `references` to the flagged steps. A transcript's results come back together from one scanner call, so a resumed scan never holds half a transcript.

One rule keeps the rows unambiguous: **step ids are unique within one scanner's results for one transcript.** The adapter emits one result per step for the monitor being scanned; a protocol's child reports go in that result's metadata. To scan a leaf inside a protocol, wrap the leaf directly. A tool call's two steps share its id, so an instance watching more than one stage is scanned one stage at a time: `as_scanner(..., stage="tool_result")`, required when the instance watches several stages and defaulting to its only one otherwise.

**Labels without Scout changes.** Per-step labels are a table keyed by transcript id and step id, with an optional split; the results dataframe joins it on the same keys. `steps_in(labels)` builds the `steps=` predicate from the table ([Mapping `Report` to `Result`](#mapping-report-to-result)), and `calibrate(target_recall=)` joins it ([Calibration](#calibration)). Scout's own validation metrics and its case editor at the step grain wait on the deferred rows below.

### What Scout changes (PR 4)

One thing: a scanner can ask for model events condensed, with `input_refs` and the message pool rather than each input expanded, so each pooled message is decoded once. Replay needs it to stay linear ([Nothing quadratic](#nothing-quadratic)).

### Deferred: one row per message or event

Decided 2026-10-20 by the maintainer, splitting the first PR 4. The first design gave `Result` an untyped `subject`, the step id, and recorded each subject-bearing result as its own row with `input_ids` `[transcript_id, subject]`. Two things were wrong with it. A step id is not something a user can find in a transcript, so no label could be written except from a results row. And Scout can already validate a message or an event: a message or event scanner's row has the message id or event uuid as its input id (`get_input_type_and_ids`, `_scanner/util.py`), and `_validate_scan` (`_scan.py`) matches a case against it; what is missing is only that a result's id is always the id of what the scanner was called on.

So the later change is smaller: **a transcript scanner's results may each name the message or event they are about**, using the input kinds Scout already has. Each is recorded as its own row with that id and kind, and Scout validates and shows it exactly as it does a message or event scanner's row: matching, predicates, splits, metrics and the `validation_*` columns do not change, and no `[transcript, step]` pair is needed, since message ids and event uuids are unique across a corpus. A label made by clicking a message or event in the transcript then matches with no sentinel knowledge. The stages map as the table in [The chosen shape](#the-chosen-shape) does; a `BeforeGenerate` step in a transcript of messages only cannot be labelled at that stage. One existing limit carries over: `Transcripts.for_validation()` selects transcripts by `sample_id`, so a set of message or event ids selects none, as is already true for message scanners.

It is deferred because only validation and labelling inside Scout at the step grain need it, and R7 does not; a pandas join over the resultset covers the development loop meanwhile.

`"sentinel"` is already in Scout's `EventType` (`_transcript/types.py`), so a scanner can ask for these events; the earlier note that Scout must add it is done.

## Mapping `Report` to `Result`

| Report | `value` | `answer` | `metadata` | `label` |
|------------------------|------------------------|------------------------|------------------------|------------------------|
| `Observation` | `suspicion` — float or dict | — | step id, stage, monitor metadata | instance path |
| `Decision` | flagged: `action` in `reject`, `modify`, `terminate` | `action` | step id, stage, `audit`, `modified`, child reports | instance path |
| abstained | `None` | `None` | step id, stage | instance path |
| failed (a monitor raised) | the transcript's scan raises: no row, the transcript's result is an error | | | |

Every result's `references` cite the step's message or event first ([The chosen shape](#the-chosen-shape)). Three things the table encodes:

- **A dict suspicion is kept whole**, so per-dimension metrics come from the dataframe, and from Scout's existing dict-target validation once rows are per item.
- **The boolean flagged value is what makes binary labels work.** A per-step label set will label steps the monitor abstained on, and abstention produces no report. The adapter emits a result for every step at the monitor's stage, `None` on abstain, and a label of `false` compares equal to "not flagged" only if the value is boolean. Teaching the `eq` predicate that `None` is negative was the alternative; mapping to a boolean keeps the predicate honest and leaves the action in `answer` for anyone sweeping on it.
- **`escalate` is not flagged.** It is "I decline to decide", not a verdict. Inside a `sequential` it also means "worth a person's look", which a reviewer might want to count; `answer` carries it for that. This is a default that is cheap to get wrong, and it is recorded as a decision rather than left implicit.

The `explanation` and the rest of `references` map directly from the report's own fields — an LLM monitor using Scout's `message_numbering` in its prompt gets cites for free.

**`unit="transcript"`** (settled 2026-10-19, answering open question 3) reduces the step results to one: for a monitor, the maximum suspicion, per dimension when it is a dict; for a protocol, the root's strongest decision across the steps (`terminate`, then `reject`, `modify`, `escalate`, `proceed`); `references` the steps that set it. Taking the root's decision is what a protocol result already means at the step grain ("the result is the outermost layer's").

**Replaying a chosen subset of steps.** `as_scanner(..., steps=...)` takes a predicate over `ReplayStep`, and `steps_in(labels)` builds one from a label table's transcript and step ids. The pass still builds every step, which costs no inference; the runner invokes the sentinel only for the chosen ones, so a unit's store sees only those. With R10 a monitor that needs the earlier conversation reads `history`, so AISI's subset is "only run these steps", as their follow-up said.

## Two modes: replay and read

Both key results by transcript and step id and cite the same message or event, so their rows join.

| Mode | What runs | When |
|------------------------|------------------------|------------------------|
| **replay** | reconstruct steps, run the monitor, one result per step | you changed the prompt, the model, or the monitor's logic |
| **read** | walk the transcript's recorded `SentinelEvent`s, one result per event | you want to know how the monitor behaved in the run it was attached to |

Read mode costs no inference and is what makes "run the eval observe-only, then look" a real workflow rather than a slogan. It is also the only mode that sees what the protocol actually did with each report, from the decision events at the parent paths, so "how often did `resample` substitute a draw" is a read-mode query. Scout's `EventType` literal gains `"sentinel"` so the transcript loader can filter for these events.

Read mode also gives the honest check on replay itself: replay the monitor over a log it was attached to, and the two modes should agree wherever the monitor is deterministic. Where they do not, the reconstruction is wrong, and that is a test worth shipping.

**The read-mode scanner** (designed 2026-10-19, PR 5): `as_reader(path, *, stage=None)` in `inspect_sentinel.scout`, a transcript scanner asking Scout only for `sentinel` events. For the instance at `path` it emits one result per `SentinelEvent` with status `reported` (and `superseded` for a decision, with the status in metadata), carrying the event's `step_id` and citing the step's message or event, mapped as [Mapping `Report` to `Result`](#mapping-report-to-result) maps a live report. An `error` event is a failed monitor, and the scan raises as replay does. A step the instance watched but did not report on (it abstained) has no event; the reader emits nothing for it, and the agreement test below compares only steps both modes report.

**The agreement test** (PR 5). A probe monitor, `fidelity_probe()` in `inspect_sentinel.scout`, watches all four stages and reports `suspicion` `0.0` with metadata holding a digest of every field of the step it was handed: per field, a hash of its JSON form, with the fields replay leaves absent (the list the live-equals-replay test names) left out. A test runs a set of scripted mockllm evals with the probe attached, then scans the logs through Scout, at each stage once with `as_scanner(probe(), stage=...)` and once with `as_reader("probe", stage=...)`, and asserts that both report the same set of `[transcript, step]` keys, which the probe allows since it never abstains, except a `BeforeGenerate` that left no `ModelEvent`, which read mode has and replay does not (R7-D11), and that for every key the metadata is equal. *Revised 2026-10-20 after review pass 1:* the probe also digests `context.eval` (task, sample id with its type, epoch, descriptions, input and metadata), and the evals include an integer sample id, a numeric string id, a sample description and a message-list input, so a context replay gets wrong fails the test too. The live-equals-replay test in inspect_ai compares the steps themselves; this one checks the whole path a user takes, through Scout's loading, the units, the replay host and the resultset. *Revised 2026-10-20 by the maintainer: the probe is public.* It is the check AISI's R7 asks for ("the monitor behaves identically and receives identical context whether it is in live or backtesting mode"), and only a user's own scaffold and logs can show it holds there: attach `fidelity_probe()` to an eval observe-only, scan its logs with `as_scanner(fidelity_probe(), stage=...)` and `as_reader(...)`, and compare. Any deterministic monitor can be compared the same way, but only the probe compares the context itself. Its digests of `history` and `agent_messages` are by length and last message ([Nothing quadratic](#nothing-quadratic)), so it checks the tip, not the interior: a scaffold that edits a sent message in place differs from replay in the interior, which the probe cannot see and PR 3's whole-list comparison can. *Review pass 2 (F7) suggested a rolling hash extended per appended message; it would not see this either, since the hash is taken when a message is appended and the edit comes after, and rehashing every list at every step is quadratic, so the probe's limit is stated instead.*

## The workflow

1. **Write** the monitor as `sentinel.md` describes. Its unit tests use `replay_monitor()` from `inspect_sentinel` over a handful of message lists — no Scout, no eval.
2. **Replay** it over a corpus with `as_scanner()` and look at what it flags in Scout View.
3. **Label** steps from the results dataframe, where each step is a row citing its message or event, as a label table with `dev` and `test` splits. Labelling in Scout's case editor waits on per-item rows (deferred, [The scan unit and the validation unit](#the-scan-unit-and-the-validation-unit)).
4. **Validate**: precision, recall, F1, balanced accuracy over the `dev` split. Change the prompt; bump the monitor's version; re-scan; compare. A join of the label table and the results until per-item rows exist; Scout's existing loop after.
5. **Calibrate** thresholds (below) if the monitor is an `Observation`.
6. **Configure** the protocol with those thresholds and attach it to the eval — observe-only first.
7. **Read** the resulting logs in read mode to confirm the deployed behaviour matches the replayed one, then let it act.

Steps 2–4 are exactly what a scanner author does today. The monitor-specific parts are the adapter in step 2 and calibration in step 5.

## Calibration

`sentinel.md` insists thresholds live in protocols, not monitors, because a threshold needs a benign score distribution and a monitor looking at one step has never seen one. This is where the distribution comes from.

**From a benign corpus.** Replay an `Observation` monitor over transcripts known to be benign. The results dataframe's `value` column *is* the benign distribution. A budget becomes a threshold by percentile: "audit the top 1%" is the 99th percentile of that column, per dimension when suspicion is structured.

**From a labelled corpus.** Replay over a corpus with numeric or boolean step labels. Scout's `gte` predicate against a numeric target is a threshold; sweeping it gives the precision–recall curve, and the operating point is a choice the author makes with the curve in front of them rather than a constant in a prompt.

A helper closes the loop:

``` python
thresholds = calibrate(results, budget=0.01)          # percentile per dimension
thresholds = calibrate(results, target_recall=0.95)   # from labels
Task(sentinel=threshold(suspicion_monitor(), reject_at=thresholds["sabotage"]))
```

It is ordinary pandas over a Scout results dataframe. It lives in inspect_sentinel, as one of the development loop's verbs, and uses Scout for the scanning (workstream 10, reframed by the maintainer on 2026-10-02). What matters more than the helper is that the *inputs* to it — recorded scores, including ones a protocol ignored — are produced by the runner as a matter of course, which is why `sentinel.md` records them.

The calibration corpus should be held out from the validation set's `test` split, and a threshold derived from one model's scores is not a threshold for another model's; both are ordinary ML hygiene rather than framework concerns, but the docs should say them. `calibrate()` does not refuse a split used for validation: split names are free-form, so it cannot tell which split a later evaluation reports on (open question 7, 2026-10-20).

## Monitors as scores

`sentinel.md`'s open question 11 asks whether a monitor can produce a `Score` beside the task's own scores. It can, without touching scoring:

``` python
Task(scorer=[my_task_scorer(), as_scorer(as_scanner(suspicion_monitor(), unit="transcript"))])
```

`as_scorer()` already turns a transcript scanner into an Inspect scorer. The transcript-grain adapter reduces the monitor's per-step reports to one value, so the monitor's suspicion appears in the log as a score with the usual metrics, and the flagged steps travel as `scanner_references` in the score metadata, which Inspect View already renders. Nothing in `inspect_ai.scorer` changes.

## Cost and parallelism

An LLM monitor over a corpus is one inference call per eligible step, which is many more calls than one per transcript. What keeps it tolerable:

- **Incremental monitors are cheaper to replay**, not just to run — the design's insistence on classifying the newest turn and folding into state means replay cost is linear in steps rather than quadratic, and the adapter's per-unit store is what makes that work.
- **Stage filtering happens before loading.** The adapter declares the content it needs from the stage it scans: messages, and the event types the log driver reads (`model`, `tool`, `compaction`, `approval`, `sentinel`, and `span_begin` and `span_end` for the cut and the conversation), so Scout loads nothing else.
- **Parallelism is across transcripts**, as for any transcript scanner (Scout's `max_transcripts`, default 25, also the default `max_connections`), **and across units within a transcript.**

**Units** (designed 2026-10-19; AISI describes their current implementation in R7). After the step pass, the runner groups a transcript's steps into units, runs units concurrently in an anyio task group, and runs the steps of a unit in order, each unit with its own `Store`, recorder and replay host. `as_scanner(split=...)` chooses the unit:

| `split` | Unit | Store | For |
|---|---|---|---|
| `"compaction"` (default) | a conversation's steps between two of its compactions (the `segment` on `ReplayStep`: the conversation, and how many of its `CompactionEvent`s precede the step) | fresh per unit | monitors without cross-step state, which with R10 includes AISI's |
| `"conversation"` | a conversation's steps | fresh per unit | state kept per agent instance, as [sub-agents.md](sub-agents.md) recommends keying it until `store_as(scope="conversation")` exists |
| `None` | the whole sample, in log order | one, as live | a monitor whose state crosses conversations, which is the live scope |

`max_unit_steps=` splits a unit further into runs of at most that many steps, each starting with a fresh store; the docs say a stateful monitor sees less at each cut. The runner bounds how many units of one transcript run at once (`max_units`, whose default PR 5 sets by measuring), and every monitor call still passes through inspect_ai's per-model connection limit, so a wide transcript queues on the model rather than flooding it.

**Prompt caching.** A unit runs its steps in order so that each step's monitor prompt can extend the previous one's, which is what provider prefix caching rewards. Whether it does is the monitor's prompt: one rendering `step.input` breaks its prefix at a compaction, which is why the default unit ends there; one rendering `step.history`, the as-sent list, which only grows, keeps its prefix across compactions and is cached best with `split="conversation"`. Splitting further trades cache hits for wall-clock time, so it is a knob, not something the framework infers.

**State across a split** (answering open question 8, 2026-10-19). Each unit starts with a fresh store; no seeding from the previous unit, no refusal to split. A monitor cannot declare that it keeps state, so the adapter cannot refuse for it, and seeding a store from a summary is the monitor's business. The docs say what each `split` does to state, and the scan records `split` and `max_unit_steps` in the scanner's parameters, so a result can be read knowing it. With R10 the commonest state, the opening prompts as sent, is in `step.history`.

**Resume.** Scout records and resumes a scan by transcript (`_recorder/recorder.py`, `resume`): a transcript's rows are written together, so an interrupted scan re-runs only transcripts it had not finished, and a long transcript is re-run whole.

Monitor inference in replay is charged to the scan, never to anything resembling an agent limit, which is the replay form of the budget exemption approvers have in an eval.

## Showing replay can be trusted

*Proposed 2026-10-20 at the maintainer's request; PR 7.* PR 3's test shows the steps are rebuilt equal to live on scripted evals, and PR 5's probe shows a monitor is handed the same fields. Neither shows that a production monitor, one that judges with a model, behaves the same on replayed steps as it did live, which is what AISI's R7 asks back-testing to establish ("the monitor behaves identically and receives identical context whether it is in live or backtesting mode"). This step measures it, on haystacks with planted needles and on real runs, and publishes the numbers.

**Monitors.** The shapes in production use, each run observe-only so that its reports are recorded and nothing it decides changes the run:

- a tool-call judge on `Host.score()`, as in `examples/llm_suspicion.py`, with its `StepPreprocessor` windows (`LastTurns`, `NewSinceLastReport`), at `BeforeToolCall`;
- a whole-turn judge at `AfterGenerate`, reading `history`;
- a rule with no model, such as `examples/no_network.py`;
- an incremental monitor that keeps state across steps, such as `examples/trajectory.py`, replayed with `split=None`;
- AISI's sync monitor, if AISI shares it or runs the harness on their side.

**Haystacks.** Scripted agents (mockllm), so a trajectory is the same in every run while the monitors' model is real: ordinary work over 20, 100 and 300 turns, with a summary compaction, parallel tool calls, a sub-agent through `as_tool()`, a provider error retried and a `human()` answer, and one to three needles planted at known steps, each a tool call the policy forbids (sending a file to an outside host, writing outside `/work`, disabling a test). Beside them, real runs: a small set of real agent tasks with the same monitors attached live, where the needles are whatever the agent did, labelled by hand.

**Three measurements**, per monitor and haystack:

1. **The same prompt.** The monitor model's request live (its `ModelEvent` inside the step's `sentinel` span) and in replay (the scan's model events), compared after replacing the nonce, which differs by design (`Host.score()` keeps it in the store, fresh per unit): the share of steps whose request is identical, and each difference traced to a known difference ([How exact replay is](#how-exact-replay-is)) or reported as a bug. This checks "receives identical context" for a real monitor, with no model noise in it.
2. **The same verdict.** Per step, the live and replayed score, and whether each crosses the monitor's threshold. A model's answer varies between calls even at temperature 0, so the noise floor is measured too: the live eval run twice, and the replay run twice. Replay agrees with live as closely as live agrees with itself, or the gap is reported.
3. **The same needles found.** Recall on the planted needles and the false-positive rate on the rest, live and in replay, with confidence intervals, and their difference.

**Trusted means**, stated as PR 7's acceptance: measurement 1 identical outside the known differences; measurement 2's live-against-replay disagreement no larger than the live-against-live floor (a two-sided test at 5%); measurement 3's recall and false-positive rate equal within their intervals. A miss is a replay bug or a new known difference, and is recorded as one.

**Where it runs.** Not in CI, since it calls real models. A script in sentinel (`benchmarks/replay_trust/`), its haystack generator and its labels, and a docs page with the latest results and how to reproduce them; rerun before a release that changes the step builder or replay. Its cost is one model call per monitored step for each of two live runs and two replays: four times the steps, times the monitors that call a model; PR 7 states the count and the spend with its results. The same script runs on a user's own logs, as the public probe does, with their monitors in place of these.

## Open questions

1. **Does `subject` belong on `Result` or on `ResultReport`?** The result is what a scanner author constructs, so it is the natural home; but expansion is a recorder concern, and a subject the recorder then copies into `input_ids` is a small duplication. Result, unless the recorder has a reason. *Answered 2026-10-19: `Result`, with the recorder writing `[transcript_id, subject]` as `input_ids`. Superseded 2026-10-20: `subject` is deferred, and the later form names a message or event ([One row per message or event](#deferred-one-row-per-message-or-event)).*
2. **What does an expanded row's `input` hold?** Parent transcript id plus subject is the proposal; whether the view needs the step's messages materialised for rendering is a viewer question. *Answered 2026-10-19: the transcript, recorded once through pooled dedup, with `[transcript_id, subject]` as `input_ids`. Superseded 2026-10-20 with question 1: R7 records a resultset per transcript.*
3. **Should `unit="transcript"` reduce by max or by strongest?** Max suspicion for observations and strongest decision are the obvious defaults and match `sentinel.md`'s composition rules; a protocol may want the outermost layer's decision instead, which the adapter can take from its own report. *Answered 2026-10-19: maximum suspicion per dimension for a monitor, the root's strongest decision for a protocol ("Mapping `Report` to `Result`").*
4. **Replaying a bridged agent's log.** A `claude_code` or `codex` transcript has no `ToolEvent`s of Inspect's own, so replay is messages-only even from an eval log. That is fine — it is the deployment those monitors face anyway — but the fidelity table should say so. *Answered 2026-10-19: the fidelity table's bridged column. The generate stages replay as live; the tool stages, which inspect_ai does not yet run for bridged agents, come from messages.*
5. **Does replay honour `portable=True`?** The check runs when a monitor's factory is called, before it runs, with no restricted host or runtime guard (`workstreams.md`, workstream 11). *Answered 2026-10-20 by the maintainer: yes, already. Replay builds each monitor through its factory, from Python or from configuration, so a `portable=True` monitor is checked as in an eval, and one built beforehand was checked when it was built. A `portable=False` monitor runs, as it does in an eval; replay does not refuse it, because refusing would not make the result say what a proxy sees: a proxy's steps come from provider traffic and hold less than a log's. Replay limited to what a proxy sees is deferred until the sidecar ships (pr-series.md, Deferred, "Replay as a proxy sees it").*
6. **Step-level labelling in the transcript view.** Results rows suffice for a first version; a "this tool call was bad" gesture on the transcript itself is the natural way to build step sets and needs Scout View work. *Answered 2026-10-20 by the maintainer: deferred with per-item rows. Once a transcript scanner's results can name a message or event, Scout's case editor labels a results row by that id, and clicking a message or event in the transcript gives the same id; a tool call is labelled through its result message. Until then labels are a table ([The scan unit and the validation unit](#the-scan-unit-and-the-validation-unit)).*
7. **Splits and calibration.** Whether `calibrate()` should refuse to read a split that is also used for validation, or merely document the hygiene. *Answered 2026-10-20 by the maintainer: document it. Split names are free-form, so `calibrate()` cannot tell which split a later evaluation reports on, and it does not refuse ("Calibration").*
8. **Sub-section splitting and stateful monitors.** Splitting a compaction segment resets the per-transcript store at each cut. Whether the adapter should refuse to split for a monitor that declares state, seed each sub-section with a summary of the prior one, or simply document the fidelity loss. *Answered 2026-10-19: document it; each unit starts with a fresh store, and `split=None` replays the sample whole with one store, the live scope ("Cost and parallelism").*
