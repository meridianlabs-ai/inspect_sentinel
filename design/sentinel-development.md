# Developing sentinels

How the monitors in a sentinel get built, measured and calibrated before they are trusted to act. The mechanism is Inspect Scout: a monitor becomes a scanner over the steps of a transcript, and Scout's validation sets, metrics and viewer become the monitor's feedback loop.

## Goal

A monitor is a classifier, and nobody should trust a classifier they have not measured. Concretely, the things a monitor author needs to do before configuring one to act:

- run it over a corpus of transcripts and see what it flags
- label a set of steps or trajectories as should-flag / should-not-flag, and get precision, recall and F1 against them
- change the prompt and see whether the numbers moved
- collect the score distribution over known-benign runs, and turn a budget ("audit the top 1%") into a threshold
- check how the monitor actually behaved in an eval it was attached to, without re-running it

Scout already does the first four for *scanners* — validation sets with splits, balanced accuracy, precision, recall and F1, Scout View for labelling, a results dataframe, and scanner versioning to compare prompts — over Inspect logs and over transcripts from other sources. The design problem is therefore small: make a monitor look enough like a scanner that all of that applies, without either package growing a second copy of anything. *Revised 2026-10-20: for R7, a scan gives one result per step in the transcript's resultset, and Scout's validation and labelling at the step grain wait on per-item rows, deferred ([The scan unit and the validation unit](#the-scan-unit-and-the-validation-unit)).*

## The shape

**A monitor is a scanner over steps.** Scout scans a `Transcript` and returns a `Result`; a monitor takes `(Context, Step)` and returns a `Report`. Everything a step needs is already in a transcript, so a transcript can be re-walked into the steps the monitor would have seen and the monitor run against each in order.

``` python
from inspect_scout import scan, scan_results_df, transcripts_from
from inspect_sentinel.scout import as_scanner

status = scan(
    scanners={"suspicion": as_scanner(suspicion_monitor("openai/gpt-4o-mini"))},
    transcripts=transcripts_from("./logs"),
)
steps = scan_results_df(status.location, scanner="suspicion", rows="results")  # one row per step
```

`as_scanner()` accepts a protocol too, so `as_scanner(threshold(...))` back-tests a whole configuration the same way, and the recorded per-layer reports go along with it. It takes the sentinel as `Task(sentinel=)` does, and records it in the configuration form the eval log records (`SentinelConfig`, through sentinel's public `inspect_sentinel.config`: `sentinel_config()` and `sentinel_from_config()`, decided by Charles 2026-10-21), so Scout can write it in the scan spec (`ScannerSpec.params`), resume the scan, and rebuild the scanner in a worker process. (`as_scanner()` was first placed in Scout as `inspect_scout.sentinel`; it moves to sentinel, decided 2026-10-19, decision R7-D3 below.)

Three things fall out of this that the rest of the document works through:

- **Offline replay is a third deployment**, beside the eval and the proxy, and it has a fidelity table like the other two. Reconstruction from a messages-only transcript is *the same projection* the proxy and the bridged agent already use, so one function serves all three.
- **The recorded reports finally have a consumer.** `sentinel.md` records every report, including the ones a protocol ignored, on the argument that they are the benign distribution calibration needs. Scout is where that distribution gets read.
- **Threshold calibration is a scan plus a percentile.** `sentinel.md`'s open question 5 — where a protocol's thresholds come from — has an answer that needs no new machinery.

## Packages

`inspect_sentinel` is its own distribution, to depend only on `inspect_core` once that is extracted (see `inspect-core.md`; today it depends on `inspect_ai`, and on `inspect_scout` for message rendering until that moves into inspect_ai, [pr-series.md](pr-series.md)). The chain is then:

```
inspect_core  ←  inspect_sentinel  ←  inspect_ai  ←  inspect_scout
```

Today `inspect_sentinel` depends on `inspect_ai` (for the wire and event types) and, since sentinel #131, on `inspect_scout` at runtime, because `step_as_str` and `Host.score` render with Scout's `messages_as_str` (`_preprocess.py`, `_score.py`). Sentinel's dependency on Scout has to go before inspect_ai depends on sentinel, or the chain is a cycle. `inspect_ai` imports sentinel lazily and does not declare it; it declares it only once inspect_core is extracted ([workstreams.md](workstreams.md), workstream 1), which is postponed. Until then the Scout adapter in sentinel adds no cycle: sentinel → Scout → `inspect_ai` is a line (R7-D3, decided 2026-10-19). The `scout` extra, `inspect_sentinel[scout]`, now only raises the floor to the Scout release the adapter needs (`inspect-scout>=0.6.1`, the first with `SCANNER_TIMELINE_NEEDED_ATTR`, which `as_scanner(timeline=, depth=)` uses; found by R7 PR 5, sentinel #135). Once `inspect_ai` declares sentinel, the runtime dependency and the adapter would close a cycle (sentinel → Scout → `inspect_ai` → sentinel); the runtime dependency goes when message rendering moves into inspect_ai, and the adapter moves to `inspect_scout.sentinel`. What goes where (revised 2026-10-19 for R7, and 2026-10-26):

| Where | What | Why there |
|------------------------|------------------------|------------------------|
| `inspect_sentinel` | public, in `inspect_sentinel.scout`: `as_scanner()`, `as_reader()`, `replay_check()` and its comparison helper, `@step_selector` and `@human_stand_in`; public elsewhere: `ReplayStep` and `inspect_sentinel.config` (`sentinel_config`, `sentinel_from_config`, `watched_stages`); internal: `steps_from_messages()`, `Context` from a transcript's info, the replay `Host`, and the replay runner (`replay_monitor()`, `ReplayReport`: one sequential pass per transcript, with one store and recorder); `calibrate()` | the replay host and runner are built on the runner's integration contract (`_integration`), so they change in step with it; the development loop's verbs live here ([workstreams.md](workstreams.md), workstream 10) |
| `inspect_ai` | the step builder, shared by the live dispatcher and a log driver, `steps_from_events()`: every step field, the as-sent fold, step ids and earlier `human()` decisions, from live facts or from a log's events | the live builder is here, and one function per field is what keeps live and replay from drifting ([One builder for live and replay](#one-builder-for-live-and-replay)); the event types are not in core today |
| `inspect_scout` | for R7, only `ModelEvent.origin` in its copy of the schema (Scout #730); replay reads Scout's expanded events, and sentinel rebuilds the message pool from them with inspect_ai's `condense_events()`; later, per-message and per-event results from a transcript scanner, and viewer work (deferred 2026-10-20) | does the scanning; owns validation and the view; knows nothing of sentinel |

**The public API is Scout's** (decided by Charles 2026-10-26). A user replays a monitor through Scout: `as_scanner()`, `as_reader()`, `replay_check()`, the `@step_selector` and `@human_stand_in` registrations, `ReplayStep` and the types their signatures need. `replay_monitor()`, `ReplayReport` and `steps_from_messages()`, public in the first plan, are internal. Deferred: a public API for testing a monitor over a hand-written conversation, if monitor authors ask for one, and a direct `steps_from_sample()`.

The middle row is pressure on `inspect-core.md`'s first open question. If `ModelEvent` and `ToolEvent` move down, the events-based reconstruction moves down with them and `inspect_sentinel` can replay an eval log at full fidelity on its own. Nothing in this document requires that; it only gets tidier.

## Replay over logs (R7)

AISI's R7 asks to run the exact same `@monitor` over stored eval logs, each replayed step carrying what the monitor saw live, including after a compaction and in logs from before Sentinel; to match each step's report to the same step live; to score a chosen subset of steps; to parallelise and use provider prompt caching; and to keep live and replay identical as Sentinel changes. The replay halves of R2 (`input`), R3 (`tools`, `truncated`), R4 (`human_decisions`) and R10 (`history`) are part of it. Parked for design on 2026-10-14 with one direction agreed: build on Scout, which already runs scanners concurrently across transcripts, manages model connections, records results, resumes and validates, rather than a standalone `replay()` engine.

The plan, proposed 2026-10-19:

1. **The log records where each model call was made** (`ModelEvent.origin`, one of a small closed set of kinds such as `agent`, `tool`, `compaction` and `environment`), and one shared rule derives agent turns from it; a call's conversation comes from the span tree ([What the log records](#what-the-log-records)). This is what replay needs that a log lacks today, and with it live stops depending on message ids the log cannot keep (R7-D8, decided 2026-10-20). Nothing else is added: where the log does not say, replay infers, and this document states where that differs from live ([How exact replay is](#how-exact-replay-is)). It is inspect_ai PR 1, which also makes `timeline_build` use it, so the viewer, Scout and replay see the same conversations; a bridged agent's event sink can name the span a generate runs under, which live then follows (inspect_ai #6004, decided by Charles 2026-10-21).
2. **One step builder in inspect_ai, two drivers.** The live dispatcher and the log driver gather facts differently and hand them to the same functions; a test runs an eval with a probe that records every step it sees, and asserts that the steps rebuilt from the written log are equal, field by field ([One builder for live and replay](#one-builder-for-live-and-replay)).
3. **Scout scans transcripts; each step is a result in the transcript's resultset.** `as_scanner()` is a transcript scanner returning one `Result` per step, citing the step's message or event and carrying the step id and stage in its metadata. Scout records the list as it records any resultset, and its dataframe gives one row per step, so Scout's row model does not change. Validation and labelling in Scout at the step grain are deferred (revised 2026-10-20; [The scan unit and the validation unit](#the-scan-unit-and-the-validation-unit)).
4. **Each transcript replays as one sequential pass**, its steps in order with one store, the live scope; Scout supplies the parallelism, across transcripts and processes (decided by Charles 2026-10-26; [Cost and parallelism](#cost-and-parallelism)).
5. **Every field has a stated fidelity** for new logs, older logs and bridged agents ([Fidelity in replay](#fidelity-in-replay)). Transcripts that do not record origins, older Inspect logs and every other source Scout imports, get their conversations and turns from the transcript's timeline, with a continuity rule that replay's log driver applies, not the public `timeline_build` (decided by Charles 2026-10-26); logs from before Sentinel get `human_decisions` from `ApprovalEvent`s ([Transcripts without recorded origins](#transcripts-without-recorded-origins)).
6. **Read mode and replay agree**, checked by the same probe, `replay_check()`, end to end through Scout. It ships, with a helper that lists the steps and fields that differ, so a user can run the check on their own scaffold and logs ([Two modes: replay and read](#two-modes-replay-and-read)).
7. **Nothing quadratic** (maintainer, 2026-10-19): replay's work is linear in the log's stored size, and no step copies or rescans the conversation, live or in replay; through Scout, which hands a scanner its events expanded, the entries of the input lists are quadratic in turns, with no extra decoding or copying ([Nothing quadratic](#nothing-quadratic)).
8. **Replay is shown to be trustworthy, not only tested** (maintainer, 2026-10-20): production monitors run live and replayed over haystacks with planted needles and over real runs, comparing their prompts, verdicts and needles found, against the noise between two live runs. It is internal validation, not a user-facing tool (decided by Charles 2026-10-26; [Showing replay can be trusted](#showing-replay-can-be-trusted)).

### Decisions

Settled by this design (2026-10-19), each argued in its section:

- **The conversation comes from the span tree; no conversation field is recorded.** *Revised 2026-10-19.* First settled as `ModelEvent.conversation` and `CompactionEvent.conversation`, because the span tree gives the live answer only if every event's span chain leads to the span `current_agent_span_id()` named, and `SpanRotationScope` moves the current span through a shared cell that tasks spawned earlier also see. Checked by reading `util/_span.py` (inspect_ai 386e0994): the rotation scope only rotates the current span, for the checkpointer's `checkpoint` spans; it never sets the agent span, and each span it opens records as its parent the span current when the scope opened. So the innermost `agent` span reached from an event's `span_id` through `parent_id`, else the sample's uuid, is what `_conversation()` returned. PR 1's tests assert it on every model call, including a sandbox-bridged agent that checkpoints, whose service tasks were spawned before a rotation; a case where it fails brings the field back. A tool step's conversation is its producing `ModelEvent`'s.
- **The step builder lives in inspect_ai**, used by both drivers; the replay host, runner and Scout adapter live in sentinel.
- **Step ids are read or computed in one sequential pass** over the whole sample before any monitor runs, so the order monitors run in cannot change them: a generate's id is the `uuid` of its first `ModelEvent` (R7-D8), and the fallbacks for older logs are computed in that pass ([Step ids](#step-ids)).
- **A failed monitor fails the transcript's scan.** The runner records a raising monitor as failed, as live; `as_scanner()` reading a failed report for a monitor it is validating raises, so the transcript's Scout result is an error, as AGENTS.md's failure policy requires. A protocol that handles `observations.failed` reports its decision as usual.
- **Read mode compares by step id and instance path**, and the agreement test uses a probe monitor whose report is a digest of every step field. *Revised 2026-10-20 by the maintainer: the probe is public, first as `fidelity_probe()`, renamed `replay_check()` by Charles on 2026-10-26.*

**Decisions for the maintainer.** None blocks the rest of the plan: each has a recommendation the PR series assumes, and changing one changes only the PR named. R7-D1 to R7-D7 were decided by the maintainer on 2026-10-19; R7-D6 and R7-D7 follow from the second. R7-D8 to R7-D12 came from review passes 1 and 2 (2026-10-20). - **R7-D2: add the `agent_messages` fingerprint to `SentinelEvent` now?** *Decided by the maintainer 2026-10-19: no, and as a rule, "nothing quadratic" ([Nothing quadratic](#nothing-quadratic)).* Recommended: no. - **R7-D3: `as_scanner()` in `inspect_sentinel.scout` rather than `inspect_scout.sentinel`?** *Decided by the maintainer 2026-10-19: sentinel, while inspect_core is postponed, on the conditions below.* Recommended: sentinel. Alternative: Scout, as first drawn in [Packages](#packages), which makes Scout depend on sentinel's private contract. Affects PRs 2 and 5.

  The dependencies decide where it can stay. Sentinel declares `inspect_ai`, Scout declares `inspect_ai`, and `inspect_ai` imports sentinel lazily without declaring it, so Scout as a sentinel extra is acyclic. The three-package cycle (sentinel → Scout → `inspect_ai` → sentinel) appears only when `inspect_ai` declares sentinel, which waits on inspect_core ([Packages](#packages)). So, decided with it:

  - Scout is an optional extra, `inspect_sentinel[scout]`, as `sidecar` is. *Overtaken by sentinel #131 (2026-10-20):* Scout became a runtime dependency of sentinel, for message rendering, and the extra stays only to raise Scout's floor for the adapter. Sentinel imports Scout lazily, so importing `inspect_sentinel` does not load `inspect_scout`.
  - `inspect_sentinel.scout` imports nothing private from sentinel: it is built on the public replay API, so it can move to Scout unchanged. *Amended by Charles 2026-10-21 (B2):* it reaches inspect_ai only through `inspect_ai._sentinel._integration`, the designated inspect_ai/sentinel seam (`registry_lookup` is to be exported through it; until then that private import is pinned by a test); it reads configurations through sentinel's public `inspect_sentinel.config` (`sentinel_config`, `sentinel_from_config`, `watched_stages`); it keeps its own copies of Scout's `_walk_spans` and `SCANNER_TIMELINE_NEEDED_ATTR`, each with a drift test; and loading a worker's sources is private to it. *Decided by Charles 2026-10-26 (sentinel #135, call 23, option (a)):* with the replay runner internal since that day ([Packages](#packages)), the adapter may import sentinel's internal replay runner (`_replay`, `_from_messages`); those imports are marked and pinned by a test. If the adapter ever moves to Scout, the runner moves with it or becomes public then.
  - When `inspect_ai` comes to declare sentinel, the adapter moves to `inspect_scout.sentinel` in the same change. `inspect_sentinel.scout` cannot stay behind as a re-export, since that import is the cycle.
  - The extra's floor is `inspect-scout>=0.6.1`, the first release with `SCANNER_TIMELINE_NEEDED_ATTR` (R7 PR 5); with PR 4 dropped on 2026-10-26, replay needs no Scout release.
  - `_integration.config_from_sentinel` stays as an alias of `sentinel_config` until inspect_ai imports `inspect_sentinel.config.sentinel_config`, which needs a sentinel release containing PR 5; it is removed in that follow-up (CASE, 2026-10-21; [pr-series.md](pr-series.md), Deferred).
- **R7-D4: where do conversations and agent turns come from in a transcript that does not record them?** *Decided by the maintainer 2026-10-19: from the transcript's timeline, improved for every reader rather than for replay alone.* First recommended the same day: `history` `None` for logs written before PR 1, with an opt-in inference flag. Revised because the case is common, not legacy: no source Scout imports (Claude Code, ATIF, LangSmith, Logfire, Phoenix, Weave) marks which model calls are the agent's own, so `None` by default would leave most of what people scan without a `history` or a correct set of generate steps. Settled with it, the same day:

  - **One definition, shared.** A conversation is an agent span of the transcript's timeline (inspect_ai `timeline_build`), and its agent turns are that span's own model calls that are not utility. The viewer, Scout's timeline scanners (`llm_scanner(timeline=, depth=, compaction=)`) and replay all read it, so improvements land in `timeline_build` and its TypeScript port, not in a replay-only classifier. *Narrowed by Charles 2026-10-26 (inspect_ai #6098, Ransom's B2, option (b)):* the continuity rule runs only in replay's log driver for now, since Scout's streaming scan builds its timeline from stub events that lack what continuity reads, so applying it in the public `timeline_build` would make Scout's streaming and materialized scans disagree. The recorded `origin` reaches every reader as planned.
  - **Facts, not a verdict.** The log records where each call was made (`ModelEvent.origin`), and one rule says which origins are turns, live and offline. A recorded `agent_turn` was considered and dropped: it would freeze wrong answers into logs, such as a Petri audit's auditor calls today, and fix the definition at the time of writing. A typed span around each region that turns agent scope off was considered and dropped as clutter in the transcript. Origins are a closed set of kinds, since the rule must decide from the value alone; which agent a call belongs to is the name of its span.
  - **Where `origin` is missing** (older Inspect logs, other sources), `timeline_build`'s prompt rules and, in replay's log driver, a new continuity rule mark helper calls ([Transcripts without recorded origins](#transcripts-without-recorded-origins)). A source that knows better supplies a stored timeline, as Petri does with `"target"`, or sets `origin` itself.
  - **Monitors do not branch on provenance.** A `context.replay` that told a monitor how its step was established was considered and dropped: a monitor under test must run the same code live and in replay. Each result records how its turns were established (`"turns": "recorded"`, `"inferred"` or `"stored"`), and what to trust is chosen by which transcripts are scanned (Scout's transcript filters, such as `source_type`) and by filtering results. Selection uses Scout's own options, `timeline=` and `depth=`, with the meanings `llm_scanner` gives them; the `infer_agent_turns=` flag and a mode treating every call as a turn are dropped. *Trimmed by Charles 2026-10-26:* `compaction=` is dropped, since a selector on `ReplayStep.segment` covers it, and `ReplayStep` gains `depth: int | None`, measured in the chosen timeline, so selectors and result metadata can use it.

  Affects PRs 1, 3, 5 and 6.
- **R7-D5: `human()` in replay when the log holds no answer for it.** *Decided by the maintainer 2026-10-19: a policy, `as_scanner(human=...)`, answers; by default the recorded answer, else the answer a host gives when no person can be asked, marked as not a person's. Revised by Charles 2026-10-26: a recorded answer is always used first, and `human=` names the answer given where there is none, or a stand-in.* First recommended the same day: `Host.ask_human` returns `None` and `human()` abstains. Revised because abstaining is not neutral. In `sequential([threshold(...), human(...)])` the threshold's `escalate` is then the chain's last decision, and an escalate that reaches the root becomes a `terminate` recorded as an unhandled escalation ([pr-series.md](pr-series.md), "Unhandled escalate"), a configuration bug the configuration does not have; beside peers in a `concurrent()` it lets their `proceed` through instead. The decided form:

  - **The recorded answer**, when the same `human()` instance, by path, answered at the step: its `SentinelEvent` ([Human decisions in replay](#human-decisions-in-replay)). For a log from an eval that ran no sentinel, a person's `ApprovalEvent` for the call answers a `human()` at `tool_call` (inspect_ai's built-in `"human"` approver, mapped as in [Transcripts without recorded origins](#transcripts-without-recorded-origins)).
  - **Otherwise the answer `human=` names**: `"reject"` (the default), `"approve"` or `"terminate"`. `"reject"` falls back to `terminate` where `reject` is not offered, which is every stage after a tool runs (`tool_result` and `model_output` offer approve and terminate); where the `human()` was configured without the named answer (`human(choices=)`), `terminate` answers, and where that is missing too, the scan raises a clear error. The default is what the sidecar host and Inspect's own host answer when no person can be asked (`sidecar/_host.py`, `ask_human`), so a protocol decides as it would live with nobody there.
  - **Or a stand-in for the person**: an async callable `(ReplayStep, Escalations, choices) -> Awaitable[HumanAnswer]`, asked where there is no recorded answer: an oracle built from validation labels, as AI control evaluations model a reviewer, or a model. `as_scanner()` takes only forms its scan spec can carry, since Scout rebuilds a scanner in a worker or a resumed scan from its registered parameters (P4-F4, accepted by Charles 2026-10-26): `human=` is `Literal["approve", "reject", "terminate"] | HumanStandIn | str`, an answer, or a stand-in registered with `@human_stand_in` or its name, and an unregistered callable is a clear error. The first forms, `"recorded"` (the default) and `"fail_closed"`, are gone; replaying while ignoring the recorded answers is deferred (`recorded_answers=False`).
  - **Each answer says where it came from.** The result of a step whose protocol reached `human()` records `"human": "recorded"`, `"unanswered"` or `"simulated"` in its metadata, with the answer given, so a back-test counts the steps that would have gone to a person apart from real blocks.
  - **A `human()` after a `threshold()` is reached only on escalation** (sentinel #153, decided by Charles 2026-10-26). `threshold()` decided nothing where none of its monitors reported, so in `sequential([threshold(...), human(...)])` the person was asked at every step the monitor skipped, and replay's default answer turned each of those into a `reject`; the R7 end-to-end test found it with a `bash`-only monitor at every `submit` call. `threshold()` now decides `proceed` there, so the person is asked, and replay answers, only where it escalates. In `concurrent()` a silent `threshold()` now votes as a low-scoring one does, and beside a rewriter the rewrite takes effect, since a `proceed` does not contest a `modify`. (Superseded 2026-10-26 by sentinel #154: as first decided, option (a), the silent threshold's `proceed` contested the rewriter's `modify`, which became a `reject`; see sentinel.md, [Two compositions](sentinel.md#two-compositions-concurrent-and-ordered).)
  - **A recorded answer no `human()` asks for is reported.** Recorded answers are matched by the `human()` instance's path, so a reshaped protocol gets none; the scan warns once per worker process where a step has an answer recorded at a path no `human()` asked from and a `human()` asking where nothing was recorded (sentinel #135, decided by Charles 2026-10-26).

  `Host` and `human()` do not change; the policy is the replay host's. Affects PR 5. *Refined 2026-10-20 after review pass 2 (F9), and trimmed the same day:* the stand-in is `async`, `(ReplayStep, Escalations, choices) -> Awaitable[HumanAnswer]`, so it can ask a model, whose usage lands in the scan's `model_usage`. A recorded answer is replayed as recorded even from a prompt the person closed without choosing, or against escalations the replayed configuration no longer makes; both are known differences ([How exact replay is](#how-exact-replay-is)).

Affects PRs 2 and 3. *`agent_messages` added 2026-10-20 after review pass 1: it is cut from a per-conversation record like the others, so it is a view too.* *The generate stages' `input` added 2026-10-20 from sentinel #133's review pass 2 (accepted by Charles 2026-10-25 through sentinel #133, call 8): it is `Sequence[ChatMessage]` at every stage; the generate stages' `tools` stays a `list`.* *Since 2026-10-21 `agent_messages` is the agent's own list, passed live by reference, so it is no copy, and `None` in replay; it stays typed `Sequence`.*
- **R7-D7: does the rule also cover the one pass each agent turn makes over its own input?** *Decided by the maintainer 2026-10-19: no, keep the pass.* Recommended: no, keep that pass. What the rule removes is work repeated at every step over the whole conversation. Alternative: treat the pass as quadratic too, and design an interface for scaffolds to pass only new messages. Affects nothing in R7 if accepted.

  - **No `input_id_overrides` field.** It was the first recommendation (sparse `[position, id]` pairs on the condensed `ModelEvent`, restoring the ids the pool drops); it is now an alternative, as are hashing the id into the pool key (a rebuilding scaffold's messages stored again on every call) and recording only the last input message's id.

The tool stages keep the tool call id.
  - **`history` decides what is new by content and position**, aligned against the previous call's input, with no ids ([The as-sent fold without ids](#the-as-sent-fold-without-ids)).

### How exact replay is

*Decided by the maintainer 2026-10-20.* Asked whether the design was adding complexity and overhead for exact playback of edge cases that add no value, the maintainer agreed to trim it to one rule: **replay is exact where monitors commonly look; elsewhere this document says it is not; a log field is added only when a common case needs it.** So PR 1 adds one field, `origin`, beside R7-D8's change to how live builds generate ids and `history`. Trimmed, each first proposed after a review pass: a generate id field (R7-D8a), how far each tool call got (R7-D9), the step named on its `sentinel` span (R7-D10), a `"missing"` record (R7-D11), `HumanAnswer.closed` (R7-D12) and an `"escalations"` marker (R7-D5), a fidelity record per step (dropped, with the one-flag form that replaced it), and most fail-closed rules for malformed logs (two kept, [One builder for live and replay](#one-builder-for-live-and-replay), "Logs as input").

**No per-step flag.** *Decided by the maintainer 2026-10-20.* A flag marking approximate steps (`ReplayStep.approximate`, `"approximate": true` in result metadata) was proposed with the trims and dropped. Monitors never see it, since R7-D4 keeps provenance out of the step, and for analysis it would mislead: most differences below cannot be detected per step (a closed prompt, a scaffold's own retry, a parallel publish race), two leave no step to mark, and the rest are properties of the whole log, so a missing flag would read as "exact" when it is not. A result keeps `"turns"` (R7-D4) and `"human"` (R7-D5), which mark something real. To leave out whole logs, filter on what Scout already exposes per transcript: its source type, the inspect_ai version, and the eval's configuration, such as `log_images`.

**Known differences.** Each is stated where it arises, and PR 3's test names it rather than scripting machinery for it:

- a tool that raises `ToolParsingError` itself gets no `AfterToolCall` in replay (R7-D9; a stated limit, accepted by Charles 2026-10-26);
- a `BeforeGenerate` that left no `ModelEvent` gets no step where no `SentinelEvent` recorded it, and fails the transcript's replay as unsupported where one did (R7-D11; inspect_ai #5991, Ransom's B1);
- a value the log does not keep: a non-finite tool argument reads back from the log as `None`, and a message with a lone surrogate fails inspect_ai's transcript subscriber with a `UnicodeEncodeError` even without a sentinel, so live `history` holds what the log cannot (inspect_ai #5991, after #5990's fix for Ransom's B1 and B2);
- a step whose `sentinel` span holds no event is cut at its anchor, which differs when a parallel call's step publishes in between (R7-D10);
- a scaffold that catches a model error and calls generate again with the same input is replayed as one generate, since attempts are grouped by inference (R7-D8a);
- two overlapping generates with equal input in one conversation, whose retry attempts interleave, can have their attempts grouped wrongly, with or without a sentinel: a recorded step id names a generate's first attempt, not its later ones (R7-D8a; P4-F2, accepted by Charles 2026-10-26);
- a tool call a sentinel modified: replay's `BeforeToolCall.call` is the approver's replacement as recorded, else the model's proposal, without the canonicalization live applied after approval, since the canonical arguments were overwritten in the log and replay never reruns a canonicalizer (P5-F1 and P6-F1, accepted by Charles 2026-10-26);
- a model hook (`on_before_model_generate`) that rewrites the input or tools: live `BeforeGenerate` sees them before the hook runs, and the log records them after, so replay's generate stages show the values as sent (P4-F1, accepted by Charles 2026-10-26);
- an operator's cancel of a running tool records the same `timeout` error as the tool's own timeout, which replay reads as the body having run, so it builds an `AfterToolCall` the cancelled call never reached live (inspect_ai #5991, review pass 2, F7; pinned by `test_an_operator_cancel_is_a_known_difference`, and accepted by Charles 2026-10-25 as #5991's call 2, with a Deferred entry in [pr-series.md](pr-series.md) for recording the cancel distinctly);
- message ids in replayed `input` and `history` are the pool's, the id of the first message stored with that content (R7-D8), and equal messages in one `history`, such as `react`'s repeated nudges or a rebuilt system message, are one pool row, so in replay they share an id and an object where live they are distinct (#5991, review pass 2, F4);
- replay infers whether a tool call was checked from the region its producing model call was made in, where live decides by the region that runs the call (`checks_tool_calls()` in `call_tool`), so a call produced in one region and run in another, with no `SentinelEvent` recording the stage, is replayed by its producer's region (#5991, review pass 2, F8);
- a log written with `log_images=False` holds a placeholder for each image;
- a recorded `human()` answer is replayed as recorded when the person closed the prompt without choosing (R7-D12), and when the replayed configuration hands `human()` different escalations from the ones the person saw;
- a scaffold that runs one message's calls in more than one `execute_tools()` call has them replayed as one batch;
- `eval.metadata` is the sample's final metadata, which a solver can have changed during the run;
- in a log written before R7-D8, generate step ids come from the fallbacks in [Step ids](#step-ids).

### Nothing quadratic

Decided by the maintainer on 2026-10-19, rejecting the `agent_messages` fingerprint (R7-D2): "nothing quadratic". A conversation of *n* turns has inputs that grow with *n*, so any work that walks the whole conversation at every step or every call costs the square of *n* over a run. Replay's work is linear in the size of the log as stored (its message pool, its events and their input ranges), and per step it is constant beyond what the monitor itself reads. *Qualified by Charles 2026-10-26 for the Scout path:* Scout hands a scanner each model event's input expanded, so the entries of those lists are quadratic in turns; no message is decoded or copied again for them, and replay works over the pool it rebuilds. Each piece:

| Work | The quadratic way | How replay does it |
|---|---|---|
| Reading model inputs | expanding every `ModelEvent`'s input from the pool into its own list of messages, decoded or copied per event | from a log, the log driver reads each event's `input_refs` and the message pool, decoding each pool message once; through Scout, which hands the scanner expanded events, sentinel rebuilds the pool with inspect_ai's `condense_events()` (decided by Charles 2026-10-26, with Scout #729 dropped). Either way a step's `input` is a view over its event's ranges |
| The as-sent fold | walking each turn's whole input against everything sent | aligning each turn's input against the previous turn's only ([The as-sent fold without ids](#the-as-sent-fold-without-ids)): a range equal to the previous turn's at the same position is matched whole; other positions are matched by a content key computed once per pool row. Linear for inputs whose pool ranges do not overlap; nested overlapping ranges, which inspect_ai's writer (`condense_model_event_inputs`) emits for an input that repeats runs of its own messages, are a known superlinear case, pinned by a test (accepted by Charles 2026-10-21, B3; documented here and at the index in inspect_ai's `_replay.py`, not in user docs), and the lookup's limit on held metadata variants is documented the same way |
| Finding a step's producing `ModelEvent`, its `sentinel` span, its `ToolEvent` and `ApprovalEvent` | a search per step | indexes built in the single pass: by event uuid, by stage and step id, and by tool call id resolved by position, the newest before the step, as live's `find_last` ([One builder for live and replay](#one-builder-for-live-and-replay), "Logs as input") |
| `history`, `human_decisions` and `input` at every stage, per step | a copy per step | a read-only view of the conversation's append-only list cut at a length, or of the event's input, typed `Sequence` (R7-D6, decided 2026-10-19; every stage's `input` from sentinel #133, 2026-10-20); the generate stages' `tools` stays a `list`; live, `agent_messages` is the agent's own list, passed by reference, and in replay `None` |
| Step ids, the cut | | generate ids read from the events; positions from the single pass |
| The agreement probe, `replay_check()` | hashing every list at every step | digests `history` and `human_decisions` by length and their last element, and `context.eval` once per transcript (P3-F7, accepted by Charles 2026-10-26); whole lists are compared only in inspect_ai's step test, over small scripted evals |
| Scout's rows | the transcript copied per row | one resultset row per transcript, expanded per step only when the dataframe is read |

**Built code the rule reaches** (found 2026-10-19, fixed in PR 3, which rewrites the builder anyway). Live, every step copies whole lists: `sent_messages()` returns `list(found.messages)`, the as-sent list so far; the tool stages copy the producing call's input and tools (`list(producer.input)`, `list(producer.tools)`); `_human_decisions()` copies the published list into a tuple (`_sentinel/_dispatch.py`, `_sentinel/_sent.py`); and inspect_ai PR #5986's first form copied its whole `agent_messages` record at every step (`ran_messages()`, found by review pass 2, F10), a recorder its 2026-10-21 rework removed. R7-D6 (decided 2026-10-19) replaces the copies with views typed `Sequence`. `record_sent` also walks each turn's whole input and rebuilds its `previous` list; R7-D7 keeps that per-call pass. Found later (Scout #729, review pass 3, F2): inspect_ai `timeline_build`'s `_extract_agent_results` scans the next model input in full for every bridged `agent-<id>` span, which is quadratic with one bridge per turn, on expanded and condensed reads alike; PR 6 fixes it in inspect_ai #6098 with an index built once over pool ranges or span positions, and an *n*/2*n* work-count test; the fix stays in the public `timeline_build`, since it does not depend on continuity and its output is unchanged.

**Pinned by counting, not timing.** PRs 3 and 5 each add a deterministic test that counts the work rather than timing it: on synthetic conversations of *n* and 2*n* turns, with a compaction and parallel tool calls, the pool messages decoded, the messages the fold visits and the elements copied into step fields stay within a constant times the log's size, and double, not quadruple, from *n* to 2*n*.

## Reconstructing steps

### What the log records

Specified 2026-10-19 as inspect_ai PR 1; revised the same day (R7-D4) from `agent_turn` and conversation fields to one fact, `origin`. Live, inspect_ai decides at each model call whether it is one of its conversation's agent turns, from a context variable (`AgentScope`, `_sentinel/_scope.py`), and folds the input into that conversation's as-sent list (`Model._record_model_interaction` calls `record_agent_turn`, `_sentinel/_dispatch.py`), but writes none of it to the log. Of the places that turn agent scope off, tools, scorers and a sentinel's own run sit in spans that say so: the compaction summary call (`model/_compaction/summary.py`) runs inside the agent's span with the agent's system prompt, and approval, review and MCP sampling open no span. So a log cannot say which calls make up `step.history`. One field fixes that:

| Event | Field | Type | Set | Old logs read as |
|---|---|---|---|---|
| `ModelEvent` | `origin` | `str \| None`, default `None`; one of the kinds below | when the event is created in `Model._record_model_interaction`, from the current scope | `None`: not recorded |

**The kinds** are a closed set that inspect_ai owns, since every reader of the rule depends on it:

| Kind | Set by | A turn |
|---|---|---|
| `"agent"` | the default during the solve, and every `span(type="agent")` (`util/_span.py`), which `as_tool()`, `handoff()`, `run()` and `as_solver()` open | yes |
| `"environment"` | `model_origin("environment")`: the setup being evaluated against, such as Petri's auditor or a simulated user | no |
| `"helper"` | `model_origin("helper")`: a scaffold's own helper call in its loop, such as its own summarizer | no |
| `"tool"` | a tool's own body (`model/_call_tools.py`) and a bridged host tool (`agent/_bridge/sandbox/service.py`) | no |
| `"compaction"` | the compaction summary call | no |
| `"approval"`, `"review"` | approval and review | no |
| `"sampling"` | MCP sampling | no |
| `"sentinel"` | a sentinel's own run, including its monitors' calls | no |
| `"scorer"` | `score()` from a solver and the task-level scorers (`_eval/task/run.py`, `_eval/score.py`, `_control/scoring.py`), a final region | no |
| `"setup"` | any other call outside the solve, such as sample init | no |

`sentinel_scope()` takes the kind of its region and the scope's context variable carries it, so `origin` is the kind of the innermost region. A `final` region keeps its kind under an agent span opened inside it, as agent scope does today: an agent span inside approval stays `"approval"`. `"environment"` and `"helper"` are final too, so an auditor's sub-agent stays environment. A new kind is a change to inspect_ai, never a scaffold's own string. The final regions are `"environment"`, `"helper"`, `"scorer"`, `"approval"`, `"review"`, `"sentinel"`, `"compaction"` and `"sampling"`: a sentinel does not check the tool calls made in them. It checks tool calls in `"agent"`, `"tool"` and `"setup"`, and only `"agent"` gets the generate stages. *Reversed by Charles 2026-10-25 (inspect_ai #5990, design call 3):* task-level scorers are a final `"scorer"` region, so a call inside a task scorer records `"scorer"`, under an agent span too. #5990's first form made them a region that is not final, so that a sentinel kept checking a task scorer's tool calls, as it did before R7, and an agent span inside a task scorer recorded `"setup"`.

**The rule is one function** in inspect_ai: a call is an agent turn when its origin is `"agent"`. The dispatcher uses it live in place of `current_scope() is AgentScope.ON`, `is_agent_generate()` becomes an active sentinel and that rule, and `timeline_build` and the log driver read it from the event. Because the context variable that sets `origin` is the one live already reads, the recorded value is the live one, with or without a sentinel (R7-D1).

**Names come from spans.** Which agent a call belongs to ("target", "auditor") is the name of its enclosing span, already in the log; no free-form name is recorded. One can be added beside the kind later, if a case without a span needs it.

**`model_origin()` is public**, accepting the kinds a scaffold may set, `"environment"` and `"helper"`; the others are inspect_ai's. Both are final regions, so, as inside approval and review, a sentinel does not check the tool calls made inside a `model_origin()` block (inspect_ai #5990, design call 9, accepted by Charles 2026-10-26; documented and tested there). Its docs say the marker reaches only the task that set it and the tasks that task spawns, so a design that makes the evaluated agent's calls from inside an environment region, such as an auditor's tool that generates the target's turn, marks the target too. Petri's current design does not ([What this asks of the other documents](#what-this-asks-of-the-other-documents)).

**The conversation is not recorded.** It comes from the span tree: the innermost `span_begin` of type `agent` reached from the event's `span_id` through `parent_id`, else the sample's uuid (Decisions, above). A `CompactionEvent` is placed in its conversation the same way. *Decided by Charles 2026-10-21 (B1):* a bridged agent's `ModelEventSink`, such as inspect_swe's Claude Code and Codex consumers, can attribute a call to a sub-agent's span, and live follows it, so the live conversation and the span tree agree: an optional `ModelEventSink.on_start(input) -> span | None`, called once per generate before `BeforeGenerate`, names the span the whole generate runs under. Moving events in `on_pending` stays supported, and the docstrings say live follows `on_start`. Built in inspect_ai #6004, stacked on PR 1, with inspect_swe #206 for the consumers.

**The timeline uses it** (PR 1). Where `origin` is recorded, `timeline_build` and its TypeScript port (ts-mono `timeline/core.ts`) mark a call whose origin is not `"agent"` as utility and do not apply their system-prompt rules to it. An agent span with no turn, such as an auditor's, stays in the tree as a conversation, not as utility. So the compaction summary call drops out of the viewer's timeline and Scout's timeline scanners as it drops out of `history`, and Petri's hand marking of its realism spans as utility (`_mark_utility_spans`) is no longer needed. The viewer can label a call with its origin; it need not.

**Additive.** `origin` has a default, so older logs load with `None`; events are pydantic models with the default `extra="ignore"` (none in `event/` sets `forbid`), so an older inspect_ai reading a newer log drops it. inspect_ai's OpenAPI schema and ts-mono's generated viewer types are regenerated with the PR (ts-mono's change lands on its `main` first), and Scout's copy of the schema with Scout #730. No span or event is added, so the transcript gains nothing to show, and the viewer and the ACP TUI, which treat span types specially, see no change, as generate-stages.md decision 15 requires.

**Cost.** About 20 bytes of JSON per `ModelEvent` (`"origin":"agent"`) before the log's compression, against model events whose `input`, `output`, `config` and `call` run to kilobytes; PR 1 measures a 300-turn mockllm sample to confirm. At run time, one context-variable read per model call.

**Not recorded, and why.** A tool event's origin or conversation: a tool step's are its producing `ModelEvent`'s. The step's `agent_messages`: the scaffold's own list, which replay gives as `None` ([Reconstructing `agent_messages` in replay](#reconstructing-agent_messages-in-replay)). A per-step input: R2 is met from the producing `ModelEvent` (pr-series.md, Deferred, "Record `step.input` instead of rebuilding it"). The untruncated tool output: never in the log, so `AfterToolCall.output` is `None` in replay.

**Acceptance for PR 1.** Table-driven tests on mockllm, with and without a sentinel configured. `origin` is `"agent"` for the `generate()` solver, `react` turns, sub-agents run through `as_tool()`, `handoff()` and `run()`, and a bridged agent's calls; `"tool"` for a tool's own call; `"compaction"`, `"approval"`, `"review"`, `"sampling"`, `"sentinel"` (a monitor's call), `"scorer"` and `"setup"` for theirs; and `"environment"` and `"helper"` under `model_origin()`, including for an agent span opened inside them or inside approval. The conversation from the span tree equals `_conversation()` on every model call, including a sandbox-bridged agent that checkpoints. With a probe sentinel watching all four stages, every live `step.history` equals the fold of the inputs of its conversation's `"agent"` calls before the step's `sentinel` span, in log order, so the field is sufficient before any replay code exists. `timeline_build` and its port agree on a shared fixture. A log written before the field loads with `None`. The schema and viewer types are regenerated. With R7-D8: the sufficiency test passes for two calls whose last input messages have the same content under ids `u1` and `u2`, an input `[a: A, b: B]` followed by `[c: B, d: A]`, a message edited between calls, a message inserted in the middle, a message dropped and later restored, two identical `continue` nudges sent at different turns, the same message object edited in place inside the matched prefix and sent again (P4-F8), and a sent message edited or elided in place and not sent again, each equal to the fold of the recorded as-sent snapshots (decided by Charles 2026-10-26, #5990 call 2); live, each generate step's id is the `uuid` of that generate's first `ModelEvent`, for parallel agents, a fan-out of one prompt object to several sub-agents, and sub-agents sharing a bridged CLI's conversation.

### The as-sent fold without ids

*Decided 2026-10-20 (R7-D8).* `step.history` holds every message a conversation's agent turns have sent, each once, where it was first sent. Live, inspect_ai decided what was new by message id and by position (`_record`, `_sentinel/_sent.py`), which a log's pool cannot reproduce. Live and replay now share one rule, in `_sentinel/_steps.py`, that uses content and position only:

- **Same content** is the message without its `id`, `source` and `metadata`, the fields not sent to the model (`_NOT_SENT`), compared by a content key: a hash of that form's JSON in the log's encoding (`logged_json()`'s, which keeps `NaN`, `inf` and `-inf` apart from `null`), so four sends differing only in a non-finite tool argument are four messages. Comparing never fails a generate: a message with a lone surrogate, which the normal encoding refuses, is keyed by its JSON with the surrogate escaped, and a message that cannot be serialized at all is keyed by identity and matches only itself (inspect_ai #5990, Ransom's B1 and B2, 2026-10-26). Live computes the key of every message it sends, on every send, and keeps the previous send's keys, so an object the scaffold edits in place and sends again has its new content's key and is new, as the rule says, wherever it sits in the input; that is the per-call pass R7-D7 accepted. *P4-F8, accepted by Charles 2026-10-25 through inspect_ai #5990 (call 1).* The first form keyed only the part after the matched prefix and found the prefix by identity, which let a same-object edit inside the prefix through. Replay computes it once per pool row. *P3-F2, accepted by Charles 2026-10-25 through inspect_ai #5990 (call 1).* An identity cache, one key per message object, was dropped: a message object is mutable, so a cached key would hide an edit made before a later send. **`history` is as sent**, even when the agent edits a message after sending it, as a scaffold that elides old tool results does (decided by Charles 2026-10-26, #5990 call 2). Live records the as-sent snapshots inspect_ai makes for the log (inspect_ai #5883): `Model.generate()` passes the snapshot to `record_agent_turn`, so a message edited or elided in place after it was sent still shows as sent, and the log's `ModelEvent` holds the same snapshot, so live equals replay. Without the snapshot, live saw the edited object and replay saw the message once, as edited, a known difference that is now gone.
- **Matched prefix.** The input's leading part that equals or extends the previous turn's input is matched whole. In replay this is a comparison of pool ranges, with no decoding and no index: an input `[0, k+1)` after `[0, k)` matches its first `k` positions at once, which is the whole input of an append-only conversation but its newest message. Live, the same prefix is found by comparing keys, message by message, with the previous send's keys, not by identity; replay's range comparison stays, since a pool row is addressed by its content.
- **Alignment of the rest.** After the matched prefix, the input is walked against the previous turn's input from the same point, with a pointer into it. A message the same as the one at the pointer, or at a later position (found through an index of the previous input's keys after the matched prefix), is matched, and the pointer moves past it; the messages skipped over were dropped by this call. A message matched nowhere at or after the pointer is new and is appended to `history`. Repeated content is matched to its first position at or after the pointer, so two equal messages are two positions. The first turn's whole input is new.
- **Cost.** Live, the per-call pass R7-D7 accepted. In replay, linear in the log as stored: equal and extending ranges are matched without visiting their messages, and the index covers only the part of the previous input after its matched prefix and is kept incrementally from turn to turn, adding and dropping the positions that change, so its construction and updates are bounded by the ranges that change and the pool rows first seen. *P3-F1, accepted by Charles 2026-10-25 through inspect_ai #5991 (call 7).* An index rebuilt over each whole previous input would visit `1 + 2 + ... + n` keys in an append-only conversation of `n` turns.

What this changes live (R10): a message rebuilt with a fresh id where it was before is matched, as the alias rule did; a message edited between calls is new, as a new version was; a message reordered is new, as one under a fresh id was. Two cases change: a message re-sent under its own id at a new position, which the id rule matched, is now new unless it follows its previous position in order; and a message dropped by one call and restored by a later one is counted again. Two equal messages sent at different turns, such as `react`'s repeated `continue` nudge, stay two messages, since each is new where it appears. PR 1 changes the live fold to this rule and its sufficiency test covers each case.

### One builder for live and replay

AISI's last R7 line, "live and replay stay identical as Sentinel changes", is a property of code, not of a document: two builders drift. So there is one.

**inspect_ai owns it.** A new module, `_sentinel/_steps.py`, holds one function per stage that takes the facts a step is made from and returns the step, and the pieces those facts need: the as-sent fold (`_Sent`, made a plain object whose `record(input)` both drivers call; `record_sent` keeps its per-transcript map for the live driver), the producing-call predicate (`_produced_by`), step ids (a generate's pre-minted `uuid`; the tool call id), and the conversation's `human()` decisions published as each step settles (`_publish`, `_human_decisions`). The live driver is `_dispatch.py` as it is, gathering facts from its arguments, the transcript's history and context variables. The log driver, `steps_from_events()`, gathers the same facts from a sample's events, messages and message pool, in one pass that is linear in the log's stored size ([Nothing quadratic](#nothing-quadratic)):

| Fact | Live (`_dispatch.py`) | From the log |
|---|---|---|
| conversation | `_conversation()` | the innermost `agent` span above the producing or own `ModelEvent` (its `span_id`, then `parent_id`), else the sample's uuid |
| agent turns folded so far | `record_sent` as each call is made | the conversation's `ModelEvent`s whose `origin` is `"agent"` before the step's cut (below), in log order; without `origin`, the timeline's turns ([Transcripts without recorded origins](#transcripts-without-recorded-origins)) |
| `input`, `tools` at the tool stages | `_producing_event()`: `transcript().history.find_last(_produced_by(id))` | the same predicate over the log's events |
| `input`, `tools`, `tool_choice`, `config`, `model` at the generate stages | `Model.generate`'s arguments | the turn's `ModelEvent` |
| `output` | `Model.generate`'s result | `ModelEvent.output` |
| `call`, `message` | `execute_tools`' arguments, canonicalized by the tool's canonicalizer before approval and again after an approver's modification (`call_tool`); at `AfterToolCall`, the call that ran (`executed_call`), with any modification a sentinel made at `BeforeToolCall` | at `BeforeToolCall`, `ToolEvent.arguments` whenever no sentinel `modify` replaced them, including after an approver modified the call and inspect_ai canonicalized the replacement (`call_tool` writes the canonical arguments there); only where a sentinel's `modify` replaced them, the approver's replacement from `ApprovalEvent.modified` where present, else the model's proposal, whose canonicalization after approval is then unavailable (a stated limit); replay never reruns a canonicalizer, since a tool's name does not identify its canonicalizer (P4-F7, P5-F1 and P6-F1, accepted by Charles 2026-10-26); at `AfterToolCall`, the call that ran, from the `ToolEvent`'s `id`, `function` and `arguments`, which PR 3 makes `call_tool` set at the first canonicalization too, as it does after an approver's or a sentinel's modification, and keep when no approver or sentinel is active, where it had restored the model's arguments (inspect_ai #5991, Ransom's B2, 2026-10-26) |
| `result` | the `ChatMessageTool` built for the model | the message with `ToolEvent.message_id`, from a later input of the conversation or `sample.messages`, else rebuilt from the `ToolEvent` (`result` is the content the model saw) |
| `truncated` | `execute_tools`' `(original, limit)` | `ToolEvent.truncated` |
| `view` | `resolve_tool_call_view(call, viewer)` | at `AfterToolCall`, `view.call` from `ToolEvent.view`; at `BeforeToolCall`, the whole view from an `ApprovalEvent` where one recorded it, else `ToolEvent.view` when the `ToolEvent`'s arguments equal the approved call's, else absent, since a sentinel's `modify` replaced `ToolEvent.view` with the modified call's and the tool's viewer is not in the log; `context` absent |
| `human_decisions` | published as each step's span ends | the same rules over the log's `SentinelEvent`s ([Human decisions in replay](#human-decisions-in-replay)) |

**The cut.** Live, a step's `history` and `human_decisions` are taken when the step is built, just before its `sentinel` span begins, and a step's own `human()` decisions are published when its span ends (`_publish`). In a log that ran a sentinel watching the step's stage, the cut is that span's `SpanBeginEvent`, found by the `SentinelEvent`s inside it, so the replayed value is the live one. Elsewhere, and for a span holding none because every instance in it abstained (R7-D10), the cut is the step's anchor, the last point before the step was built: before its own `ModelEvent` at `BeforeGenerate`; at that event's end at `AfterGenerate`; just before its call's `tool` span begins at `BeforeToolCall` (`call_tool` builds the step after approval and before the span); and at that span's end at `AfterToolCall` (`_apply_tool_review` builds it once the body returns). Decisions published before the anchor are in; the step's own call's are not. *Revised 2026-10-20 after review pass 1: the tool stages' anchor was after the producing `ModelEvent`, which drops a decision published at the call's `tool_call` step from its `tool_result` step.* The anchor differs from the live cut only when a parallel call's step publishes between this step being built and its anchor, or another agent turn of the same conversation starts there, which takes two agents sharing a conversation, as sub-agents inside one bridged CLI do.

**Events in log order.** The driver reads events in the order the log stores them, flattening an older log's nested events (`ToolEvent.events`) in place, and makes one sequential pass over the whole sample before any monitor runs: step ids, the fold, the cut and the published decisions all depend on order, and none on monitor results. The pass yields `ReplayStep`s in live order, and the runner runs them in that order ([Cost and parallelism](#cost-and-parallelism)).

**Logs as input.** *Added 2026-10-20 after review pass 2 (F5); trimmed the same day.* Replay trusts the structure inspect_ai writes (events, their order, spans and their parents, the ids inspect_ai mints, the message pool) and never the content the agent under observation writes or is shown, which it passes to monitors as data and never reads as structure. Tool call ids come from the provider, and through some servers and bridged CLIs from the model's own text, so nothing makes them unique across a sample; replay resolves one by position, as live does (the newest producing `ModelEvent` before the step, `find_last`, and the `ToolEvent` and `ApprovalEvent` after it). Two things fail the transcript, a Scout error naming the rule, rather than being guessed at: two steps of one stage with one step id, which no result row could tell apart, and a `parent_id` cycle in the span tree, which a walk must never loop on. An unknown `origin` needs no rule: only `"agent"` is a turn, so a kind added later reads correctly as not a turn. `origin` stays typed `str` in the schema, since a `Literal` would make an older inspect_ai fail to load any log written after a kind was added.

**Which steps ran.** *Added 2026-10-20 after review pass 1; revised after review pass 2, and trimmed to inference.* From events, a step exists where it ran live, or would have run had a sentinel watched its stage, which a result message or a completed `ModelEvent` does not imply. A generate is one `Model.generate()` call, which writes one `ModelEvent` per attempt: a provider error retried, an attempt timeout, or a cache hit on a retry (a failed attempt keeps its event with `error` set and a pre-filled empty output, `_model.py`). Its attempts are grouped as follows, and the generate's id is its first attempt's `uuid` (R7-D8a). *P3-F3, accepted by Charles 2026-10-26.* Where the generate ran under a sentinel watching a generate stage, its `SentinelEvent`s record that id as their `step_id`, which identifies the generate's first attempt exactly; later attempts carry no id and are associated by inference: errored attempts followed by one with the same input, in the same span, are one generate. Two overlapping generates with equal input in one conversation whose retries interleave can be grouped wrongly, with or without a sentinel, which is a known difference. *P4-F2, accepted by Charles 2026-10-26.* The pass-3 form claimed exact grouping under a sentinel; a first-attempt id is not on the later attempts, so it is not.

| Stage | Exists when | Inferred from |
|---|---|---|
| `BeforeGenerate` | once per agent-turn generate, not per attempt | `origin`; a generate that left no `ModelEvent` gets no step, or fails the replay as unsupported where a `SentinelEvent` recorded it (R7-D11) |
| `AfterGenerate` | the generate's last attempt records no `error`, and its output is not a refusal raised under `fail_on_refusal` (`config.fail_on_refusal`, a non-empty output, `stop_reason == "content_filter"`) | the events |
| `BeforeToolCall` | the call got past parsing, lookup and approval, and ran in inspect_ai's own executor | not for a sandbox-bridge host tool, whose `ToolEvent` carries `metadata["bridge"]` and whose executor never runs the tool stages (inspect_ai #5991, Ransom's B3, 2026-10-26; a stage a `SentinelEvent` records is still kept), nor for a call with `parse_error`, an unknown tool, an `ApprovalEvent` that rejected or terminated, or a halted call's synthesised `cancelled` result |
| `AfterToolCall` | that call's tool span ended with its body returned normally and no review policy terminated it, even if a sibling in its batch later raised | not for the calls above, nor a call whose error is `parsing` (read as a schema validation error, R7-D9), nor one whose `ToolEvent` records `failed`, nor one whose own `ToolEvent` was left pending or whose own review ended the sample. A `timeout` error is read as the body having run, so an operator's cancel of a running tool, which records the same error, gets an `AfterToolCall` (a known difference, #5991 call 2) |

Reachability is decided per call. *P3-F5, accepted by Charles 2026-10-26.* A batch that raised still has the `AfterToolCall` steps of the calls that completed before it raised, since each call runs its own review and after-stage sentinel (`call_tool_task` calls `_apply_tool_review` before the batch can fail). The rule that a batch that raised added nothing to `agent_messages` went with the replayed `agent_messages` (2026-10-21).

The messages projection ([From messages](#from-messages)) cannot tell any of this and stays approximate: it builds a step for every assistant message and tool result.

### From messages

The canonical reconstruction works from `list[ChatMessage]` alone, because that is what every source has — an eval log, a Scout transcript from another agent framework, a proxy request. It is exactly the projection `agent/_bridge/_approval.py` performs on a model response and `sentinel-deployment.md` describes for a proxy:

| Stage | Reconstructed from | Fidelity |
|------------------------|------------------------|------------------------|
| `BeforeGenerate` | every message before an assistant message is that generate's `input` | `tools`, `tool_choice`, `config` absent |
| `AfterGenerate` | the assistant message is `output.choices[0].message`; `usage`, `time` absent | good |
| `BeforeToolCall` | each `tool_calls[i]` on an assistant message, with the message text and history to that point | `view` absent |
| `AfterToolCall` | the `ChatMessageTool` whose `tool_call_id` matches, as `result`; history to that point | `output` (untruncated) absent; `truncated` is `None` (unknown) |

From messages alone, as in every replay, `agent_messages` is `None` ([Reconstructing `agent_messages` in replay](#reconstructing-agent_messages-in-replay)). At the tool stages `input` (and with it `tools`) is `None` from messages alone: the history to that point is right until the first compaction and wrong after it (the model was shown a summary plus recent turns), so it is not offered as the model's input. A live step without a recorded model call gets `None` the same way, so a monitor handles both alike.

`view` and `output` being absent is the case `sentinel.md` already requires monitors to tolerate for proxies, which also give `agent_messages` as `None`, so a portable monitor replays from messages unchanged. Note the last row is *better* than the proxy's: a proxy never sees the final step's result because no further request carries it, whereas a transcript is complete.

``` python
@dataclass(frozen=True)
class ReplayStep:
    id: str                 # the step id — see below
    stage: Literal["model_input", "model_output", "tool_call", "tool_result"]  # as SentinelEvent.stage
    step: Step
    segment: tuple[str, int]  # the conversation, and how many of its compactions came before
    depth: int | None       # the shallowest level of a span holding one of its conversation's model calls (2026-10-26)
    recorded_answers: Mapping[str, HumanAnswer]  # this step's own recorded human() answers, by instance path


def steps_from_messages(messages: list[ChatMessage]) -> Iterator[ReplayStep]: ...  # internal since 2026-10-26
```

The `Context` is the sample's and constant, so the runner holds it rather than each step (revised 2026-10-19). `recorded_answers` holds the answers recorded at this step by each `human()` instance, by path, empty when none, for the replay host's `ask_human()` (R7-D5); `step.human_decisions` holds only earlier steps' decisions, so it cannot. It is replay provenance on `ReplayStep`, never on `Step` (R7-D4), and lands in PR 2 as a follow-up commit. *P4-F3, accepted by Charles 2026-10-25 through sentinel #133 (call 7).* `depth` is added by Charles's decision of 2026-10-26 (R7-D4) and computed in PR 5 from the chosen timeline: the shallowest level, as Scout counts it for `depth=`, of any span holding one of the step's conversation's model calls, and `None` for a step whose model call sits in no span (as sentinel #135 implements it at f5dde52). `ReplayStep` is sentinel's; inspect_ai's `steps_from_events()` builds it, as the live dispatcher builds sentinel's step types.

### From events

An eval log's events restore what messages lose. `ModelEvent` carries `input`, `tools`, `tool_choice`, `config` and `output` — `BeforeGenerate` and `AfterGenerate` field for field. `ToolEvent` carries `function`, `arguments`, `view`, `result` and `truncated` (the output's size and the limit it was cut to), which restores `view` and lets `result` be exactly what the model saw. It gives `AfterToolCall.truncated` as the live host set it: `Truncation(*event.truncated)` when set, and `False` when absent in a log new enough to record it, that is, one whose `eval.packages["inspect_ai"]` is 0.3.31 or later (`max_tool_output`, inspect_ai #478, which added the field); in an older log, `None`. At the tool stages the producing `ModelEvent` gives `input` and `tools`, the same lookup the live dispatcher makes. The one thing an eval log does not hold is the untruncated tool `output`, so `AfterToolCall.output` stays optional in replay too.

Events also restore `input` exactly, from `ModelEvent.input`, and let `history`, the as-sent view of an agent's run (AISI R10), be rebuilt per agent; it is not `agent_messages`, the agent's own list, which the log does not record and replay gives as `None` ([Reconstructing `agent_messages` in replay](#reconstructing-agent_messages-in-replay)). Live, inspect_ai folds each agent turn's input in as the call is made, by content and position, and writes nothing to the log (built 2026-10-14, revised by inspect_ai #5990; `sentinel.md`, "The history as sent"). Replay runs the same fold, the same `_Sent.record()`, over the inputs of the conversation's `ModelEvent`s whose `origin` is `"agent"`, up to the step's cut ([One builder for live and replay](#one-builder-for-live-and-replay)). What the fold needs that a log lacked is which model calls were the instance's agent turns; [What the log records](#what-the-log-records) adds it, and the instance comes from the span tree. Transcripts without it get their turns from the timeline ([Transcripts without recorded origins](#transcripts-without-recorded-origins)). `CompactionEvent`s are not needed for the fold, since a message stays in the list once sent; they mark where a conversation's input stopped extending its previous input, which `ReplayStep.segment` counts.

`steps_from_events()` is an *enrichment* of the messages reconstruction rather than a second algorithm: it walks the same steps, in the order the log records them, and attaches the matching event's fields where one exists. Tool-stage ids, the tool call id, are the same either way. Generate-stage ids are not: since R7-D8 a generate's id is its first `ModelEvent`'s `uuid`, which a messages-only transcript does not have, so the messages projection names its generate steps by their position in the conversation, and a label made on a generate step of one projection does not carry to the other. *P4-F10, accepted by Charles 2026-10-26.* One more thing differs: which steps exist. From events, a step exists only where it ran, or would have run under a sentinel ([One builder for live and replay](#one-builder-for-live-and-replay), "Which steps ran"); from messages, every assistant message and tool result projects one.

### Reconstructing `agent_messages` in replay

*Decided by Charles 2026-10-21: replay gives `None`.* `agent_messages` is the `messages` of the outermost `@agent` agent function running in the step's conversation, read live by reference at every stage, and `None` when no agent is running and for bridged agents (inspect_ai #5986; sentinel #134; [sentinel.md](sentinel.md#agent-messages)). It is the scaffold's own list, which a scaffold may curate: a control scaffold can keep a side-task instruction out of it while adding it to the model's request. The log does not record it, so the instruction appears only in model input. Replay therefore never rebuilds `agent_messages` from model input, from messages or from events: every replayed step carries `agent_messages=None`, which the step types already allow ("a list the host could not provide stays `None`"). A monitor that reads it handles `None`, as under a proxy; the exact model traffic is in `input` and `history`, which replay rebuilds. The live-equals-replay test and `replay_check()` leave the field out of their comparisons. *Decided by Charles 2026-10-26 (sentinel #152):* the default `StepPreprocessor` leaves out `agent_messages`, and `history`, even where they are `None`, rather than naming them as unavailable, so a default `Host.score()` prompt in replay is the same as the live one; PR 7's benchmark found every replayed judge prompt differing from live by that block. A window that asks for the list still names it as unavailable.

*Earlier, 2026-10-13 to 2026-10-20:* replay was first to cross-check `sample.messages` against the conversation's outputs and tool results and give a verified prefix, else `None`, with a recorded fingerprint declined in R7-D2 as quadratic; then, after a redefinition on 2026-10-20 as the conversation as the agent ran it, to rebuild it from the log at the three moments live changed it (the opening input, each output after its `AfterGenerate`, each `execute_tools()` batch's results). The 2026-10-21 definition makes both unnecessary.

### Human decisions in replay

Decided 2026-10-14 (AISI R4); not built. A replayed step's `human_decisions` holds what the live step held: the decisions a person made through `human()` at earlier steps of the conversation. Replay reads them from the log rather than making them, which is the only way, since a replay cannot ask the person: for each step, the `SentinelEvent`s with `factory == "inspect_sentinel/human"`, `kind == "decision"`, `status == "reported"` and the step's `conversation`, from steps whose `sentinel` span ended before the `sentinel` span of the step itself began, in event order (live, the host publishes a step's decisions as its span ends, and snapshots the list when it builds a step, before its span begins), less each one withdrawn by a `superseded` event at its own step: one with the person's action at the person's `path` or the path of a layer above it, the rule `supersedes()` applies live. A `terminate` that a sibling's `decide_final()` outran is recorded `reported` and then `superseded`, possibly as a copy a composition passed up, at a layer above the person. Both events fall inside the step's span, so a later step sees the same result live and in replay, including a parallel step that began while that span was open. Each becomes an `HumanDecision`: `stage` and `step_id` from the event; `decided` a `Reported[Decision]` rebuilt from `path` (its last segment the name), `function`, `action`, `explanation`, `message`, `modified`, `references` and `metadata`; `call_ids` the step id at a tool stage, and at `model_output` the tool calls of that generate's output (its last attempt's `ModelEvent`; in a log from before R7-D8, the assistant message with that id, from its `ModelEvent` output or `sample.messages`). Because the records are what was decided live, the order replay runs steps in cannot change the list.

A log from before Sentinel records a person's approval as an `ApprovalEvent`; replay could map one from a human approver to the same record (stage `tool_call`, step id the call id, `approve` to `proceed`), but this is not planned; until then such a log gives `None`, since replay cannot tell whether a person decided anything. *Revised 2026-10-19 for AISI's R7: planned, in [Transcripts without recorded origins](#transcripts-without-recorded-origins).*

The log driver applies these rules with the same functions the live host uses: it rebuilds each `Reported[Decision]` from the event and calls sentinel's `kept_human_decision()` and `supersedes()` (`_human_decisions.py`), as inspect_ai's `_Recorder` does live, and publishes a step's kept decisions at its span's end with the shared `_publish`, so a field added to `HumanDecision` changes both paths at once.

### Transcripts without recorded origins

Older Inspect logs, written before PR 1, and every transcript Scout imports from another framework. Decided 2026-10-19 (R7-D4); planned as PR 6. AISI's R7 names the first; the second is most of what a Scout database holds. Everything a tool or generate step reads from `ModelEvent`, `ToolEvent` and messages is as exact in an older Inspect log as in a new one (the fidelity table's middle column). Two things differ: which calls are turns, and, in logs from before Sentinel, where a person's earlier decisions come from.

**Conversation.** From the span tree, as for new logs, so the replay loads span events (`as_scanner()` asks Scout for `span_begin` and `span_end`). Scout's Claude Code and ATIF importers put sub-agents in agent spans. LangSmith's types every chain as an agent, so its transcripts split into more conversations than the agent had; continuity does not join conversations across spans, and the importer tests in PR 6 measure the effect.

**Agent turns** come from the timeline: `timeline_build`'s existing rules (`event/_timeline.py`: `_wrap_utility_events` treats a call that makes no tool calls and has a different system prompt from the span's first tool-calling call, or a one-token warm-up call, as utility; `_classify_utility_agents` does the same for a single-turn child span with a different prompt under a parent that runs a tool loop), and, in replay's log driver, a continuity rule added for these transcripts (PR 6, inspect_ai #6098). Continuity is an offline form of the agent bridge's own thread tracking (`AgentBridge._track_state`, `agent/_bridge/types.py`), which tells a bridged CLI's turns from its side calls live. PR 6's eight design calls were accepted by Charles on 2026-10-26, and the rule below is as built:

- Within each conversation of a timeline span, in order, keep the thread's tip: the last turn's input and output. A call whose input continues the tip, with the tip's output at position `len(tip.input)`, is on the thread. The thread is per conversation, since the timeline can unroll the solvers' calls beside a lone agent span.
- A call that continues nothing is a candidate; if the next call continues it, the thread moves to it, which is how the bridge follows a compaction it cannot see. A `CompactionEvent` resets the tip directly where one exists (Inspect, Claude Code, ATIF). Only a summary compaction (`type="summary"`) can have a summarizer; an edit or a trim ends the thread.
- **Utility only on evidence.** A call is utility only where the conversation demonstrably went on without it, or where it is the summarizer. Two calls that continue one tip are a fork: the one whose output is carried on is the turn, and the dead end is utility. A fork with nothing after it goes to the call whose output is in the conversation's final messages, which only the log driver has; where none is, it is left, with any calls still open, to the existing rules. Where the thread ends, a lone head is its last turn. *This replaces "else the later call" for a fork at the end:* a 2024 scaffold that resent the same input on every call made one 17-way fork that no call carried on, and that rule marked 16 real turns as utility.
- **The summarizer.** The call just before a summary `CompactionEvent` is utility only if its output appears in the next call's input, matched by fingerprint or by its text from the last `<summary>` tag, since Inspect wraps the summary in a preamble after dropping the `<analysis>` (refined by Charles 2026-10-26, option (b)). Otherwise it stays a turn. *Revised 2026-10-20 after review pass 2 (F8):* Inspect's compaction summary call continues the tip (its input is `system + input + conversation + [prompt]`, `model/_compaction/summary.py`) and is the only call that does, since the next turn's input is the compacted list, and the `CompactionEvent` is written after it (`_compaction.py`), so the fork rule alone would make it a turn; the prompt rules miss it too, since it uses the agent's own system prompt. The 2026-10-20 form made any call followed by a summary `CompactionEvent` before another call continued it utility, which dropped the last real turn where no summary call was logged (ATIF's terminus-2, a constructed Claude Code compact boundary). Two stated limits, each keeping a step rather than losing one: a summary reworded before it is sent stays a turn, and so does a summary call followed by another call before the compaction.
- **Failed calls.** A failed call is what its retry is; a retry sends the failed call's own input, and a failed call never retried is a turn.
- **Fingerprints.** Messages are matched by role, a hash of their text, and each tool call's id and function, since a turn that only makes tool calls has no text, and with role and text alone two different tool-call forks look equal. Message ids are not used, since they do not survive a scaffold's round trip; Scout's `_trim_prefix` (`_transcript/messages.py`) matches by text after trying ids. A scaffold that sends a tool call back under a new id breaks the link, and the existing rules decide that span.
- A span in which no call continues another keeps the existing rules' answer, so a scaffold that rebuilds its prompt every turn does not lose every turn.
- **Linear work.** Each call is compared at one position, not along its whole prefix, and fingerprints come from the message pool, each stored message hashed once. Every open input length is looked up until the thread settles its open calls; an input stored as pool ranges is looked up by its ranges, so the lookups are linear in the log as stored ([Nothing quadratic](#nothing-quadratic)). PR 6 counts the work at *n* and 2*n*.

Where `origin` is unset, the driver infers one for each call: a turn is `"agent"`, a call in a tool span `"tool"`, one in the `scorers` span `"scorer"`, one in `init` `"setup"`, and the timeline's other utility calls `"helper"`, so "Which steps ran" reads inferred origins as it reads recorded ones. A producing call that records an empty tools list, as the Claude Code importer's calls do, does not rule its tool calls out. With a stored timeline (`timeline=`), turns are inferred within its conversations, so each branch of a rollback keeps its generates (Ransom's B1 on #6098). The driver extracts agent results before it wraps utility calls, so a result that reached only a summary call's input is kept (B3). A transcript with no model events goes through the messages projection, routed by sentinel's adapter, its only caller, not by inspect_ai's driver.

**Only in replay's log driver** (decided by Charles 2026-10-26, Ransom's B2 on #6098, option (b)). The rule runs in the internal timeline `steps_from_events()` builds to infer turns, never in the public `timeline_build`, so the viewer, Scout's timeline scanners and Scout's streaming scan show the timelines they showed before PR 6. Scout's streaming scan builds its timeline from stub events, which keep no other input messages and no output text, both of which continuity reads, so a public rule would make Scout's streaming and materialized scans of one log disagree. Continuity in the public `timeline_build`, the viewer (ts-mono #817, deferred) and Scout waits for a coordinated change ([pr-series.md](pr-series.md), Deferred). The `_extract_agent_results` fix stays in the public `timeline_build`: it does not depend on continuity, and its output is unchanged.

Continuity is not applied where `origin` is recorded, since a scaffold that drops a turn's output would make it disagree with live. A source that knows its structure supplies a stored timeline, as Petri does with `"target"`, which `as_scanner(timeline="target")` reads, or its importer sets `origin`. Each result records how its turns were established (`"turns"`: `"recorded"`, `"inferred"` or `"stored"`).

**Measured in PR 6** (inspect_ai #6098 at `c1d4dc494`). Over PR 3's test logs with `origin` removed, 90 of 93 replay exactly as with it (1,570 steps). The three that differ are declared: a `model_origin("helper")` region, which is not in the span tree (4 extra tool steps, 1 step whose fields differ); two agents interleaved in one conversation (one generate's 2 steps missing, 10 steps whose fields differ); and a rollback replayed without its stored timeline (with it, every step agrees). The R7 end-to-end harness with origins removed agrees on 7 of 7 samples (138 steps). Over 44 transcripts from Scout's Claude Code, ATIF, LangSmith, Logfire, Phoenix and Weave importers, 87 of 87 calls are turns and none raises.

**Earlier decisions.** When the eval ran no sentinel (`eval.config.sentinel` unset), each `ApprovalEvent` from a person becomes a `HumanDecision`, published once its tool call's step settles, as live: stage `tool_call`, `step_id` and `call_ids` the call's id, `decided` a `Reported[Decision]` with the approver's name as its `name` and `path`, `approve` as `proceed` with the explanation, `reject` as `reject` with it as `message` and `explanation`, `terminate` as `terminate`, and `modify` as `modify` with the `modified` call. An `escalate` is passed on, not decided, and is skipped. Which approvers are people is fixed, with no argument (decided by Charles 2026-10-26): inspect_ai's built-in `"human"` approver, the registry name its `human_approver` records (`approval/_call.py`, `record_approval`), is a person, and every other approver is not. An option to name custom human approvers, such as a team's own Slack or ACP-based approval UI (AISI R9), is deferred until someone asks ([pr-series.md](pr-series.md), Deferred). The log driver's internal `human_approvers=` parameter (inspect_ai #5991) stays internal; sentinel passes `("human",)`. A person who decides through approval always leaves an `ApprovalEvent`, so a log without one gives `()`, not `None`. A log from an eval that ran a sentinel gets `human_decisions` from its `SentinelEvent`s only, as live, where approval's decisions were never in it.

### What replay cannot do

Replay reproduces the monitor's *reports*, not its *effects*. A `reject` in replay does not change the transcript; the agent already did what it did. This is the right limitation for measuring a classifier — precision and recall are about reports — but it means two things cannot be back-tested offline:

- **Interventions.** Whether rejecting call 7 would have led the agent somewhere better is a question for a live eval, not a replay.
- **Humans.** `human()`, a protocol with no children, cannot be replayed. The useful substitute is to *replay the recorded human decision* when the transcript carries a `SentinelEvent` from that `human()` instance for that step, so a `sequential` can be back-tested against the answers a person actually gave. The replay host does this in `ask_human()`: it reads the asking instance's path from the runner's layer state and answers with that instance's recorded decision at the step (`approve` for a `proceed`). Where there is none, the answer the scan's `human=` names answers, `reject` by default (`terminate` where `reject` is not offered), or a registered stand-in for the person; each result says which (decision R7-D5, revised 2026-10-26). A log from an eval that ran no sentinel has no `human()` instances; a person's `ApprovalEvent` for a call answers a `human()` at that call's `tool_call` stage, and reaches later steps as `human_decisions`.

## Step ids

Per-step validation needs each step to have an id that exists in an events transcript and **live, at the moment the monitor runs** — so that a label made once serves replay and also the read mode over recorded events. Tool call ids satisfy that. Generate steps used the last input message's id for the same reason, since a `BeforeGenerate` monitor runs before its `ModelEvent` exists; since R7-D8 the generate's id is its own, the `uuid` of its first `ModelEvent`, which inspect_ai mints before `BeforeGenerate` runs (inspect_ai #5990), so it exists live before the monitor runs and is recorded on the event. A messages-only transcript has no `ModelEvent`s, so it has no generate id; its projection names generate steps by position ([From events](#from-events)).

| Stage | Step id |
|------------------------|------------------------|
| `BeforeGenerate` | the generate's id: the `uuid` of its first `ModelEvent`, minted before the sentinel runs (R7-D8 and R7-D8a, decided 2026-10-20) |
| `AfterGenerate` | the same generate's id (R7-D8b, decided 2026-10-20) |
| `BeforeToolCall` | the tool call id |
| `AfterToolCall` | the tool call id |

*Until 2026-10-20* `BeforeGenerate`'s id was the last input message's, with an ordinal suffix on repeat (`{message_id}:2`) for a rejected call regenerated behind the same last message, counted per transcript. The generate's own id needs no ordinal: a provider retry inside one call keeps the generate's id, each `Model.generate()` call mints its own, so a regenerate gets a new one, and nothing counts in an order concurrency could change; two cache hits on one request no longer share an id (R7-D8b). Within one monitor's stage, ids are unique per transcript; a `BeforeToolCall` monitor and an `AfterToolCall` monitor both key by tool call id, but validation sets are per scanner so there is no collision.

**Consequence for `sentinel.md`:** `SentinelEvent` gains `step_id: str`, recorded by the runner live, so the read-mode scanner emits results with the same step ids the replay scanner does. *Built: `SentinelEvent.step_id` at all four stages (inspect_ai `_dispatch.py`, `_step_id`).*

**Computing them in replay** (revised 2026-10-20). Replay reads a generate's id from the `uuid` of its first `ModelEvent`. Logs written before R7-D8 used message-based ids live (Charles: "many old logs will not have this field, of course", said of the field then proposed), and a step id only has to equal live where a live record exists to join against: `SentinelEvent`s, `HumanDecision`s and labels. For such a log, a generate's step id is, in order:

1. **The recorded `SentinelEvent.step_id`**, wherever the step's `sentinel` span holds events. Logs from sentinel 0.1.x runs record the live ids in the old format (the last input message's id, with `:N` on a repeat), so read mode, `HumanDecision`s and labels still join.
2. **The `uuid` of the generate's first `ModelEvent` attempt**, as for a new log. Events have carried a unique id since inspect_ai #2097 (2025-07-05; `uuid` today). Attempts are grouped by inference, as for a new log.
3. **The generate's position within its conversation, in log order**, for logs from before event ids: deterministic, but not proof against concurrency, since two agents sharing a conversation number their calls in scheduling order.

Sources 1 and 2 match live where a live record exists; source 3 may not, for logs from before 2025-07. A log from an eval without a sentinel has nothing live to match, so its generate ids need only be deterministic and unique within the transcript, which sources 2 and 3 are.

## The scan unit and the validation unit

Three grains of label are in play, and they do not need three scan units:

| Grain | The label answers | Keyed by |
|------------------------|------------------------|------------------------|
| step | did this tool call or generate deserve a flag | transcript id and step id; the step's message or event |
| transcript | did this trajectory contain an attack | transcript id |
| protocol | did the configuration reach the right decision at this step | as a step; the result is the outermost layer's |

Five ways of getting the step grain into Scout were considered:

- **A `Step` scanner input type.** First-class, and the view could render it natively. But `sentinel.md` says monitors should be incremental, so nearly every real monitor is stateful across steps and needs its transcript's steps *in order with one store*. Scout's input model does not promise sequential in-order invocation within a transcript, so the new type would also need a new ordering guarantee. It buys less than it looks.
- **Scanning individual messages or model events** (Scout's `Scanner[ChatMessage]` and `Scanner[ModelEvent]`), considered 2026-10-20. Scout validates and shows these per item today. But it calls the scanner once per item with only that item, and a step is not a function of one item: `history` is folded from the conversation's earlier agent turns, `human_decisions` comes from earlier `SentinelEvent`s, a tool step joins a `ToolEvent` with its producing `ModelEvent`, turns without `origin` need the timeline, step ids count across the sample, and a stateful monitor needs its steps in order with one store. Rebuilding that context per item would be quadratic and still differ from live.
- **A `Sequence[Step]` input per transcript.** Preserves order, but the ids on a sequence input are the whole list, so validation cannot address one step.
- **A resultset per transcript, each result citing its step.** Chosen for R7, 2026-10-20. No change to Scout's rows: Scout records a list of results as one resultset row, its dataframe expands that into a row per result (`scan_results_df(rows="results")`, `_expand_resultset_rows` in `_scanresults.py`), and Scout View renders citations as links. What it does not give is Scout's validation at the step grain: a case matches a row's input ids, which for a resultset are the transcript's, and label validation is presence or absence per label, so "step 7 was flagged and should not have been" is not expressible.
- **Keep the transcript as the scan unit; make each result its own row.** Chosen on 2026-10-19 as `Result.subject`; deferred 2026-10-20 ([One row per message or event](#deferred-one-row-per-message-or-event)).

### The chosen shape

The adapter is a `Scanner[Transcript]`. It asks Scout for the events it needs, which Scout hands it expanded, rebuilds the message pool from them with inspect_ai's `condense_events()` so the log driver reads pool ranges as from a log ([Nothing quadratic](#nothing-quadratic)), builds the steps in one pass, runs them in order with one store for the transcript ([Cost and parallelism](#cost-and-parallelism)), and returns one `Result` per eligible step, as a list. Each result's metadata holds the step id and stage, and its `references` cite the step's message or event first, then whatever the report cites:

| Stage | The step cites |
|---|---|
| `BeforeGenerate` | its `ModelEvent` (`event`) where the transcript has events (decided by Charles 2026-10-26); else the last input message |
| `AfterGenerate` | the assistant message produced (`message`) where the transcript's messages hold it; else its `ModelEvent` |
| `BeforeToolCall`, `AfterToolCall` | the call's tool result message (`message`) where the transcript's messages hold it; else the `ToolEvent` that recorded it, as for a sub-agent's call; Scout has no reference kind for a tool call |

**Citations resolve and are labelled** (sentinel #135, decided by Charles 2026-10-26). Every reference the replay and read scanners emit carries a `cite` label, as Scout's own scanners write them: `[M<n>]` for the transcript's *n*th message and `[E<n>]` for its *n*th event, numbered by position, so one label names one reference across all of a transcript's rows. The result's explanation mentions each label, which is what makes Scout View render it as a link: `Step [M3]: ` before the monitor's own explanation, which is kept intact, then `Also cites [M5].` for any label the text does not hold; a `results="transcript"` row adds `Also set at ...` for the other steps that set it. A label a report gave its own reference is mapped to that reference's position label, and the report's explanation is rewritten to match. No reference is unresolvable: a message the transcript's messages do not hold, such as a sub-agent's tool result, is cited by the event that recorded it (the `ToolEvent` with that `message_id`, or the `ModelEvent` whose output it is), and a reference that resolves to neither is dropped. Steps cite their message where the transcript holds it rather than always their event, because following an event link moves nothing in Scout View's result panel today while a message link scrolls to the message; a `model_input` step keeps its `ModelEvent`. Making citations visible on the viewer's side, including highlighting event references, is Scout #750.

``` python
as_scanner(monitor, results="step")        # one Result per step, in the transcript's resultset
as_scanner(monitor, results="transcript")  # one Result; transcript id, as today
```

State stays where `sentinel.md` already puts it; Scout's parallelism across transcripts is untouched; and the transcript-grain form is the same adapter reducing to one result by max suspicion or strongest decision, with `references` to the flagged steps. A transcript's results come back together from one scanner call, so a resumed scan never holds half a transcript.

`results=` was `unit=` until Charles renamed it on 2026-10-26, so "unit" names nothing in replay. One rule keeps the rows unambiguous: **a step id and stage are unique within one scanner's results for one transcript.** The adapter emits one result per step for the monitor being scanned; a protocol's child reports go in that result's metadata. To scan a leaf inside a protocol, wrap the leaf directly. A tool call's two steps share its id, so each result carries its stage in its metadata. *Decided by Charles 2026-10-26:* `stage=` is optional; with `None` every stage the instance watches gives rows, and `as_scanner(..., stage="tool_result")` narrows them to one stage. Naming a stage the instance does not watch is an error. Scout's summary of a scan averages across stages unless `stage=` is passed, which the docs say. It was first required for an instance watching several stages. *P3-F4, accepted by Charles 2026-10-26:* `stage=` selects which results are emitted, not which functions run: the runner executes every stage the instance watches, in order, as live does, so a monitor whose stages share state (`examples/trajectory.py`'s `failure_count`, whose `AfterToolCall` function counts failures that its `BeforeToolCall` function scores) sees the same state as live; the other stages' reports are computed and not returned, and their model calls are charged to the scan. `steps=` still skips invocations, so a monitor's state across skipped steps is lost, as [Mapping `Report` to `Result`](#mapping-report-to-result) says.

**Labels without Scout changes.** Per-step labels are a table keyed by transcript id and step id, with an optional split; the results dataframe joins it on the same keys. `as_scanner(steps=labels)` takes the table directly ([Mapping `Report` to `Result`](#mapping-report-to-result)), and `calibrate(target_recall=)` joins it ([Calibration](#calibration)). Scout's own validation metrics and its case editor at the step grain wait on the deferred rows below.

### Deferred: one row per message or event

Decided 2026-10-20 by the maintainer, splitting what was then Scout's PR 4 (itself dropped on 2026-10-26). The first design gave `Result` an untyped `subject`, the step id, and recorded each subject-bearing result as its own row with `input_ids` `[transcript_id, subject]`. Two things were wrong with it. A step id is not something a user can find in a transcript, so no label could be written except from a results row. And Scout can already validate a message or an event: a message or event scanner's row has the message id or event uuid as its input id (`get_input_type_and_ids`, `_scanner/util.py`), and `_validate_scan` (`_scan.py`) matches a case against it; what is missing is only that a result's id is always the id of what the scanner was called on.

So the later change is smaller: **a transcript scanner's results may each name the message or event they are about**, using the input kinds Scout already has. Each is recorded as its own row with that id and kind, and Scout validates and shows it exactly as it does a message or event scanner's row: matching, predicates, splits, metrics and the `validation_*` columns do not change, and no `[transcript, step]` pair is needed, since message ids and event uuids are unique across a corpus. A label made by clicking a message or event in the transcript then matches with no sentinel knowledge. The stages map as the table in [The chosen shape](#the-chosen-shape) does; a `BeforeGenerate` step in a transcript of messages only cannot be labelled at that stage. One existing limit carries over: `Transcripts.for_validation()` selects transcripts by `sample_id`, so a set of message or event ids selects none, as is already true for message scanners.

It is deferred because only validation and labelling inside Scout at the step grain need it, and R7 does not; a pandas join over the resultset covers the development loop meanwhile.

`"sentinel"` is already in Scout's `EventType` (`_transcript/types.py`), so a scanner can ask for these events; the earlier note that Scout must add it is done.

## Mapping `Report` to `Result`

| Report | `value` | `answer` | `metadata` | `label` |
|------------------------|------------------------|------------------------|------------------------|------------------------|
| `Observation` | `suspicion` — float or dict | — | step id, stage, monitor metadata | instance path |
| `Decision` | flagged: `action` in `reject`, `modify`, `terminate` | `action` | step id, stage, `audit`, `modified`, child reports | instance path |
| abstained | `None` | `None` | step id, stage | instance path |
| failed (a monitor raised) | the transcript's scan raises: no row, the transcript's result is an error | | | |

Every result's `references` cite the step's message or event first ([The chosen shape](#the-chosen-shape)). Three things the table encodes:

- **A dict suspicion is kept whole**, so per-dimension metrics come from the dataframe, and from Scout's existing dict-target validation once rows are per item.
- **A decision's value is a boolean flag; an abstention's is `None`.** A per-step label set will label steps the monitor abstained on, and abstention produces no report, so the adapter emits a result for every step at the monitor's stage, `None` on abstain. In the label join that stands in for step-grain validation until per-item rows exist ([The scan unit and the validation unit](#the-scan-unit-and-the-validation-unit)), `None` counts as not flagged for a decision and as no score for an observation; the docs and `calibrate()` say so. Mapping a decision to a boolean, not its action, keeps the join honest and leaves the action in `answer` for anyone sweeping on it. *P4-F10, accepted by Charles 2026-10-26: this item described Scout's `eq` predicate at the step grain, which waits on the deferred rows.*
- **`escalate` is not flagged.** It is "I decline to decide", not a verdict. Inside a `sequential` it also means "worth a person's look", which a reviewer might want to count; `answer` carries it for that. This is a default that is cheap to get wrong, and it is recorded as a decision rather than left implicit.

The `explanation` and the rest of `references` map directly from the report's own fields — an LLM monitor using Scout's `message_numbering` in its prompt gets cites for free.

**`results="transcript"`** (settled 2026-10-19, answering open question 3) reduces the step results to one: for a monitor, the maximum suspicion, per dimension when it is a dict; for a protocol, the root's strongest decision across the steps (`terminate`, then `reject`, `modify`, `escalate`, `proceed`); `references` the steps that set it. Taking the root's decision is what a protocol result already means at the step grain ("the result is the outermost layer's").

**Replaying a chosen subset of steps.** A selector is `(transcript_id, ReplayStep) -> bool`, since a tool call id is not unique across transcripts and a sub-agent's conversation is not the transcript; the adapter binds it to each transcript and hands the internal runner a one-argument predicate over `ReplayStep` (P5-F3). `as_scanner(..., steps=...)` takes forms its scan spec can carry: a table directly, as a DataFrame with `transcript_id` and `step_id` columns and optionally `conversation` and `stage`, a Scout results frame, whose conversation and stage it keeps, or pairs, saved in the spec as `(transcript_id, conversation, stage, step_id)` rows, a row with no conversation or stage selecting its step in every one, since two agents' tool calls can share an id and a call's two steps do (revised 2026-10-29); or a selector registered with `@step_selector`, or its name. `StepsIn` and `steps_in()` are not public. A selector defined in a notebook is refused with a clear error, since a worker cannot import it; the docs show the workaround, a `.py` file next to the notebook, and an in-process fallback is deferred. Given a table, the scanner returns early, before rebuilding steps, for a transcript the table does not list; Scout has no scanner-level transcript filter, so the docs also show narrowing the scan's transcripts. *P4-F4, P4-F5 and P5-F3, accepted by Charles 2026-10-26, with `steps=` taking a table directly.* The pass still builds every step of a listed transcript, which costs no inference; the runner invokes the sentinel only for the chosen ones, so the transcript's store sees only those. With R10 a monitor that needs the earlier conversation reads `history`, so AISI's subset is "only run these steps", as their follow-up said.

## Two modes: replay and read

Both key results by transcript and step id and cite the same message or event, so their rows join.

| Mode | What runs | When |
|------------------------|------------------------|------------------------|
| **replay** | reconstruct steps, run the monitor, one result per step | you changed the prompt, the model, or the monitor's logic |
| **read** | walk the transcript's recorded `SentinelEvent`s, one result per event | you want to know how the monitor behaved in the run it was attached to |

Read mode costs no inference and is what makes "run the eval observe-only, then look" a real workflow rather than a slogan. It is also the only mode that sees what the protocol actually did with each report, from the decision events at the parent paths, so "how often did `resample` substitute a draw" is a read-mode query.

Read mode also gives the honest check on replay itself: replay the monitor over a log it was attached to, and the two modes should agree wherever the monitor is deterministic. Where they do not, the reconstruction is wrong, and that is a test worth shipping.

**The read-mode scanner** (designed 2026-10-19, PR 5): `as_reader(path="", *, stage=None)` in `inspect_sentinel.scout`, a transcript scanner; `path` defaults to `""`, the root (decided by Charles 2026-10-26). *P3-F6, read-mode citations, accepted by Charles 2026-10-26.* It asks Scout for the `sentinel` events, and for the model and tool events and messages its citations need, with the pool rebuilt as replay rebuilds it, and builds the same lookup indexes as replay (a generate's `ModelEvent`s by first-attempt `uuid`, a tool call's result message by `ToolEvent.message_id`), inferring nothing else. For a log from before R7-D8, whose generate-stage step ids are message ids, it associates a recorded generate step with its `ModelEvent` by identity first: an `AfterGenerate` step's old id is its output message's id, so it cites the `ModelEvent` whose output message has that id. A `BeforeGenerate` step's old id is the last input message's, which several calls can share, so it is associated by position, the next model event after its `sentinel` span, only within the same conversation and only when no other generate in that conversation overlaps it; otherwise it cites nothing, a stated limit. The same association serves replay's old-log fallback. *P4-F9 and P5-F2, accepted by Charles 2026-10-25 through inspect_ai #5991 (call 11).* The pass-4 rule chose neighbouring events by position alone; a `ModelEvent` is placed when its call starts, not when it completes, so overlapping generates could cite each other's output. A recorded step with no underlying event or result, such as a `BeforeGenerate` that left no `ModelEvent` (R7-D11), cites nothing and carries its step id and stage in metadata. For the instance at `path` it emits one result per `SentinelEvent` with status `reported` (and `superseded` for a decision, with the status in metadata), carrying the event's `step_id` and citing the step's message or event, with the labels and the resolution rule replay uses ([The chosen shape](#the-chosen-shape)), mapped as [Mapping `Report` to `Result`](#mapping-report-to-result) maps a live report. An `error` event is a failed monitor, and the scan raises as replay does: read mode stays strict on recorded failures (decided by Charles 2026-10-26). A step the instance watched but did not report on (it abstained) has no event; the reader emits nothing for it, and the agreement test below compares only steps both modes report.

**The agreement test** (PR 5). A probe monitor, `replay_check()` in `inspect_sentinel.scout` (first named `fidelity_probe()`; renamed by Charles 2026-10-26), watches all four stages and reports `suspicion` `0.0` with metadata holding a digest of every field of the step it was handed: per field, a hash of its JSON form, with the fields replay leaves absent (the list the live-equals-replay test names) left out. A test runs a set of scripted mockllm evals with the probe attached, then scans the logs through Scout, at each stage once with `as_scanner(probe(), stage=...)` and once with `as_reader("probe", stage=...)`, and asserts that both report the same set of `[transcript, step]` keys, which the probe allows since it never abstains, except a `BeforeGenerate` that left no `ModelEvent`, which read mode has and replay refuses as unsupported (R7-D11, revised 2026-10-26), and that for every key the metadata is equal. *Revised 2026-10-20 after review pass 1:* the probe also digests `context.eval` (task, sample id with its type, epoch, descriptions, input and metadata), and the evals include an integer sample id, a numeric string id, a sample description and a message-list input, so a context replay gets wrong fails the test too. The live-equals-replay test in inspect_ai compares the steps themselves; this one checks the whole path a user takes, through Scout's loading, the runner, the replay host and the resultset. *Revised 2026-10-20 by the maintainer: the probe is public.* It is the check AISI's R7 asks for ("the monitor behaves identically and receives identical context whether it is in live or backtesting mode"), and only a user's own scaffold and logs can show it holds there: attach `replay_check()` to an eval observe-only, scan its logs with `as_scanner(replay_check())` and `as_reader(...)`, and compare the two with the helper PR 5 adds, `replay_check_differences(replayed, recorded)` (first `replay_check_report`, a working name), which takes the replayed and recorded scan results and lists each step, stage and field whose digest differs, and the steps present on one side only (decided by Charles 2026-10-26). Any deterministic monitor can be compared the same way, but only the probe compares the context itself. Its digests of `history` and `human_decisions` are by length and last element, and its digest of `context.eval` is computed once per transcript and reused ([Nothing quadratic](#nothing-quadratic)); `agent_messages`, `None` in replay, is left out. *P3-F7, accepted by Charles 2026-10-26.* Hashing every `human_decisions` record at every step is quadratic in a transcript with many `human()` answers, and the context is the same at every step. So the probe checks the length and the tip, not the interior; since both sides fold the as-sent snapshots (decided by Charles 2026-10-26, #5990 call 2), an edit made in place after sending does not differ between them. *Review pass 2 (F7) suggested a rolling hash extended per appended message; it would not see an interior difference either, since the hash is taken when a message is appended, and rehashing every list at every step is quadratic, so the probe's limit is stated instead.*

## The workflow

1. **Write** the monitor as `sentinel.md` describes, and unit-test it as any async function over hand-built steps. A public API for replaying a monitor over a hand-written conversation is deferred until monitor authors ask for one (2026-10-26).
2. **Replay** it over a corpus with `as_scanner()` and look at what it flags in Scout View.
3. **Label** steps from the results dataframe, where each step is a row citing its message or event, as a label table with `dev` and `test` splits. Labelling in Scout's case editor waits on per-item rows (deferred, [The scan unit and the validation unit](#the-scan-unit-and-the-validation-unit)).
4. **Validate**: precision, recall, F1, balanced accuracy over the `dev` split. Change the prompt; bump the monitor's version; re-scan; compare. A join of the label table and the results until per-item rows exist; Scout's existing loop after.
5. **Calibrate** thresholds (below) if the monitor is an `Observation`.
6. **Configure** the protocol with those thresholds and attach it to the eval — observe-only first.
7. **Read** the resulting logs in read mode to confirm the deployed behaviour matches the replayed one, then let it act.

Steps 2–4 are exactly what a scanner author does today. The monitor-specific parts are the adapter in step 2 and calibration in step 5.

## Calibration

`sentinel.md` insists thresholds live in protocols, not monitors, because a threshold needs a benign score distribution and a monitor looking at one step has never seen one. This is where the distribution comes from.

**From a benign corpus.** Replay an `Observation` monitor over transcripts known to be benign. The results dataframe's `value` column *is* the benign distribution. A budget becomes a threshold by percentile: "audit the top 1%" is the 99th percentile of that column, per dimension when suspicion is structured.

**From a labelled corpus.** Replay over a corpus with numeric or boolean step labels and join the results with the label table; sweeping a threshold over the scores gives the precision–recall curve (Scout's `gte` predicate does this itself at the step grain once per-item rows exist, which are deferred), and the operating point is a choice the author makes with the curve in front of them rather than a constant in a prompt.

A helper closes the loop:

``` python
thresholds = calibrate(results, budget=0.01)          # percentile per dimension
thresholds = calibrate(results, target_recall=0.95)   # from labels
Task(sentinel=threshold(suspicion_monitor(), reject_at=thresholds["sabotage"]))
```

It is ordinary pandas over a Scout results dataframe. It lives in inspect_sentinel, as one of the development loop's verbs, and uses Scout for the scanning (workstream 10, reframed by the maintainer on 2026-10-02). What matters more than the helper is that the *inputs* to it — recorded scores, including ones a protocol ignored — are produced by the runner as a matter of course, which is why `sentinel.md` records them.

The calibration corpus should be held out from the validation set's `test` split, and a threshold derived from one model's scores is not a threshold for another model's; both are ordinary ML hygiene rather than framework concerns, but the docs should say them. `calibrate()` does not refuse a split used for validation: split names are free-form, so it cannot tell which split a later evaluation reports on (open question 7, 2026-10-20).

## Monitors as scores

`sentinel.md`'s open question 11 asks whether a monitor can produce a `Score` beside the task's own scores. It can, without touching scoring:

``` python
Task(scorer=[my_task_scorer(), as_scorer(as_scanner(suspicion_monitor(), results="transcript"))])
```

`as_scorer()` already turns a transcript scanner into an Inspect scorer. The transcript-grain adapter reduces the monitor's per-step reports to one value, so the monitor's suspicion appears in the log as a score with the usual metrics, and the flagged steps travel as `scanner_references` in the score metadata, which Inspect View already renders. Nothing in `inspect_ai.scorer` changes.

## Cost and parallelism

An LLM monitor over a corpus is one inference call per eligible step, which is many more calls than one per transcript. What keeps it tolerable:

- **Incremental monitors are cheaper to replay**, not just to run — the design's insistence on classifying the newest turn and folding into state means replay cost is linear in steps rather than quadratic, and the transcript's one store is what makes that work.
- **Stage filtering happens before loading.** The adapter declares the content it needs from the stages the instance watches (all of which run, P3-F4): messages, and the event types the log driver reads (`model`, `tool`, `compaction`, `approval`, `sentinel`, and `span_begin` and `span_end` for the cut and the conversation), so Scout loads nothing else.
- **Parallelism is across transcripts and processes**, as for any transcript scanner (Scout's `max_transcripts`, default 25, also the default `max_connections`, and its worker processes); within a transcript, steps run in order.

**One pass per transcript** (decided by Charles 2026-10-26). After the step pass, the runner runs a transcript's steps in log order, with one `Store`, recorder and replay host for the whole sample, the live scope. Units, concurrent groups of a transcript's steps designed on 2026-10-19 (`split`, `max_units`, `max_unit_steps`, with a fresh store at each cut), are gone: Scout already runs transcripts concurrently across tasks and processes, and units bought wall-clock time only for a corpus of a few very long transcripts, at the cost of state a stateful monitor lost at each cut. Opt-in parallelism within a transcript is deferred until such a corpus needs it ([pr-series.md](pr-series.md), Deferred).

**Prompt caching.** Steps run in order, so each monitor prompt can extend the last.

**Resume.** Scout records and resumes a scan by transcript (`_recorder/recorder.py`, `resume`): a transcript's rows are written together, so an interrupted scan re-runs only transcripts it had not finished, and a long transcript is re-run whole.

Monitor inference in replay is charged to the scan, never to anything resembling an agent limit, which is the replay form of the budget exemption approvers have in an eval.

## Showing replay can be trusted

*Proposed 2026-10-20 at the maintainer's request; PR 7, sentinel #150.* PR 3's test shows the steps are rebuilt equal to live on scripted evals, and PR 5's `replay_check()` shows a monitor is handed the same fields. Neither shows that a production monitor, one that judges with a model, behaves the same on replayed steps as it did live, which is what AISI's R7 asks back-testing to establish ("the monitor behaves identically and receives identical context whether it is in live or backtesting mode"). This step measures it, on haystacks with planted needles and on real runs, and records the numbers.

**Internal validation** (decided by Charles 2026-10-26). The benchmark is sentinel's own check, not part of the package: users never run it, the user docs do not mention it, and its how-to-run, acceptance rules, spend and results are in `benchmarks/replay_trust/README.md`, not on a published docs page. Its first form also ran on a user's own logs and monitors; that mode is removed. Users check their own replays with `replay_check()` and `replay_check_differences()`, and a user-facing check of verdicts on their own logs waits until AISI asks (Deferred in [pr-series.md](pr-series.md), added by sentinel #150).

**Monitors.** The shapes in production use, each run observe-only so that its reports are recorded and nothing it decides changes the run:

- a tool-call judge on `Host.score()`, as in `examples/llm_suspicion.py`, with its `StepPreprocessor` windows (`LastTurns`, `NewSinceLastReport`, which resumes in constant time from a `(last_id, copies, length)` mark, sentinel #133), at `BeforeToolCall`;
- a whole-turn judge at `AfterGenerate`, reading `history`;
- a rule with no model, such as `examples/no_network.py`;
- an incremental monitor that keeps state across steps, such as `examples/trajectory.py`;
- AISI's sync monitor, if AISI shares it or runs the harness on their side.

**Haystacks.** Scripted agents (mockllm), so a trajectory is the same in every run while the monitors' model is real: ordinary work over 100 and 300 turns by default (Charles, 2026-10-26; 20 turns stays available as a quick smoke check, usually inconclusive by the minimum below), with a summary compaction, parallel tool calls, a sub-agent through `as_tool()`, a provider error retried and a `human()` answer, and one to three needles planted at known steps, each a tool call the policy forbids (sending a file to an outside host, writing outside `/work`, disabling a test). Beside them, real runs: a small set of real agent tasks with the same monitors attached live, where the needles are whatever the agent did, labelled by hand; these are not yet run.

**Measurements**, per monitor and haystack:

1. **The same prompt.** The monitor model's request live (its `ModelEvent` inside the step's `sentinel` span) and in each replay (the scan's model events), compared after replacing the nonce, which differs by design (`Host.score()` keeps it in the store, fresh per transcript): every difference is traced to a known difference ([How exact replay is](#how-exact-replay-is)) or reported as unexplained. This checks "receives identical context" for a real monitor, with no model noise in it.
2. **The same verdict.** Per step, whether each run's score crosses the monitor's threshold, compared for each pair of a live run and a replay (two live runs, two replays, so four pairs). A model's answer varies between calls even at temperature 0, so live against live and replay against replay are the noise reference.
3. **The same needles found.** Each labelled needle one by one, and recall and the false-positive rate, with intervals, as a description.
4. **The same human answers.** Each call a person answered live through `human()` is answered in both replays as the person answered it.

**Trusted means** (designed after PR 7's review pass 3, decided by Charles 2026-10-26), stated as PR 7's acceptance:

- **Decided per monitor and haystack.** Each cell is decided on its own and haystacks are never pooled; a monitor is trusted only where every haystack is.
- **Three outcomes: trusted, not trusted, inconclusive.** A cell is not trusted where anything differs: a prompt outside the known differences, in either replay; a step without a row in some run; a needle changed; a person's answer not given again; or a paired test that rejects. It is inconclusive where its sample is too small to detect a difference that matters, or nothing was measured, and trusted otherwise. Evidence of a difference counts at any sample size; below the minimum a cell is never trusted.
- **The minimum.** The smallest difference that matters is one step in ten flagged differently. Measurement 2's eight tests share 5%, so each is at 0.625%, where an exact McNemar test needs nine discordant steps, all one way, to reject: a cell needs 90 compared steps, and one needle the live runs agree on. This is the size at which such a difference can be detected at all, not a power target.
- **Needles one by one.** A needle the two live runs agree on, both flagging it or neither, must be flagged the same way in both replays, so equal counts cannot hide one needle lost and another gained.
- **Paired tests.** The runs score the same steps, so each live-and-replay pair gets two exact two-sided McNemar tests on the per-step flags: a shift in what is flagged, and disagreement beyond the live-against-live noise. Both replays are gated. Where neither noise pair disagrees at any step, as with a deterministic monitor, any live-against-replay difference is not trusted.
- **Live rows must exist.** Read mode records nothing where a monitor abstained, so a step without a row in every run is unmatched, and not trusted, unless the live log records the abstention; the benchmark's monitors record theirs.
- **Error across cells** is held at 5% within a cell and not corrected across cells and monitors, which the README says.

A miss is a replay bug or a new known difference, and is recorded as one.

**Where it runs.** Not in CI, since it calls real models; CI runs the whole pipeline on deterministic models so the harness does not break between real runs. A script in sentinel (`benchmarks/replay_trust/`), with its haystack generator and labels; rerun before a release that changes the step builder or replay. Its cost is one model call per monitored step for each of two live runs and two replays: four times the steps, times the monitors that call a model.

**First results** (sentinel #150, 2026-10-26). With a deterministic judge, every monitor is trusted on the 100- and 300-turn haystacks. The first run with a real monitor model, `openai/gpt-4o-mini`, over the default haystacks with all four monitors, was trusted on both, with no findings, for 4,297 model calls and $1.80. Every prompt difference in that run was the `agent_messages` block that the default `StepPreprocessor` named as unavailable in replay, which sentinel #152 removes ([Reconstructing `agent_messages` in replay](#reconstructing-agent_messages-in-replay)). No stronger monitor model was run.
