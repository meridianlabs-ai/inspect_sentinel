# Requirements: the AISI sync monitor

External requirements from AISI (UK AI Security Institute), 2026-10-08, for moving their internal sync monitor onto Inspect Sentinel. The first section reproduces the document as received, lightly formatted. The rest is ours: what is met today, where each requirement sits in the plan, where a requirement conflicts with a recorded decision, and a suggested order.

Status: received 2026-10-08, and first checked against inspect_sentinel `main` and inspect_ai `feature/sentinel` on that date; statuses rechecked on 2026-11-23 against the inspect_sentinel 0.4.0 release (`main` at f85cbec), inspect_ai 0.3.292 and inspect_scout 0.6.4, the dependency floors. Each requirement's section keeps its earlier assessments as history. AISI's follow-up the same day ([PR #66](https://github.com/meridianlabs-ai/inspect_sentinel/pull/66#issuecomment-6064370831) comment, reproduced below) narrows R2, R4, R5, R6 and R7 and adds R10; the sections after it reflect the narrowed requirements. Priorities and the remaining choices are for the maintainer to decide; nothing here changes a recorded decision.

## The document

**Context.** We are refactoring our internal sync monitor to use Inspect Sentinel, but so far we have run into a few limitations that stop us doing it fully without workarounds. We have monitors that run before tool calls and monitors that run after them. The pre-tool-call monitor runs once per step and sees all of that step's tool calls at once. The post-tool-call monitor runs separately after each tool call.

### R1: escalation to human review at AfterGenerate

**What we need:** A protocol at AfterGenerate can return escalate. A monitor there sees the whole assistant turn, before any of its tool calls run. human() can review the turn at that stage. The human reviewer sees the turn's tool calls and step.escalations, and can at least approve, so the turn proceeds unchanged, or terminate.

**Why:** Our monitors judge a turn as a whole, because the combined effect of parallel calls matters. We need to be able to escalate from our monitor to human review.

### R2: exact step.input at AfterToolCall, or an explicit failure

**What we need:** At AfterToolCall, step.input is exactly what was sent to the model call that produced step.call, however long the run and even when older transcript events are no longer resident. When the exact input isn't available, the monitor can tell, rather than silently getting history in its place, and replay (R7) gives the same step.input. This may be worth having at BeforeToolCall too, but we only need it at AfterToolCall.

**Why:** Our tool-result monitors judge each result in the context the agent actually had. After a compaction that is a summary plus recent turns, not the whole history. If that record is lost we fail closed. Showing the monitor the fuller history instead may show it context the agent never had without anyone knowing, which we want to avoid.

### R3: the step's tool definitions and truncation at AfterToolCall

**What we need:** At AfterToolCall, a monitor can directly get the exact tool definitions offered to the model call that produced step.call (as AfterGenerate has in step.tools). It can also tell whether step.result was truncated, through one signal that is the same live and in replay. The tools may be worth having at BeforeToolCall too, but we only need them at AfterToolCall.

**Why:** What a tool does changes how suspicious a call to it is, so our tool-result monitors show the definitions of the tools the agent actually had for that step. At the moment the only way to get them at AfterToolCall is to scan transcript events for the producing model call. Our monitors also judge the result as the model saw it, and mark truncation in a way the agent can't forge. Live, we can work truncation out by comparing step.result with step.output, but the untruncated output isn't in the log, so replay needs another source.

### R4: a monitor can see earlier decisions in its conversation

**What we need:** A monitor can see the decisions recorded at earlier steps of its conversation, for example that the human() link approved the turn or call escalated at step X. This works at AfterGenerate (R1) and the tool stages, and in replay (R7).

**Why:** When a person approves a flagged action, our later prompts mark those calls as approved, so the monitor doesn't flag them again in isolation and the person isn't asked again and again. The approval is a decision by the human() link of a sequential, and a monitor can't see another layer's decisions; step.escalations covers only the current step.

### R5: escalate or terminate on monitor scores, without rejecting

**What we need:** A built-in protocol, whether an extension of threshold or something new, that turns monitors' suspicion into escalate at one score and/or terminate at another, without also requiring a reject score. It works at AfterGenerate (R1), BeforeToolCall and AfterToolCall, and can combine monitors that watch different stages. Each decision's explanation includes every contributing monitor's score and explanation.

**Why:** None of our configurations rejects: a rejection tells the agent no, and the agent keeps trying variations. Ours terminate, or escalate to a person, above a score threshold. Two of our monitors act at AfterToolCall, and one configuration combines a proposed-action monitor with a tool-result monitor. The reviewer needs to see why the action was flagged, and where monitors disagree.

### R6: an unhandled escalate doesn't let the action through

**What we need:** When the root's decision is escalate, at any stage, the action does not proceed, and the log shows what happened.

**Why:** A flagged action must never run without someone deciding. At the moment a root escalate proceeds with a warning, so a misconfigured chain, such as a threshold that escalates with no human() after it, lets the action through. Inspect's approval doesn't in the same situation.

### R7: efficient replay over existing logs

**What we need:** A way to run the exact same @monitor over stored eval logs. Replayed AfterGenerate and AfterToolCall steps carry what the monitor would have seen live (the exact input, tools, and result with its truncation), including after a compaction and in logs from before Sentinel, where approvals are ApprovalEvents. Each step's Observation can be matched to the same step live and in replay, and a chosen subset of steps can be scored. Replay parallelises well and makes good use of provider prompt caching, while each step still sees the store_as state it would have had live. Live and replay stay identical as Sentinel changes.

**Why:** We need to be confident that backtesting results are valid i.e. that the monitor behaves identically and receives identical context whether it is in live or backtesting mode. Backtesting can be slow for long transcripts and we want to make sure we can run backtesting as quickly and efficiently as possible. For reference, our current implementation runs transcripts and compaction segments in parallel (optionally splitting long segments further), and steps in order within each segment so we can make use of provider prefix caching.

### R8: monitor-safe message rendering

**What we need:** The shared message renderer (Scout's messages_as_str and MessageFormatOptions, which pr-series.md plans to move into inspect_ai) meets the needs in the table below, so a monitor's view of the transcript becomes configuration rather than our own ~650 lines of rendering.

**Why:** We need secure transcript rendering that can't be tampered with / injected by the agent, and we need to support certain configuration of what is shown to the monitor from the transcript.

| | Need | Detail |
|---|---|---|
| 8.1 | Agent text can't forge structure | No message content, argument value or tool output can be mistaken for the rendering's own structure. format="json" already protects message boundaries; we also need it inside a message: tool calls and results, errors, \<thinking\> blocks and harness-set markers. |
| 8.2 | An actions-only view | Tool calls can be rendered without the assistant's prose around them, with or without reasoning. exclude_tool_usage does the opposite. |
| 8.3 | Compaction summaries | Readable summaries are shown as summaries rather than \<data /\>; unreadable ones are optionally left out. |
| 8.4 | Tool result status | Whether a result was an error, or was truncated (R3), is shown in a way the agent can't fake. |
| 8.5 | Referring to earlier calls | Tool calls can be identified, so a prompt can say which ones a person approved (R4). |
| 8.6 | Prompt caching | Per-message output, as format="list" gives now, survives the move. We put each turn in its own ContentText block so the prompt prefix stays cacheable. |
| 8.7 | Content it can't show | A monitor can tell when the transcript holds content that can't be rendered as text, such as images or unknown types, so it can fail closed. |
| 8.8 | Tool definitions | Tool definitions (ToolInfo) can be rendered. |
| 8.9 | Withheld messages | A deployment can withhold messages it has flagged from the monitor (for example a jailbreak prompt in a red-team eval), and the monitor can tell something was withheld. In general it would also be useful to have a well thought out escape hatch for message rendering so that it is possible to modify the rendered transcript (but hard to do accidentally or for the model to do) for e.g. ControlArena where we want to test the monitor by giving the agent a red team prompt that the monitor can't see. |

### R9: human() routed to a team's own review tool

Lower priority than the rest.

**What we need:** A task can route human() to its own review channel rather than inspect_ai's built-in human_approver panel, at the tool stages and at AfterGenerate (R1).

**Why:** We may want to use our own approver UI. Currently some teams do and may want to continue using their implementation, and escalated actions need to reach it.

## AISI follow-up (2026-10-08)

Received as a comment on PR #66, lightly formatted. It answers the conflicts listed below and adds one request.

**R6 (root `escalate`).** An opt-in is enough: a task-level or root-level setting that makes an unhandled `escalate` fail closed. The default can stay as recorded. `terminate` is fine as the fail-closed action at every stage; `reject` is never needed here.

**R2 (fallback to history).** Any explicit signal works: `input` being `None`, a flag on the step, or an exception. Keeping a fallback is fine too, as long as the step says it fell back. What must be avoided is a monitor silently judging context the model was never sent.

**R5 (`threshold` explanations).** Each monitor's observation is already a `SentinelEvent`, so the log is covered. This only matters for what the person reviewing an escalation sees: every contributing monitor's score and reasoning should reach `human()`, whether through the explanation, `step.escalations` or metadata.

**R4 (earlier decisions vs monitor independence).** Narrowed: only earlier decisions by protocols, in practice `human()` approvals of escalations, and only at steps before the current one. Other monitors' observations, at the same step or earlier, are not needed, so the independence property can stay as it is.

**R7 (concurrent segments vs `store_as` state).** The only state across steps is the agent's opening prompts as they were sent to the model, recorded at a conversation's first monitored step so they survive a compaction that drops them from later inputs. With R10, monitors would keep no state across steps, the conflict goes away, and step selection is just "only run these steps".

### R10: the history as sent to the model

**What we need:** A second field beside `step.history` holding every message this agent instance has sent to the model, in the order sent. It is scoped to one agent instance, so sub-agents and parallel agents in the same sample are not mixed in. `history` stays as it is. It works live and in replay. Open question: how to show a message the scaffold edits after it was sent; keeping each version in the order it was sent seems right, but any consistent answer works.

**Why:** `step.history` is the scaffold's list, which can differ from what the model was sent, for example when a scaffold edits messages before sending them. The only as-sent view is `step.input`, which covers only the current call. This gives the opening prompts and the pre-compaction context as the model actually saw them, without monitors keeping state, live and in replay, and resolves the R7 conflict. It depends on the same `conversation` id on events that R4 and R7 need; [sentinel-development.md](sentinel-development.md), "From events", already sketches rebuilding history per agent from `ModelEvent`s and `CompactionEvent`s sharing that id.

**R6** (narrowed: an opt-in is enough; decided 2026-10-10 as the default). *As assessed 2026-10-08 and 2026-10-10, superseded:* A root `escalate` proceeds, stays recorded as the root's decision, and warns once per process (`_dispatch.py`, `_run`; [pr-series.md](pr-series.md), "Root and escalate"). Decided 2026-10-10 ([pr-series.md](pr-series.md), "Unhandled escalate"): an escalate that reaches the root is a configuration bug, and sentinel's `run_sentinel` turns it into a terminate at every stage, recorded as unhandled; `handle_escalation("terminate" | "continue")` states a policy explicitly, and typed decisions (a follow-up) catch a provably unhandled escalate when the sentinel is built. **R7.** Met since 0.3.1 (sentinel #135, #151, on inspect_ai's log driver), extended in 0.4.0 (sentinel #193 and #245, on inspect_ai 0.3.292 and inspect_scout 0.6.4); built as designed in [sentinel-development.md](sentinel-development.md), "Replay over logs (R7)" ([pr-series.md](pr-series.md), "Replay through Scout (R7 PR 5)" and "Replay joins on ids (R7 PR C)"). Against each part of the requirement:

- **The same `@monitor` over stored logs.** `inspect_sentinel.scout.as_scanner(sentinel)` replays a monitor or protocol through the same runner as an eval, as a Scout transcript scanner, rebuilding the sentinel from its configuration in each Scout process.
- **What the monitor would have seen live.** One step builder in inspect_ai (`_sentinel/_steps.py`) serves the live dispatcher and the log driver (`steps_from_events()` in `_sentinel/_replay.py`), so a replayed `AfterGenerate` or `AfterToolCall` step has the live `input`, `tools`, `assistant_message`, `truncated` and `history`, after a compaction too (`input` is the request as sent, compacted). Absent in replay, as [replay.qmd](../docs/replay.qmd) lists: `AfterToolCall.output`, `agent_messages` and `view.context`.
- **Logs from before Sentinel.** Turns are inferred from the timeline where a log records no `origin` (R7 PR 6), and the `ApprovalEvent`s of inspect_ai's built-in `"human"` approver become `human_decisions`. A log from inspect_ai before 0.3.100, a transcript without model events and an import without `messages_from` replay from their messages, with less in each step; an import that records `messages_from` replays from its events (0.4.0, #193).
- **Matching a step live and in replay.** Every step has a stable step id (a generate's first `ModelEvent` uuid, a tool call's id or execution id, a bridged step `<model call uuid>/<call id>`). `as_reader()` reads what a sentinel recorded live as rows that join replay's, a bridge check through `replay_step_id` (0.4.0, #245); `compare_decisions()` lists each step's two decisions, and `replay_check()` with `replay_check_differences()` lists each field whose digest differs.
- **A chosen subset of steps.** `as_scanner(steps=)` takes a label table or a module-level selector; `stage=` and `depth=` narrow further.
- **Parallelism, prompt caching and `store_as` state.** Scout runs transcripts in parallel, across tasks and processes; each transcript replays as one sequential pass, steps in order with one store, the scope a monitor has live (decided by Charles 2026-10-26), so a monitor whose prompt grows with the conversation can use a provider's prefix cache as it does live.
- **Live and replay stay identical.** The shared builder is pinned by inspect_ai's test that steps rebuilt from a log equal the live ones field by field (R7 PR 3's acceptance); users run `replay_check()` over their own logs; the internal benchmark (`benchmarks/replay_trust/`, R7 PR 7) found replay trusted for a real monitor model.

Known limits and gaps, as [pr-series.md](pr-series.md), Deferred, records them unless noted:

- **A request filter that rekeys call ids can pair a check with the wrong step.** An `agent_bridge(filter=...)` that generates several responses and hands one over under a call id another of them proposed leaves the discarded generation as the one model call that proposed the id, so read mode pairs the check with its step and `compare_decisions()` lists the pair `matched`. Documented in `as_reader()` and [replay.qmd](../docs/replay.qmd#bridged-agents), and pinned by a test; shipped so by Charles on 2026-11-23. The fix records the proposing model call on the bridge's check event ("Exact joins for bridge checks, from a recorded producer").
- **Read mode doesn't join renamed calls.** A call the bridge handed over under a fresh id (when the model reuses an id for a different call) is replayed under that id, which read mode doesn't match, so its check is `"only recorded"` (same entry).
- **Replay of Claude Code auto-mode logs written before the classifier is fixed is quadratic in side calls** (deferred by Charles 2026-11-19; a lazy fold would make it linear).
- **Claude Code's auto-mode classifier is recorded as agent turns.** Through the bridge its requests have origin `agent` and share the main conversation, so they duplicate the conversation in `history`, get generate steps of their own, and make the history fold quadratic in side calls, live and in replay (deferred by Charles 2026-11-19; blocked on how Claude Code treats a classifier model name).
- **A stored timeline can change which result steps replay builds.** With `as_scanner(timeline=)` each event's conversation is the stored timeline's (`_conversation` in inspect_ai's `_sentinel/_replay.py`), and a bridged call's `tool_result` step is built only where its conversation proposed the call id once, while read mode's `replay_step_id` assumes a replay without `timeline` (`replayed_step_ids` in `scout/_steps.py`). So with `timeline=` a bridge check can be left unmatched where replay built its step under the timeline's conversations, or name a step that replay did not build. Not yet on pr-series.md's Deferred list.
- **A checked native run replay skips can take the next run's row**, under a reused call id with a sentinel `modify` replay can't place: a wrong join, documented in `as_reader()`, not fixed.
- **Concurrent agents whose provider reuses call ids** fail replay with `MalformedLogError`, since step ids are unique per sample (deferred by Charles 2026-11-07).
- **An operator's cancel of a running tool** is recorded as the tool's timeout, so replay keeps an `AfterToolCall` that live dropped.
- **Not built:** parallelism within one transcript (opt-in, by conversation or compaction segment), `as_scanner(recorded_answers=False)`, and a public API for testing a monitor over a hand-written conversation. Scout hands replay each model input expanded, which is quadratic in turns but cheap into thousands of turns.

**R8.** Checked against Scout `main` (fdc17b34) and sentinel `main` (dc2d26e) on 2026-11-22, and rechecked on 2026-11-23 against the released code: 8.4 (#266), 8.7 (#267), 8.3 (#268), 8.9 (#269) and 8.2 (#270) shipped in sentinel 0.4.0, with Scout 0.6.4, the dependency floor, rendering the placeholders and compaction tags. The items below were written on 2026-11-22 from those PRs as built, and match the released code. Sentinel renders a step with `render_step()` (`_preprocess.py`, used by `step_as_str()` and `Host.score`), which renders messages through Scout's `message_numbering()` (`inspect_scout/_scanner/extract.py`). The shared renderer, which moves Scout's `messages_as_str`, `message_as_str` and `MessageFormatOptions` into inspect_ai with output exactly Scout's, is still planned, not started ([pr-series.md](pr-series.md), Deferred, "Shared message rendering, then the prompt helpers").

- **8.1.** Met with a nonce. Scout's renderer takes `nonce=` (Scout #709) and writes it on every marker: message headers, `Tool Call`/`Tool Use` lines, tool error lines, `<thinking>`, `<thinking_summary>` and `<prefill>` tags, and `[BEGIN 'key']`/`[END 'key']` lines around an argument that spans lines (Scout #726). Sentinel's `[BEGIN ...]`/`[END ...]` block lines and `[TOOL CHOICE]` line carry it too. `Host.score` generates one per sample and its prompt tells the model that a marker without it is content (sentinel #105). `step_as_str()` adds it only when passed one (see "`step_as_str` nonce by default" in [pr-series.md](pr-series.md)). Without a nonce, agent text can still imitate every marker.
- **8.2.** Met in sentinel (2026-11-22): `StepPreprocessor(omit_assistant_text=True)` takes the text out of every assistant message a step shows (the three lists, the text beside a tool stage's call, and `AfterGenerate`'s reply) and keeps the tool calls. Reasoning follows `omit_reasoning`, so a monitor can judge actions with or without it, and a provider's own tool use follows `omit_tool_usage`. An assistant message left with nothing, such as a final answer of text alone, is left out of the lists ([sentinel.md](sentinel.md), "Step preprocessing"). In Scout, `exclude_tool_usage` removes tool calls and results, and there is no option that keeps only them.
- **8.3.** Met in Scout and sentinel (2026-11-22; Scout 0.6.4, the dependency floor, renders the compaction tags). A provider's own compaction is data content holding `compaction_metadata`: Anthropic's (`"anthropic_compact"`) holds a readable summary, which now renders between `<compaction_summary>` tags with or without a nonce; OpenAI's (`"openai_compact"`) is encrypted and renders as `<compaction_unreadable 3f9a1c7e />` with a nonce, or `<data />` without one, as before. `StepPreprocessor(omit_unreadable_compaction=True)` leaves an unreadable one out, and a message left with nothing else with it. `Host.score`'s default prompt says what the two tags mean. Inspect's summary compaction writes its summary as a user message of text (`metadata={"summary": True}`), which renders readably as an ordinary `USER` message whose text contains Inspect's `[CONTEXT COMPACTION SUMMARY]` label; the label is text, so agent text can imitate it, and after a provider merge the message may also hold the task or another user turn. A `COMPACTION SUMMARY` header for Inspect's summary was built and dropped in review (2026-11-22, Charles), so do not re-add it without trusted provenance from inspect_ai: the summary's only marks are `metadata={"summary": True}` and Inspect's fixed text, which a scaffold can also write, so the header could be forged without the nonce (and Scout's pre-existing `role_label` metadata could produce the same header); and monitors see the input after inspect_ai's provider collapse (`Model._prepare_input()` merges consecutive user messages for Anthropic, Bedrock, vLLM and others before the generate stages, and `ModelEvent.input` and replay record the merged request), so the task and the summary usually arrive as one message that could not honestly carry the header anyway. Neither the `"summary"` key nor `compaction_metadata` is documented by inspect_ai, so `compaction_metadata` is read as inspect_ai writes it today; the `compaction_summary(step)` helper still waits on inspect_ai documenting the `"summary"` key (Deferred, Later).
- **8.4.** Met with a nonce. A tool error renders on an `Error in tool call` line that carries the nonce, so the agent cannot fake it. Truncation is on the step as `AfterToolCall.truncated`, built from `ToolEvent.truncated`, so it is the same live and in replay. When it is a `Truncation`, `render_step()` opens the `RESULT` block with a line that carries the nonce, `[OUTPUT TRUNCATED (3f9a1c7e)] The tool's output was 48,210 bytes; the agent's model was shown at most its first 8,192 and last 8,192 bytes, with the middle left out.`, and `Host.score`'s default template says what the line means. A tool output that holds Inspect's "too long" notice or imitates the line lacks the nonce. Where the host cannot tell (`None`: a proxy, a replay from messages) no line renders, so a cut there shows only as Inspect's notice in the result text. The standalone `result_as_str(result, truncated=)` that [sentinel.md](sentinel.md), "The helpers", plans is not built; it moves with the shared renderer. Where in the text the cut falls is not marked (pr-series.md, Deferred, "Marking the cut point").
- **8.5.** Partly met. `message_numbering()` labels messages `[M1]`; tool call ids are not rendered. `step.human_decisions` and `human_decision_for()` give the decisions, but the renderer does not annotate the calls they cover.
- **8.6.** Met in Scout: `format="list"` gives one string per message. The plan requires the moved renderer's output to match Scout's.
- **8.7.** Met except the TASK block (built 2026-11-22; Scout 0.6.4, the dependency floor, renders the placeholders). Images, audio, video, data and documents render as placeholders naming their type, and with a nonce the placeholder carries it (`<image 3f9a1c7e />`), so agent text cannot imitate one; a content type the renderer does not know renders the same way, named by its type, with or without a nonce, rather than being dropped. At a tool stage, such content in the assistant message that made the call (an image beside the call) renders in the `CALL` block after the call's text. `unrenderable(step)` lists each such content part in a step (the part of the step, the message's position and id, and the type), counted on the step as `preprocess_step()` leaves it, so windows, omissions, `hide_messages` and `transform` apply: content in a hidden message, or in a hidden result of the step's own call, is not counted, since the prompt shows the hidden-messages marker in its place. `Host.score` counts the same, less messages its head cut drops, into `Observation.metadata` (`{"unrenderable": {"input": {"image": 2}}}`), and its `on_unrenderable` option fails closed: `"flag"` returns suspicion 1.0 for every dimension without asking the model, `"raise"` raises so the runner records the monitor as failed. The default is `"score"`, since in a computer-use eval nearly every tool result is a screenshot. Redacted reasoning is not counted, nor is a provider's compaction that Scout shows as its summary (Anthropic's); one Scout shows as `<compaction_unreadable 3f9a1c7e />` (OpenAI's) is counted as `data`, by Scout 0.6.4's rule (`_provider_compaction_text`). The default template tells the model that a nonce-marked placeholder stands for content it is not shown. The exception is `Host.score`'s TASK block: content in the sample's input that is not text is dropped from it without a placeholder and is not counted, so `on_unrenderable` does not fail closed on it ([pr-series.md](pr-series.md), "Content the TASK block cannot show"; Deferred, Later).
- **8.8.** Met by sentinel: `render_step()` renders the request's tools as JSON in a `TOOLS` block while `input` is known. Scout has no `ToolInfo` renderer.
- **8.9.** Met for sentinel monitors (2026-11-22). `StepPreprocessor(hide_messages=...)` takes a predicate over `ChatMessage` and hides the system, user and tool messages it matches from every list the step shows, an `AfterToolCall` step's own result, and `Host.score`'s TASK block, always leaving a nonce-marked `[N messages hidden (nonce)]` line in their place, so the monitor can tell something was hidden and the agent cannot forge the marker. It never hides an assistant message, so the agent's replies and tool calls, including the step's own call and reply, are always shown (decided 2026-11-23). Matching metadata the eval sets, the agent cannot trigger the hiding either; matching text, which is the only option for bridged agents, it can get a tool result or a user message it wrote (a sub-agent's prompt) hidden, but never its own actions. The marker can't be turned off and never holds message text. What was hidden is recorded on the thinned step (`hidden`). A hidden step result is shown as the marker after its call, and the step is scored; hiding never makes `Host.score` raise. In-process the eval matches on message metadata; through the agent bridge neither metadata nor ids reliably survive, so the docs say to match on text, with that limit. A step a protocol thinned keeps its TASK hidden when a child scores it. A compaction summary that restates a hidden message is left to the filter (inspect_ai records no compacted span). Scout's `MessagesPreprocessor.transform` remains free-form, with no marker. It is named "hide" because the sidecar's `Withheld` is a different thing: a turn held back from the eval, not from the monitor.

## Conflicts with recorded decisions
